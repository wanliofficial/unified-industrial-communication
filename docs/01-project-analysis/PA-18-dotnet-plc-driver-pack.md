# PA-18　.NET PLC 驱动包

## 1　定位与问题域

### 1.1 项目定位

该方案是一个 .NET 平台的 PLC 通信驱动包集合，以 NuGet 包分发，目标框架为 `netstandard2.0;netstandard2.1`，可同时被 .NET Framework 与 .NET Core / .NET 5+ 引用。代码约 74 个 C# 文件、7,863 行。它不做平台、不做采集调度、不做存储，只做一件事：**把「读 PLC 标签、写 PLC 标签」做成可被任意上位机系统引用的库**。

许可证为 MIT，可嵌入闭源商业产品。形态决定了它不承担平台级责任（调度、存储、可视化、多租户），也因此工程完成度显著高于同批的平台型方案。

### 1.2 解决的核心问题

| 问题 | 方案的回答 | 完成度 |
|---|---|---|
| 不同厂商协议差异大 | 泛型驱动接口 + 按厂商实现，地址语义由类型参数承载 | 高：两家厂商均可用 |
| 厂商原生协议栈不可控 | 原生库按平台/架构打包，P/Invoke 调用，风险限制在 Windows | 中：隔离但不消除 |
| 数据类型多、样板代码多 | 泛型读写 + 静态分派写入 + 结构体映射 | 高 |

### 1.3 与另两案的取向差异

| 维度 | PA-16 | PA-17 | PA-18 |
|---|---|---|---|
| 形态 | 单二进制平台 | 多服务分层平台 | NuGet 驱动库 |
| 范围 | 接入+存储+规则+界面 | 接入+存储+告警+AI+界面 | 仅 PLC 读写 |
| 协议自主性 | 自研 broker | 自研报文 | 封装厂商原生栈 |
| 工程完成度 | 低-中 | 中 | 高 |

PA-18 是三案中范围最窄、单点做得最实的一例：价值不在功能多，而在每个功能都真的能用。

## 2　功能分析

### 2.1 功能域与完成度

| 功能域 | 功能点 | 实现方式 | 完成度 |
|---|---|---|---|
| 驱动抽象 | 连接/单点读写/批量读写 | 泛型接口，地址类型由调用方指定 | 完整 |
| 厂商 A · 标签式 EtherNet/IP | 标签读写 | 封装厂商原生 DLL，单次上限 1,994 字节 | 完整 |
| 厂商 A · 扩展 | 标签扫描 + 不限长度读 | 扩展驱动调用增强接口 | 完整 |
| 厂商 B · ADS | 索引地址 / 符号地址读写 | 索引表达式与变量名两种寻址 | 完整 |
| 类型系统 | 位/字节/字/双字/结构体 | 定宽类型 + 结构体反射映射 | 完整 |
| 泛型写入 | 无装箱写入 | 每类型一个写入器，静态分派 | 完整 |
| 原生依赖 | 按平台/架构隔离 | 运行时标识目录 + P/Invoke | 仅 Windows |
| 交付 | 自动构建 + 包发布 | 托管 CI，标签触发发布 | 完整 |

### 2.2 核心机制

**泛型接口统一了不同厂商的地址语义。** 接口声明连接、断开、单点读写、批量读写；类型参数表示地址形态——一方是标签名字符串，另一方是索引表达式或符号名。调用方在编译期即确定地址类型，厂商差异被挡在实现内部。

**厂商 A 的驱动是对原生栈的封装，不是自研协议栈。** 驱动通过 P/Invoke 调用厂商提供的标签读写动态库（分 x86/x64 两套），基础接口单次读取上限 1,994 字节，增强接口取消该限制并支持标签扫描。这个判断很重要：方案的能力边界完全取决于厂商动态库，也决定了它只能在 Windows 上运行。

**厂商 B 的驱动建立在 ADS 之上。** 索引驱动接受十六进制索引表达式，符号驱动按变量名访问；底层引用厂商官方 ADS 客户端包。两代运行时的端口段不同（801/811/821/831 与 851/852/853/854），站点地址形如 `A.B.C.D.1.1`，且要求本机安装路由服务。

**类型系统覆盖工业常用宽度。** 8/16/32/64 位定宽类型对应字节、字、双字、长字；结构体映射用反射把 .NET 结构体对齐到 PLC 连续地址；写入器按类型静态分派，避免装箱与运行时类型判断。这是该库最可直接复用的部分。

## 3　架构分析

### 3.1 模块关系

```
调用方（上位机 / SCADA / MES）
        ▼
驱动接口层（泛型 连接/读写/批量）
   ├── 厂商 A 驱动（基础 + 扩展） ──▶ 原生 DLL（P/Invoke）
   │                                  runtimes/win-x64|x86
   └── 厂商 B 驱动（索引 + 符号） ──▶ 官方 ADS 客户端包
类型层：定宽类型 · 结构体映射 · 写入器分派（被两侧共用）
```

结构是「接口 + 厂商实现 + 类型 + 原生」四段，没有分层框架也没有领域模型。对一个只做读写的库，这个粒度是合适的——再抽一层就是过度设计。

### 3.2 关键抽象与职责边界

| 抽象 | 职责 | 边界问题 |
|---|---|---|
| 泛型驱动接口 | 连接生命周期 + 读写 + 批量 | 无异步成员，长读阻塞调用线程 |
| 地址表达式 | 承载厂商特定寻址语义 | 解析失败在运行期才暴露 |
| 写入器分派 | 按类型选择无装箱写入路径 | 自定义类型需自行扩展 |
| 结构体映射 | .NET 结构体 ↔ 连续地址 | 对齐与字节序依赖调用方约定 |
| 原生绑定 | 声明并调用厂商动态库 | 平台/架构不匹配时运行期失败 |

### 3.3 并发模型

该库不创建线程，也不提供异步接口：所有读写都是同步阻塞调用，驱动实例本身不是线程安全的（推断：未见锁或连接池实现）。调用方若要并发访问同一 PLC，需自行加锁或每线程一个实例。

| 项 | 现状 | 影响 |
|---|---|---|
| 调用模型 | 同步阻塞 | 高频采集需调用方自行编排线程 |
| 连接复用 | 调用方持有驱动实例 | 库内无连接池 |
| 并发安全 | 无明显同步措施 | 共享实例并发读写存在竞态风险 |
| 背压 | 不涉及 | 请求节奏完全由调用方控制 |

### 3.4 故障恢复与平台约束

| 项 | 现状 | 评价 |
|---|---|---|
| 超时与重试 | 依赖底层，库未提供统一参数 | 弱 |
| 断线重连 | 由调用方重新调用连接 | 弱 |
| 平台约束 | 厂商 A 仅 Windows；厂商 B 客户端包只提供旧框架资产 | 中 |
| 兼容性告警 | 新运行时引用旧资产会告警，方案以抑制方式处理 | 中：行为差异未知 |

「延迟失败」是本方案最需注意的运维特性：在非 Windows 平台引用包不会编译失败，而是在首次连接时因找不到动态库抛出异常。调用方应在启动阶段主动探测平台与架构并给出明确提示。

### 3.5 协议清单

| 协议名 | 角色 | 传输 | 代码位置/模块 | 备注 |
|---|---|---|---|---|
| EtherNet/IP（标签式） | 客户端 | TCP | 厂商 A 驱动目录 | 封装原生 DLL，单次上限 1,994 字节 |
| EtherNet/IP（扩展） | 客户端 | TCP | 厂商 A 驱动目录 | 标签扫描，取消长度上限 |
| ADS（索引寻址） | 客户端 | TCP | 厂商 B 驱动目录 | 十六进制索引表达式 |
| ADS（符号寻址） | 客户端 | TCP | 厂商 B 驱动目录 | 按变量名访问 |
| ADS（协议栈） | 客户端 | TCP | 官方客户端包 | 两代运行时端口段不同 |

## 4　需求分析

### 4.1 谁在什么现场

| 角色 | 现场 | 显性需求 | 隐性需求 |
|---|---|---|---|
| 上位机开发者 | Windows 工控机，单机部署 | 引用即用、类型安全 | 线程安全、超时可控 |
| 设备集成商 | 多厂商混合产线 | 覆盖主流 PLC | 扩展成本、版本兼容 |
| 跨平台项目 | Linux 边缘盒、容器 | 任意平台运行 | 明确的能力声明 |
| 合规敏感方 | 需审计协议实现 | 可审计协议栈 | 源码级可控 |

### 4.2 隐性需求的覆盖缺口

| 隐性需求 | 覆盖情况 | 说明 |
|---|---|---|
| 断网续传 | 未覆盖 | 库不缓存、不重发 |
| 点位变更不停机 | 部分覆盖 | 标签/符号寻址可动态改，索引地址需重连 |
| 地址越界保护 | 部分覆盖 | 依赖底层返回错误码 |
| 字节序与字序 | 部分覆盖 | 定宽类型有约定，结构体需调用方保证 |
| 批量读优化 | 覆盖 | 原生批量接口 + 扩展读 |
| 诊断可观测 | 弱 | 无内置日志与指标，需调用方埋点 |
| 许可与合规 | 覆盖 | MIT，商用无障碍 |

### 4.3 适用与不适用

**适合**：Windows 平台的上位机、SCADA、MES 客户端；需要快速接入这两家 PLC 的项目；需要把 PLC 读写嵌入自有产品的商业交付。

**不适合**：Linux 或容器化部署；需要覆盖大量厂商；需要自主可控、可审计协议栈；需要采集调度、存储、可视化的完整平台。

## 5　可借鉴与应规避

### 5.1 值得借鉴

| 设计 | 说明 |
|---|---|
| 泛型驱动接口 | 用类型参数承载厂商地址语义，编译期即确定寻址形态 |
| 写入器静态分派 | 每类型一个写入器，避免装箱与运行期分支 |
| 结构体映射 | 结构体与连续地址自动对齐，便于批量读写结构化数据 |
| 运行时标识目录 | .NET 标准原生依赖隔离方式，一包多架构 |
| 基础/扩展驱动分离 | 把「够用」与「增强」拆成两个类型，降低认知负担 |
| 标签触发发布 | 托管 CI 自动构建并推包，发版可复现 |

### 5.2 应规避

| 设计 | 问题 | 替代做法 |
|---|---|---|
| 封装厂商动态库 | 能力受制于厂商，无法跨平台、无法审计 | 关键场景自研协议栈，或明确标注平台限制 |
| 延迟失败 | 非 Windows 引用不报错，连接时才失败 | 启动期探测平台/架构并快速失败 |
| 无统一超时与重试 | 网络抖动由调用方兜底 | 提供可配置超时、重试与熔断 |
| 同步阻塞且无并发保护 | 共享实例存在竞态 | 提供异步接口或线程安全封装 |
| 抑制兼容性告警 | 旧资产在新运行时行为未知 | 升级到标准目标框架版本，或标注支持矩阵 |

## 6　结论

### 6.1 总体评价

PA-18 是范围最窄、单点最实的一例。价值在于**用泛型接口 + 静态分派 + 原生依赖隔离，把 PLC 读写做成可被任意上位机引用的库**；局限在于**封装厂商原生栈而非自研协议**，导致能力受制于厂商、无法跨平台、无法审计。

三个方案不在同一层面竞争：PA-16 与 PA-17 是整机，PA-18 是零件。一个完整系统可以同时使用三者——用分层方案做骨架，用驱动库做现场接入，用前者的主题契约做消息总线约定。

### 6.2 六维评分

| 维度 | 评分 | 理由 |
|---|---|---|
| 协议广度 | 2.0 | 仅两家厂商、四种寻址形态，覆盖面窄但每种都真实可用 |
| 架构可演进性 | 3.5 | 接口/实现/类型/原生四段清晰，新增厂商需改包而非插件 |
| 跨平台能力 | 1.5 | 原生栈仅 Windows；另一家客户端包只提供旧框架资产 |
| 可运维性 | 2.5 | 包版本可追溯，但无日志、无指标、无超时重试封装 |
| 工程质量 | 4.5 | 构建与测试可过、CI 完整、多架构打包规范 |
| 许可与合规风险 | 5.0 | MIT，嵌入闭源产品无障碍 |

### 6.3 三条关键结论

1. **「封装厂商栈」是效率与自主可控的交换。** 协议细节交给厂商，开发成本低、兼容性好；代价是能力边界、平台支持与可审计性都由厂商决定。评估时必须区分「自研协议栈」与「封装厂商协议栈」——前者是能力，后者是集成，二者不应同分。
2. **泛型接口 + 静态分派是性能与类型安全的平衡点。** 编译期确定地址类型、运行期避免装箱，API 也比「每类型一个方法」更简洁。这套做法可直接移植到其他语言的驱动库设计中。
3. **工程成熟不等于能力完整。** 该方案在构建、测试、CI、打包四项上明显优于两个平台型方案，但它只解决「PLC 读写」一件事。把库与平台放进同一张表比总分，既会低估平台的价值，也会高估库的适用范围。
