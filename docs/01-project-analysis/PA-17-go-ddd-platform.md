# PA-17　Go 语言 DDD 分层工控平台

## 1　定位与问题域

### 1.1 项目定位

该方案是一个按领域驱动设计（DDD）分层组织的 Go 工控物联网平台，覆盖协议驱动、采集调度、数据流水线、告警、AI 推理与可视化全链路。代码约 173 个 `.go` 文件、49,510 行，严格按 `domain / application / infrastructure / interfaces` 四层划分。

许可证为 MIT，可自由用于商业场景。但它是**服务形态**而非库形态：可以被整体部署，不能被当作依赖嵌入其他进程。

### 1.2 解决的核心问题

| 问题 | 方案的回答 | 完成度 |
|---|---|---|
| 如何用一套架构承载多协议 | 协议驱动接口 + 进程内注册表，协议差异隔离在驱动层 | 中：Modbus 完整，其余多为报文构造 |
| 如何把采集、存储、告警、AI 串成流水线 | DAG 工作流 + 节点执行器注册 | 中：引擎可用，节点实现多为占位 |
| 如何支撑生产部署 | 关系库 + 时序库 + 缓存 + 指标 + 容器编排 | 中：组件齐全，接口大量未实现 |

### 1.3 与另两案的取向差异

| 维度 | PA-16 | PA-17 | PA-18 |
|---|---|---|---|
| 形态 | 单二进制平台 | 多服务分层平台 | NuGet 驱动库 |
| 复杂度放置 | 运行时（配置驱动） | 设计期（分层抽象） | 接口期（泛型契约） |
| 状态归属 | 进程内全局变量 | 数据库 + 缓存 | 无状态 |
| 变更成本 | 加表/加页面近乎零成本 | 加功能需改五层 | 加厂商需写驱动 |
| 工程完成度 | 低-中 | 中 | 高 |

PA-17 是三案中架构纪律最强、但「可运行」与「可交付」差距最大的一例。

## 2　功能分析

### 2.1 功能域与完成度

| 功能域 | 功能点 | 实现方式 | 完成度 |
|---|---|---|---|
| 协议采集 | Modbus RTU/TCP/ASCII | 帧编解码 + CRC16/LRC，串口/TCP 通道 | 完整 |
| 协议采集 | PROFIBUS / EtherNet/IP / HART / DeviceNet / PROFINET / EtherCAT | 报文构造，部分仅接口 | 低：无连接管理 |
| 协议采集 | OPC UA | 依赖可选构建标签，默认桩实现 | 低 |
| 采集调度 | 分组批量读 | 按设备分组合并请求 | 中：依赖驱动的批量能力 |
| 数据流水线 | 采集 → 处理 → 落库 | 单协程顺序处理 + 批量写入器 | 低-中：无背压 |
| 存储 | 关系库 + 时序库 + 缓存 | 迁移脚本 + 仓储实现 + 缓存封装 | 中：表结构多，实体不完全对齐 |
| 告警 | 规则评估 + 通知 | 规则实体 + 评估方法 | 低：评估方法为未完成桩 |
| AI 推理 | 5 类模型定义 | 模型结构 + 简化前向计算 | 低：占位实现 |
| 工作流 | DAG 编排 + 节点执行 | 邻接表 + 拓扑排序 + 执行器注册 | 中：引擎可用，节点多为桩 |
| 北向接口 | REST + WebSocket | 路由层 + 实时推送 | 中：路由约 185 条，推送满即丢 |
| 可观测 | 指标 + 健康检查 + 结构化日志 | 标准端点 | 高 |
| 认证授权 | JWT + RBAC | 中间件 + 权限存储 | 中：默认弱口令 |

### 2.2 核心机制

**四层隔离靠接口下沉实现。** 领域层定义实体与仓储接口，基础设施层用 ORM 实现仓储，应用层编排用例，接口层只做协议转换。依赖方向单向，因此「换存储」「换协议」原则上只需替换基础设施实现。这是方案最值得肯定的部分，也是它区别于 PA-16 的根本点。

**串口默认模拟，且没有真实打开路径。** 串口实现的「模拟」标志默认为真，读取返回构造数据；即使显式关闭模拟，代码中也没有串口参数（波特率、校验、流控）的配置路径，取不到真实串口。这是「默认安全但功能不可用」的典型：默认值保护了演示环境，却没有为生产留出通路。

**协议驱动与节点执行器都靠注册表扩展。** 驱动由工厂返回并登记到设备管理器，采集器按协议类型创建；工作流节点由执行器工厂按类型创建，允许注册自定义节点。相比 PA-16 的动态库方案，这种做法没有 ABI 版本问题，代价是新增协议必须重新编译整个服务。

**数据流水线是单协程顺序处理。** 构建出的流水线只有一个处理方法，从输入通道读数据，依次执行处理器链，写输出通道；没有并行、没有分段、没有背压。协程池在队列满时直接丢弃任务，批量写入器在提交失败时丢弃缓冲。对可容忍丢失的环境采集够用，对计费、审计类数据不可接受。

**AI 与告警是架构占位。** 五类模型（长短期记忆、门控循环、卷积、注意力、自编码）的结构定义完整，但前向计算是简化算式；规则检测节点直接返回固定判定与固定分数；告警规则评估方法为未完成桩。方案的真实价值是「预留了扩展位置」，而不是「提供了推理能力」。

### 2.3 工程完成度的关键事实

| 事实 | 证据形态 | 影响 |
|---|---|---|
| 全仓构建失败 | 并发工具包引用了已改名的旧包路径（该路径在仓库中不存在）；示例目录引用多个不可达包 | 只有服务入口可构建 |
| 测试极少 | 仅基础设施层 2 个测试文件 | 领域层、应用层、驱动层零覆盖 |
| 接口多为桩 | 数据源创建对 Modbus/串口直接返回未实现；执行器工厂返回未实现；告警评估返回固定值 | 关键路径不可用 |
| 迁移与实体不一致 | 17 个迁移、49 张表，部分字段与实体定义不匹配 | 运行时可能出现映射错误 |
| 默认弱口令 | 初始管理员账号为常见默认值 | 部署即风险 |

这些事实共同决定：该方案是**架构示范 + 可运行原型**，不是可交付产品。

## 3　架构分析

### 3.1 模块关系

```
┌───────────────────────────────────────────────┐
│ 接口层  REST 路由 │ WebSocket 推送 │ 中间件      │
└───────────────┬───────────────────────────────┘
                ▼
┌───────────────────────────────────────────────┐
│ 应用层  设备 │ 采集 │ 告警 │ 工作流 │ 用户       │
└───────┬──────────────────────────┬────────────┘
        ▼                          ▼
┌───────────────────┐   ┌────────────────────────┐
│ 领域层 实体 + 仓储接口│   │ 基础设施层 仓储实现/串口/  │
│ （无外部依赖）       │◀──│ 消息/认证/AI 实现        │
└───────────────────┘   └────────────────────────┘
                ▲
                │
┌───────────────┴───────────────────────────────┐
│ 采集执行链：驱动工厂 → 采集器 → 流水线 → 批量写 │
└───────────────────────────────────────────────┘
```

组装点只有一个服务入口，手工完成依赖注入，未使用代码生成或容器框架。小规模下清晰，规模扩大后组装点会膨胀。

### 3.2 关键抽象与职责边界

| 抽象 | 职责 | 边界问题 |
|---|---|---|
| 协议驱动接口 | 定义连接、单点读写、批量读写 | 批量能力只在 Modbus 驱动实现，其他协议缺 |
| 仓储接口 | 领域层声明的持久化契约 | 部分实现绕过接口直接使用 ORM，破坏可替换性（推断） |
| 采集器接口 | 按分组调度设备读取 | 分组与时间片策略耦合在应用层 |
| 节点执行器 | 工作流单步处理 | 多数实现为固定输出，无法承载真实逻辑 |
| 推理模型接口 | 统一前向计算入口 | 实现为简化算式，未接真实模型运行时 |
| 消息推送中心 | 向订阅端广播实时数据 | 满即丢，无降级策略 |

### 3.3 并发模型

| 环节 | 模型 | 上限/参数 | 风险 |
|---|---|---|---|
| 服务入口 | 每请求一协程 | 无显式上限 | 无准入控制 |
| 采集调度 | 分组串行轮询 | 按配置间隔 | 慢设备拖慢整组 |
| 数据流水线 | 单协程顺序 | 无 | 单处理器阻塞即全链阻塞 |
| 协程池 | 有界队列 + 丢弃 | 队列满即丢 | 高峰丢数据 |
| 批量写入 | 定时/定量提交 | 提交失败丢缓冲 | 落库缺口 |
| WebSocket | 广播 + 丢弃 | 慢消费者丢消息 | 大屏可用，审计不可用 |

整体是「一处顺序处理 + 多处可丢弃队列」的组合。没有背压信号从下游回传到采集端，也没有优先级区分，控制指令与遥测数据走同一条通道。

### 3.4 故障恢复与运维能力

| 项 | 现状 | 评价 |
|---|---|---|
| 设备重连 | 驱动层有连接状态，未见指数退避与熔断 | 中 |
| 断点续采 | 无本地缓存补发，无 Outbox | 弱 |
| 数据补传 | 批量写失败即丢，无重试队列 | 弱 |
| 配置校验 | 启动时部分校验，协议参数缺失运行期才暴露 | 中 |
| 可观测 | 指标端点、健康检查、结构化日志齐备 | 高 |
| 部署 | 容器编排清单齐备，支持横向扩副本 | 中：有状态组件需外置 |
| 安全 | JWT + 角色权限完整；默认口令弱；串口默认模拟 | 中 |

### 3.5 数据模型

数据模型以关系库为主、时序库为补充，17 个迁移脚本、49 张表。核心聚合包括：设备、点位、采集分组、告警规则、工作流定义与执行记录、模型注册、用户与权限。迁移方式为 ORM 自动迁移与手写 SQL 混用，这本身是风险来源——两套机制对同一张表的结构认知可能分叉。

## 4　需求分析

### 4.1 谁在什么现场

| 角色 | 现场 | 显性需求 | 隐性需求 |
|---|---|---|---|
| 中大型甲方 | 多厂区、多租户生产环境 | 高可用、可审计、可扩展 | 权限隔离、数据保留策略、合规 |
| 系统集成商 | 交付周期 3–6 个月的项目 | 架构清晰、易维护 | 交付文档、二次开发成本 |
| 算法团队 | 需要把模型接入产线数据 | 推理入口、模型版本管理 | 特征对齐、漂移监控、回滚 |
| 设备厂商 | 接入自有协议 | 驱动接口稳定 | 兼容性承诺、升级路径 |
| 小型团队 | 快速验证想法 | 上手快、依赖少 | 低运维成本 |

### 4.2 隐性需求的覆盖缺口

| 隐性需求 | 覆盖情况 | 说明 |
|---|---|---|
| 断网续传 | 未覆盖 | 无本地缓存补发，队列满即丢 |
| 时钟漂移 | 部分覆盖 | 数据带时间戳，无对时机制 |
| 点位变更不停机 | 部分覆盖 | 元数据可改，采集器需重启生效（推断） |
| 地址越界保护 | 部分覆盖 | Modbus 有范围校验，其他协议缺 |
| 字节序与字序 | 部分覆盖 | Modbus 有明确处理，跨协议无统一约定 |
| 批量读优化 | 部分覆盖 | 仅 Modbus 支持批量 |
| 诊断可观测 | 覆盖 | 指标、健康检查、日志齐备 |
| 许可与合规 | 覆盖 | MIT，无传染性 |

### 4.3 适用与不适用

**适合**：需要长期维护、多人协作的中大型项目；需要多租户与可观测的生产环境；需要把 AI 推理嵌入数据流的架构预研。

**不适合**：资源有限、要求快速原型的团队（分层过重）；高吞吐且不可丢数据的场景（单协程 + 丢弃队列）；需要开箱即用推理能力的项目（模型为占位）。

## 5　可借鉴与应规避

### 5.1 值得借鉴

| 设计 | 说明 |
|---|---|
| 四层严格隔离 | 接口下沉到领域层，基础设施只做实现，替换成本低 |
| 驱动 + 执行器双注册表 | 协议与工作流节点都能按类型扩展，无 ABI 约束 |
| 分组批量读 | 把同组设备的离散点位合并为连续请求，显著降低往返 |
| DAG 工作流 | 邻接表 + 拓扑排序 + 节点注册，可编排复杂处理链 |
| 版本化迁移 | 17 个迁移脚本记录 schema 演进，可回溯 |
| 可观测三件套 | 指标端点、健康检查、结构化日志，生产可用 |
| 多环境配置 | 配置文件 + 环境变量 + 命令行覆盖 |

### 5.2 应规避

| 设计 | 问题 | 替代做法 |
|---|---|---|
| 串口默认模拟且无参数配置 | 默认拿不到真实数据，关闭模拟仍不可用 | 默认模拟 + 显式开启 + 完整串口参数 + 启动自检 |
| 流水线单协程 | 单处理器阻塞全链，无背压 | 分段并行 + 有界队列 + 下游反馈 |
| 队列满即丢 | 池、写缓冲、推送三处都丢 | 关键路径阻塞或落盘，非关键路径降级 |
| 接口留桩不标注 | 调用方难以判断能力边界 | 要么实现，要么显式返回「不支持」并记录 |
| 模型占位当能力 | 评估与使用都会误判 | 明确标注实验状态，或在构建期禁用 |
| 默认弱口令 | 部署即风险 | 首启强制改密 + 强哈希 |
| 全仓构建失败 | 示例与工具包失修，CI 缺失 | 门禁构建 + 最小测试集 |

## 6　结论

### 6.1 总体评价

PA-17 是三者中架构纪律最强、工程完成度居中偏下的一例。价值在于**用四层隔离把「换存储、换协议、换模型」的成本压到最低**；风险在于**可运行与可交付之间存在实质缺口**——全仓构建失败、测试仅两个文件、关键接口留桩、模型为占位。

与 PA-16 相比，两者是同一问题的两种解法：PA-16 用配置换开发速度，PA-17 用分层换长期可维护性。与 PA-18 相比，PA-17 的广度更大、深度更浅。

### 6.2 六维评分

| 维度 | 评分 | 理由 |
|---|---|---|
| 协议广度 | 3.0 | 列出十余种协议，实际可用者主要是 Modbus 三形态；其余为报文构造或接口 |
| 架构可演进性 | 4.5 | 四层隔离 + 接口下沉 + 双注册表，替换实现的成本是三案中最低 |
| 跨平台能力 | 4.0 | 纯 Go 无 CGO 依赖，可交叉编译；串口实现缺失削弱了实际跨平台价值 |
| 可运维性 | 3.5 | 指标、健康检查、迁移、编排清单齐备；缺断路器与补发机制 |
| 工程质量 | 2.0 | 全仓构建失败、测试近乎为零、接口大量留桩、迁移与实体不一致 |
| 许可与合规风险 | 4.5 | MIT，商用与闭源集成均无障碍 |

### 6.3 三条关键结论

1. **分层是核心价值，样板是必然代价。** 四层隔离让「换实现」变便宜，「加功能」变贵——新增一个用例往往要动实体、仓储接口、仓储实现、应用服务、路由五处。适用前提是团队规模与项目周期足以摊薄这部分固定成本。
2. **「默认模拟但无真实通路」比「未实现」更危险。** 默认值让演示顺畅，关闭模拟却没有串口参数配置，用户会误以为已经接入真实设备。正确形态是：默认模拟 + 显式开关 + 完整参数 + 启动自检并在界面明示当前处于模拟态。
3. **架构评分与工程评分必须分开。** 该方案的架构可演进性接近满分，工程质量却明显不及格；若合并成一个总分，会同时误导「值得借鉴」与「可以直接用」两种判断。评估结论应当明确：借鉴其分层与注册表设计，不要直接采用其实现。
