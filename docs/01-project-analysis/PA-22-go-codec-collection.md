# PA-22｜Go 工业协议编解码库集合

> **分析对象**：纯库集合（单 Go module、多协议包，无服务、无 CLI、无调度）
> **编号**：PA-22（按脱敏约定，不披露来源标识）
> **技术栈**：Go 1.20；仅依赖 can/serial 两个外部库（串口与 CAN）与若干同作者工具库；无框架、无 CGO
> **规模画像**：23 个包目录、92 个 `.go`（66 生产 / 26 测试）、9,989 行（生产 8,924）；58 个测试函数、0 个基准
> **成熟度画像**：个人协议实验田——覆盖面 20+ 协议，深度与质量差异极大；无 README、无 LICENSE、单次提交

---

## 1. 定位与问题域

### 1.1 它是什么

一个"协议帧工厂"式仓库。每包基本按同一模板写：`NewXxx()` 造请求结构体 → `Bytes()` 序列化 → `DecodeXxx([]byte)` 反序列化响应 → 少量 `GetInt/GetFloat/GetBool` 取值助手。根包只有两个声明：`Interface{ Bytes() }` 与 `ReadFunc func(*bufio.Reader) ([]byte, error)`，外加一段注释说明"协议不关心传输，传输只需 `io.ReadWriteCloser`"。用法因此极简：用库拼一帧，自己建 socket/串口把帧发出去，再把响应字节丢回 `Decode`；库内除 Modbus 服务端外没有任何连接、重连、调度代码。

### 1.2 面向的用户与场景

- **写采集器的 Go 开发者**：已有传输与调度层，只缺"这家的帧怎么拼、CRC 怎么算"，希望按需 import 一个包而不是引入整套运行时。
- **协议对照与移植**：包内保留了大量地址换算、CRC 表与帧字段布局，可当实现参考；但**不适合直接选型**（无文档、无许可、无版本 tag，部分包是空壳）。

### 1.3 边界（不做什么）

- **不做连接与可靠性**：无连接池、重连、超时、重试、采集调度，一律交给调用方；**不做协议状态机**：S7 只造请求与拆响应，Modbus 服务端是唯一带循环的组件。
- **不做点表/北向**：没有"设备/点位/通道"概念，也不产出统一数据模型，只产出各协议自己的结构体。

## 2. 功能分析

### 2.1 功能域总览

| 功能域 | 功能点 | 实现方式 | 完成度 |
|---|---|---|---|
| 帧编解码 | 请求序列化、响应反序列化 | 每包一组 `NewXxx/Bytes/DecodeXxx` 函数 | 覆盖面广，深度不一 |
| 客户端请求构造 | 读写寄存器/变量、握手、启动停止 | 结构体字面量 + 显式长度/校验字段 | 主流协议可用 |
| 服务端 | Modbus TCP/RTU 从站 | 内置监听、功能码分发表、线圈/寄存器回调 | 仅此一处，功能完整 |
| 分包与值转换 | 从字节流切帧；整数/浮点/布尔/位序转换 | `ReadFunc`/`ReadFrom` + `bufio.Reader`；`GetInt/GetFloat/GetBool` | 可用，但无长度上限、无类型系统 |
| 非工业协议 | IP/ICMP、HTTP、M3U8、Base64、DNS、手柄 | 同类帧结构 + 编解码 | 说明其真实定位是"字节工具集" |

### 2.2 协议与接口覆盖

| 协议/接口 | 角色 | 传输 | 代码位置（角色名） | 备注 |
|---|---|---|---|---|
| Modbus RTU/TCP | 主站 + 从站 | TCP / 串口 | `modbus` 包（约 1,385 行） | 客户端覆盖 8 个功能码，3 个方法直接返回"未实现"；服务端含 TCP/RTU 监听 |
| S7（S7comm） | 主站 | TCP（由调用方建连） | `siemens/s7`（631 行） | 握手/读写帧 + 地址解析（`DB1.DBX0.0`）+ 值解码；`ReadFrom` 从 `io.Reader` 拆包 |
| MC 协议 | 主站 | TCP | `mitsubish/mc`（288 行） | Type3E 帧，位/字设备 |
| FINS / Host Link | 主站 | TCP / 串口 | `omron/fins`（407）、`omron/hostlink`（202） | FINS 为 TCP 帧；Host Link 靠分包函数拆帧 |
| DLT645 / IEC 104 / DNP3 / BACnet / KNX / ADS | 编解码 | TCP/UDP | 各包 337–796 行 | 请求+响应帧齐全，无会话状态；KNX 的 `Register` 直接读写传入的 `io.ReadWriter` |
| CIP / CAN / DNS / PROFIBUS | 占位或骨架 | — | `omron/cip` 4 行、`can` 23 行、`dns` 11 行、`profibus` 277 行 | cip 为空结构体；can/dns 只有注释与字段；profibus 的 `Read()` 是空函数 |

### 2.3 典型使用流程

```
client := modbus.NewTCP(1)                                  // 只选协议与从站号
req, _ := client.ReadHoldingRegisters(0, 10)                // 拿到 []byte，不含发送
conn.Write(req); resp := readExactly(conn, 25)              // 传输完全自备
frame, _ := client.Decode(resp)                             // 帧结构体
data, _ := client.DecodeData(resp)                          // 数据域（去掉功能码/字节数）
```

这段流程就是全库的"契约"：**编码与解码是纯函数，传输与超时是调用方的责任**。它让库可同时服务 TCP、串口、蓝牙甚至内存回环，但也意味着每个调用方都要重写分包与错误处理。

## 3. 架构分析

### 3.1 分层与模块

```mermaid
flowchart LR
    A[调用方采集器] -->|NewXxx| B[请求结构体]
    B -->|Bytes| C[[]byte 帧]
    C --> D[自备传输<br/>TCP/串口/回环]
    D --> E[响应字节]
    E -->|DecodeXxx| F[响应结构体]
    F -->|GetInt/GetFloat/GetBool| G[字段值]
    subgraph 库内
      B
      C
      F
    end
```

包与包之间没有 import 关系，也没有共享的文件/工具层：CRC 在 Modbus 与 DNP3 各写一份，字节序处理在每个包里重复，`GetInt/GetFloat` 只在 S7 有。这是"复制而非抽象"的组织方式——加协议快，跨协议统一慢。

### 3.2 关键抽象与接口

| 抽象 | 职责 | 边界 | 位置 |
|---|---|---|---|
| `Interface{ Bytes() }` | 给"可序列化帧"一个最小约束 | 只有一个方法，不表达解码、类型或错误；多数包并未显式实现或引用它 | 根包 |
| `ReadFunc(*bufio.Reader) ([]byte, error)` | 分包函数：从流中切出一帧 | 由调用方循环调用；无超时、无最大长度；读失败常以 panic 收场 | 根包 |
| Modbus `Frame` 接口 | 取/设控制码、数据、序列化 | 只有 Modbus 使用；服务端靠它做通用应答 | `modbus` |
| Modbus `Server` | 监听、功能码分发表、线圈/寄存器回调 | 把 `net.Listener` 与串口放进协议包，与根包"协议不关心传输"的主张相反 | `modbus` |

根包那段注释是本仓库最好的设计陈述，但它只是**声明**：实际边界由每个包自觉维持，结构上没有任何东西阻止协议包引入 socket。各包的解码函数命名也不统一（`Decode`/`DecodeData`/`DecodeValue`/`Parse`），错误语义各异。

### 3.3 数据流与时序

全部是同步纯函数调用，没有事件循环或回调链（Modbus 服务端除外）。请求侧：结构体 → 补长度/校验 → `[]byte`；响应侧：`[]byte` → 校验（CRC/长度/从站号）→ 结构体 → 值转换。库本身不缓存、不复用、不重试，所有状态在调用方手里；分包是唯一"有状态"的环节，`bufio.Reader` 由调用方持有，`ReadFunc` 每次消费一帧——半包、粘包、超时都要调用方自己处理。

### 3.4 并发与连接管理

| 主题 | 做法 | 评价 |
|---|---|---|
| 并发模型 | 库内无 goroutine（Modbus 服务端每连接一个） | 客户端侧天然可并发，但共享状态未加锁 |
| 共享状态 | S7 的包级随机数、Modbus 客户端的 `slave/model` | 并发调用 S7 构造函数会竞争同一 `rand.Rand`（推断） |
| 服务端并发 | 每连接一 goroutine，无连接数上限、无读写超时 | 慢客户端可长期占住 goroutine |
| 背压与恢复 | 无；连接由调用方持有 | 断线、超时、重试全部由上层实现 |

### 3.5 配置、部署与扩展

无配置文件、无数据库、无部署形态，是一个纯 import 的库；仓库只有一次提交、没有 tag，`go.mod` 用伪版本锁定同作者工具库，引用方只能锁 commit，且无 CI、无 lint、无 CHANGELOG。新增协议 = 新建目录 + 结构体 + `Bytes()`/`DecodeXxx()`，无需注册；代价是没有统一入口——做"通用采集器"必须在调用方写 `switch protocol`，并适配各包不同名、不同返回类型的解码函数。

### 3.6 工程质量观察

- **测试**：58 个测试函数、0 个基准；92 处 `t.Log` 对约 41 处断言，多数用例只打印十六进制串；测试里还留着 `192.168.10.x` 的内网设备地址，部分用例必须连真机。
- **明确缺陷**：`DecodeRTU` 先做一次 CRC 比较，判据用 `&&` 连接两个字节的比较（应为 `||`），随后又用十六进制字符串重复比较一次——第一次判断既错又多余；`DecodeTCP` 把控制码直接当 `error` 返回，判据写成 `> 0x80` 而非 `>= 0x80`，异常码本身不参与错误构造。
- **健壮性**：`ReadFrom` 在读错误时 `panic`；`profibus.Read()` 是空函数；CIP/CAN/DNS 只有类型定义。**合规**：无 LICENSE、无 README，注释里贴外部博客链接作参考。

## 4. 需求分析

### 4.1 显性需求

1. 用 Go 拼装与解析多种工业协议帧，不引入重框架、不依赖 CGO。
2. 传输自由：TCP、串口、蓝牙、内存回环都能复用同一份编解码。
3. 覆盖主流 PLC 与电力/楼宇协议（S7/MC/FINS、DLT645/IEC104/DNP3/BACnet/KNX），API 足够轻。

### 4.2 隐性需求

| 隐性需求 | 方案中的对应处理 | 若缺失的后果 |
|---|---|---|
| 统一错误语义 | 各包自定义 error 文本与返回形态 | 无法区分"设备拒绝""校验失败""链路错误" |
| 分包边界 | `ReadFunc` 约定 + 头部长度字段 | 异常长度或半包可导致阻塞或越界读 |
| 并发安全 | 未声明；S7 使用包级随机数 | 多设备并发采集时消息号可能重复（推断） |
| 版本与兼容 | 单次提交、无 tag、无 CHANGELOG | 引用方无法锁定行为，升级即可能破坏 |
| 许可与文档 | 无 LICENSE、无 README，测试充当示例 | 企业无法合规引入，使用者只能读实现猜语义 |

### 4.3 非功能需求

| 维度 | 现状 | 判断 |
|---|---|---|
| 性能 | 大量 `append` 与临时切片；无基准测试 | 单帧开销可接受，但无数据支撑（推断） |
| 可维护性 | 每包自洽、命名风格统一（`mb_`/`s7_`/`fins_` 前缀） | 单包好读，跨包难统一；测试以打印为主，回归价值低 |
| 安全 | 无长度上限、`panic` 混入库路径、测试含内网地址 | 不适合直接暴露在不可信网络 |

### 4.4 需求缺口与误判

| 缺口 | 证据 | 影响 |
|---|---|---|
| 抽象只剩一个 `Bytes()` | 根包接口无解码、无类型、无错误 | 无法做统一驱动层，"多协议"在调用方退化为 switch |
| 分层主张与实现不符 | Modbus 包内置 listener 与串口 | "协议与传输解耦"只对客户端成立 |
| 空壳与实现混放 | cip 4 行、can 23 行、dns 11 行 | 按包数量评估覆盖面会严重高估 |

## 5. 可借鉴与应规避

### 5.1 可直接吸收的机制

1. **请求/响应分离的纯函数编解码**：`NewXxx() → Bytes()` 与 `DecodeXxx()` 都不碰网络，天然可单测、可跨传输复用。目标产品的驱动层应保持这个形状：编码器只吃"地址+类型+值"，解码器只吃"字节+模板"。
2. **分包函数作为一等公民**：`ReadFunc(*bufio.Reader) ([]byte, error)` 把"怎么从流里切一帧"独立出来，TCP 粘包、串口半包、自定义封装都能套同一层。
3. **按协议分包、零跨包依赖**：任何协议出问题不影响其他协议，引用方只 import 需要的包；地址解析与值转换单独成文件，便于对照规范逐条验证。

### 5.2 明确应规避的做法

| 做法 | 问题 | 目标产品应如何做 |
|---|---|---|
| 库内 `panic` + 把控制码当 error | 进程级故障；异常码丢失 | 一律返回 error，定义携带功能码与异常码的异常类型 |
| 重复且错误的校验 | `DecodeRTU` 两次 CRC、第一次判据错误 | 校验只做一次，写表驱动测试 |
| 空壳包不标注 | 使用者按包名以为支持 CIP/CAN | 未实现的能力不导出，或在文档中标注状态 |
| 无 LICENSE/README | 无法合规引入，也无法判断 API 语义 | 首日就补许可、示例与版本 tag |
| 测试只打印 | 回归时无法发现行为变化 | 断言字节序列与错误分支 |

### 5.3 迁移到目标产品的成本

**低**：帧布局、CRC 表、地址解析、值转换可直接对照复用（重写比读文档快）。**中**：分包函数与 Modbus 服务端的回调模型。**高**：作为依赖直接引入——无许可、无版本、无错误语义、无会话状态机；S7/MC/FINS 只到"单帧"级别，批量读、多变量读、重连都要自己补。

## 6. 结论

### 6.1 六维评分

| 维度 | 分数(1-5) | 理由 |
|---|---|---|
| 协议广度 | 4 | 20+ 协议、含电力与楼宇，广度罕见；但深度从 4 行到 1,385 行不等 |
| 架构可演进性 | 2.5 | 包独立、易加协议；但抽象只剩 `Bytes()`，跨协议统一要在调用方做 |
| 跨平台能力 | 4.5 | 纯 Go、无 CGO，除串口/CAN 外全平台可用 |
| 可运维性 | 1 | 库形态无运维面；无版本、无 CI、无文档，出问题只能读源码 |
| 工程质量 | 2 | 有测试但以打印为主，存在 CRC 判据错误与 `panic`，空壳包与真实实现混放 |
| 许可与合规风险 | 1 | 无 LICENSE、无 README，依赖同作者工具库，企业不可直接引入 |

### 6.2 三条关键结论

1. **覆盖面是假象，深度才是能力。** 包目录数看着像"支持 20 多种协议"，实际能直接用的是 Modbus、S7、FINS、Host Link、DLT645 等少数几个；CIP/CAN/DNS/PROFIBUS 是空壳。评估这类库必须按"每包行数 + 可调用函数"逐项核实，而不是数目录。
2. **"协议不关心传输"方向正确，但只做到一半。** 客户端确实是纯编解码，可 Modbus 服务端把 listener 与串口塞进了协议包——边界靠作者自觉维持，结构上没有任何隔离。目标产品若沿用这个主张，应把传输抽成接口并把分包器作为参数注入。
3. **它是参考实现，不是依赖。** 帧布局、CRC、地址解析值得对照，但无许可、无版本、无统一错误语义、无会话状态机，直接 `import` 会把合规与可靠性风险一起带进来；正确用法是"读它、抄它的字节布局、自己写状态机与测试"。
