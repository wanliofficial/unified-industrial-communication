## 1. 产品定位

### 1.1 一句话

> **UIC 是一个可治理、可测试、可回滚的跨平台工业连接底座：单二进制部署，协议驱动可插拔，从第一天起就带虚拟设备与配置版本。**

### 1.2 它是什么

| 是 | 说明 |
|---|---|
| 南向采集运行时 | 连接 PLC、仪表、楼宇设备、电力设备，按点位采集 |
| 北向数据网关 | 通过 REST / SSE / MQTT / OPC UA 把数据交付给上层系统 |
| 边缘自治单元 | 断网继续采集、本地缓存补发、本地报警、看门狗自愈 |
| 可运维的软件产品 | 指标、健康检查、配置版本、远程命令、诊断包 |
| 驱动开发平台 | 提供驱动 SDK、虚拟设备、故障注入与一致性测试 |

### 1.3 它不是什么（边界）

| 不是 | 理由 |
|---|---|
| 组态软件 / HMI 绘图器 | 这是独立产品；UIC 通过 API 把数据交给现成的 SCADA/HMI |
| 时序数据库 | 用 SQLite（边缘）与客户既有 TSDB（中心）；不自研存储引擎 |
| 云端 SaaS 平台 | Wave 3 之前只做边缘软件 + 可选中心聚合器 |
| 全协议一站式替代品 | Wave 1 只做 12 个协议，但每个都做到可测试 |
| 硬实时控制器 | 闭环周期 100ms–1s 级，不做 μs 级运动控制 |
| Windows 桌面工具 | 主形态是无头服务 + Web 控制台 |

### 1.4 目标用户与角色

| 角色 | 谁 | 核心诉求 | 与产品的主要交互 |
|---|---|---|---|
| **现场工程师** | 电气/自动化工程师 | 快速接通设备、看到数据、改点不重启 | Web 控制台、点表导入、实时监视 |
| **系统集成商** | 项目交付方 | 批量配置、模板复用、快速复制到多个站点 | 模板 + CLI + 配置导入导出 |
| **运维人员** | 客户 IT/OT 运维 | 知道哪里坏了、能远程修、改错能退 | 指标、健康、诊断包、远程命令 |
| **上层开发者** | MES/SCADA/云平台开发 | 稳定的 API、清晰的契约、可预期的错误 | REST / SSE / MQTT / OPC UA |
| **驱动开发者** | 内部或合作方 | 不接真机也能开发与验证驱动 | 驱动 SDK + 虚拟设备 + 一致性套件 |

### 1.5 三个典型场景

**场景 A：产线设备上云（汽车零部件）**

- 现场：3 条产线，18 台 PLC（S7-1200/1500、CIP），约 1200 个点位。
- 诉求：数据每 1s 上云；断网不能丢；点位变更不停线。
- UIC 的回答：模板化配置（3 个模板 × 6 实例）；时间片调度；Outbox 补发；热更新。

**场景 B：水务泵站远程运维（无人值守）**

- 现场：12 个泵站，每站 1 台边缘盒子（ARM64，1GB 内存），IEC 104 + Modbus 电表。
- 诉求：无人值守；远程改配置；坏了能自愈；有审计。
- UIC 的回答：单二进制 ARM 部署；配置版本 + 回滚；看门狗；RBAC + 审计。

**场景 C：楼宇能耗采集（多协议混合）**

- 现场：一栋楼，BACnet 空调、Modbus 电表、MQTT 传感器。
- 诉求：统一命名空间；按楼层/系统分组；数据给能耗平台。
- UIC 的回答：四类寻址统一模型；命名规范；REST/SSE 输出；OPC UA 映射。

## 2. 产品原则

| # | 原则 | 具体含义 | 反面教材 |
|---|---|---|---|
| P1 | **可诊断优先于功能多** | 每个功能都必须能回答「它现在是否正常工作」 | 38 个方案中 34 个只有日志文件 |
| P2 | **运行时可无头** | 所有能力通过 API/CLI 可达；UI 只是客户端 | PA-10/35 的入口绑 UI |
| P3 | **配置即制品** | 配置有版本、可 diff、可回滚、可审计 | 改配置靠手工备份 |
| P4 | **无设备也能开发** | 每个驱动配虚拟设备与金报文 | 只能等现场有 PLC 才测 |
| P5 | **失败必须可见** | 不允许静默吞异常；每类失败有指标与日志字段 | PA-35 的多处 `catch {}` |
| P6 | **默认安全** | 默认认证、默认加密、无默认口令 | PA-21/26/31/37/38 的明文凭据 |
| P7 | **一种事实来源** | 点位当前值只在快照中；不允许多处缓存各自为政 | 多处 `Dictionary` 各自维护 |
| P8 | **向后兼容** | 配置格式、API、驱动契约都有版本与迁移路径 | 升级即重配 |

## 3. 功能需求

编号规则：`FR-<域>-<序号>`。优先级：M（Must）/ S（Should）/ C（Could）。

### 3.1 南向采集（COL）

| 编号 | 需求 | 优先级 | 验收标准 |
|---|---|---|---|
| FR-COL-01 | 支持 Modbus TCP 主站，含 FC1/2/3/4/5/6/15/16 | M | 对虚拟从站与真实设备均能读写 |
| FR-COL-02 | 支持 Modbus RTU/ASCII 主站，含串口参数与帧间延时 | M | 波特率 9600–115200 可配；半双工正确 |
| FR-COL-03 | 支持 Modbus TCP 从站（用于自测与替代设备） | M | 可被第三方 Modbus 主站读写 |
| FR-COL-04 | 支持 S7comm 主站（S7-300/400/1200/1500） | M | 支持 DB/IB/QB/MB 区；PDU 自动协商 |
| FR-COL-05 | 支持 OPC UA 客户端（读/写/订阅） | M | 支持 SecurityPolicy None/Basic256Sha256 |
| FR-COL-06 | 支持 MQTT 南向订阅取数 | M | QoS 0/1；断线重订阅 |
| FR-COL-07 | 支持虚拟设备驱动（正弦/斜坡/随机/常量/故障注入） | M | 无真实设备可跑通全链路 |
| FR-COL-08 | 驱动能力四态声明（支持/不支持/视情况/实验性） | M | 控制台按四态渲染徽标 |
| FR-COL-09 | 批量读规划（寄存器合并、符号分组、非法跨越拒绝） | M | 100 个离散点合并为 ≤ N 个请求 |
| FR-COL-10 | 每点位独立采集周期（可覆盖设备周期） | S | 快变量 100ms、慢变量 10s 并存 |
| FR-COL-11 | 写入（单点/多点），含写后校验与超时 | M | 写入成功/失败/超时三态明确 |
| FR-COL-12 | 订阅型协议支持（COV / 事件 / 通知） | C | Wave 2 |

## 4. 关键用户流程

### 4.1 首次开通（从零到看到数据）

```
启动 uic → 日志打印初始管理员口令
  → 浏览器打开 http://<ip>:8080
  → 强制改密 → 新建通道（选协议，填连接参数）
  → 测试连接（复用驱动的 Probe）
  → 新建设备（选模板或手工）
  → 导入点表 CSV（预览新增/冲突）
  → 启动采集 → 监视页看到点位值与质量码
  → 配置 MQTT/UA 北向 → 在第三方工具中验证
```

**目标**：熟练工程师 15 分钟内完成一台设备 50 个点的开通。

### 4.2 点位变更（不停产）

```
编辑点位 → 平台计算差异（新增 3 / 修改 1 / 删除 0）
  → 预览影响（受影响设备：1 台；预计重启 2s）
  → 应用 → 仅该设备重启采集，其余不受影响
  → 新版本号写入历史
```

### 4.3 远程排障

```
告警：设备 D-07 采集成功率 62%
  → 打开诊断：最近错误 Top3（超时 / 异常码 02 / CRC 错）
  → 查看该设备指标：P95 耗时 2800ms，重连 4 次/小时
  → 网络诊断：ping 通，端口通，但 RTT 波动 5–800ms
  → 结论：现场交换机问题（附证据）
  → 生成诊断包交给网络组
```

### 4.4 改错回滚

```
远程下发配置（版本 v42）→ 应用失败（点位地址越界）
  → 自动回滚到 v41（状态文件记录 rollbackCount=1）
  → 审计日志记录：谁、何时、下了什么、失败原因
  → 设备继续采集，业务无中断
```

## 6. 版本范围

### 6.1 Wave 1（MVP，3 个月）

**做**：Modbus TCP/RTU/ASCII（主站 + 从站）、S7、OPC UA 客户端与服务端、MQTT、REST/SSE；虚拟设备与故障注入；调度器；配置版本与回滚；Outbox；指标与健康；Web 控制台（最小集）；单二进制交付。

**不做**：BACnet、IEC 104、DL/T 645、CIP、MC、FINS；历史库；报警引擎；RBAC 细粒度；Sparkplug；进程外驱动。

| # | 门槛 | 判定 |

| 3 | 配置改错自动回滚 | 注入非法配置验证 |
| 4 | 1000 点 / 50 设备稳定运行 72h | 浸泡测试 |
| 5 | 安全扫描零高危 | 内网扫描 |
| 6 | 三个平台产物均能启动并通过 `/readyz` | CI 矩阵 |

## 7. 成功度量

| 指标 | 目标 | 观测方式 |
|---|---|---|
| 首次开通时间 | ≤ 15 分钟/设备 | 用户测试 |
| 现场故障平均定位时间 | ≤ 30 分钟 | 支持工单统计 |
| 配置变更回滚率 | 可回滚 100% | 审计日志 |
| 驱动开发周期（新协议） | ≤ 2 周（含测试） | 开发记录 |
| 单实例无故障运行 | ≥ 30 天 | 遥测（可选） |
| 单元 + 集成测试覆盖率 | ≥ 70%（核心包 ≥ 85%） | CI |

## 10. 术语表

| 术语 | 定义 |
|---|---|
| 通道（Channel） | 一条物理或逻辑链路（TCP 连接、串口、UDP 会话），是并发与故障的边界 |
| 设备（Device） | 一个可寻址的从站/站点，属于某个通道，含协议参数与点表 |
| 点位（Point） | 设备内的一个可读写数据项，含地址、类型、缩放、死区、单位 |
| 采样（Sample） | 一次采集的结果：值 + 质量码 + 设备时间 + 采集时间 + 序号 |
| 批读计划（Read Plan） | 把离散点位合并为若干连续读请求的规划结果 |
| 时间片（Time Slice） | 把设备轮询分散到固定时间槽，避免同时打满网络 |
| 质量码（Quality） | 描述数值可信度的枚举 |
| 代次（Generation） | 每次设备启动/重连递增的编号，用于丢弃迟到结果 |
| Outbox | 待上报消息的持久化队列，保证至少一次投递 |
| 配置版本 | 配置内容的哈希，配合备份与回滚形成可追溯的变更历史 |
| 运行态 | 设备的实际状态（连接中/采集中/降级/故障），与配置态分离 |
