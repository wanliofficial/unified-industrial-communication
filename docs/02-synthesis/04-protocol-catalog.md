# 总分析四｜协议目录：45 个工业协议的角色、难度与实现顺序

> **文档性质**：横切分析（协议视角）
> **数据来源**：38 份逐方案文档的协议清单交叉统计 + 各方案源码中的编解码实现
> **计数口径**：「提及」指该协议在 38 份文档中被讨论（含「未实现」「仅声明」）；「可实现参照」指有可核实的编解码代码
> **难度与优先级为主观评估**（已标注），其余为可核实事实
> **脱敏**：仅用 PA 编号

## 1. 为什么需要一份协议目录

工业协议不是一个平面清单，而是**四层结构 × 六类角色 × 四种寻址**的组合。同一个「Modbus」，作为主站、从站、网关、仿真器的实现难度差 5 倍；同一个「BACnet」，只做发现与做完整对象读写差 20 倍。

如果按「协议名字」排优先级，必然得出「先做 Modbus 再做 S7 再做 OPC UA」这种线性结论，而错过真正重要的维度：**哪些协议共享同一套传输与寻址，可以复用；哪些协议是完全不同的范式，必须单独设计。**

本文的组织方式：

```
§2  四层模型：把 45 个协议放回协议栈
§3  四种寻址：决定数据模型能否统一
§4  六张主表：按协议族给出角色/传输/难度/优先级/关键坑
§5  难度分级与工作量估算
§6  三波实现路线
§7  协议知识库的最小字段集
§8  规范获取与法律边界
```

## 2. 四层模型

工业协议的「层」与 OSI 不完全对应，按实现视角可分为：

```
┌──────────────────────────────────────────────────────────┐
│ L4 信息模型层  对象/属性/类型/伴生规范                       │
│    OPC UA Information Model · IEC 61850 SCL · BACnet Objects│
│    Sparkplug B 的 Topic 与 State · CIP 的 EDS/结构体        │
├──────────────────────────────────────────────────────────┤
│ L3 应用协议层  服务/命令/事务                                │
│    S7comm · CIP · FINS · MC · Modbus PDU · DNP3 · 104 ASDU  │
│    SECS-II · BACnet APDU · ADS · Host Link                  │
├──────────────────────────────────────────────────────────┤
│ L2 会话/封装层  连接管理/分片/序号/握手                       │
│    TPKT/COTP · ISO-on-TCP · BVLC/NPDU · HSMS · MMS          │
│    Modbus MBAP · DNP3 Link/Transport · IEC 104 APCI         │
├──────────────────────────────────────────────────────────┤
│ L1 传输层  TCP / UDP / 串口 / TLS / 总线                     │
└──────────────────────────────────────────────────────────┘
```

**这张图解释了为什么「协议数量」是个假指标**：45 个协议在 L1 只有 5 种，L2 约 15 种，L3 约 30 种，L4 只有 5 种。真正的复用点在 L1/L2，真正的工作量在 L3/L4。

| 层 | 可复用度 | 典型复用方式 |
|---|---|---|
| L1 传输 | 极高 | 一个 `Transport` 抽象覆盖 TCP/UDP/串口/TLS |
| L2 封装 | 高 | TPKT/COTP 被 S7 与 IEC 104 共用；MBAP 被四种 Modbus 变体共用 |
| L3 应用 | 低 | 每个协议独立，但可共享「事务号/序号/超时重试」骨架 |
| L4 信息模型 | 中 | OPC UA 与 IEC 61850 都是「类型 + 实例 + 属性」，可共享节点树结构 |

## 3. 四种寻址：决定数据模型

| 寻址 | 结构 | 协议 | 平台模型要求 |
|---|---|---|---|
| **寄存器** | `(区, 偏移, 长度, 类型)` | Modbus、DL/T 645、CJ/T 188、部分 PLC 直读 | 区枚举 + 位偏移 + 字序策略 |
| **符号** | `(路径, 下标)` | S7 DB 符号、CIP 标签、ADS 变量、OPC UA NodeId、M-Bus 记录名（`q:energy@1/2`） | 字符串路径 + 类型推导 + 数组下标 |
| **对象** | `(对象类型, 实例, 属性, 索引)` | BACnet、IEC 61850、SNMP OID | 四元组 + 属性枚举 + 索引 |
| **文件/记录** | `(文件ID, 记录ID, 偏移)` | IEC 61850 File Transfer、部分表计、OPC UA File | 三级定位 + 分块传输 |

**关键事实**：38 个方案中，能把两种以上寻址做成平台级模型的只有 4 个（PA-06、PA-08、PA-15、PA-24），能做三种以上的为 0。

这不是因为技术难，而是因为**产品通常从一个协议起家，地址模型被第一个协议塑形**。一旦定型，后续协议只能「打补丁」。

## 5. 难度分级与工作量估算

| 难度 | 含义 | 典型工作量（单人，含测试） |
|---|---|---|
| 1 | 无状态文本/JSON 协议 | 1–2 天 |
| 2 | 简单二进制帧 + 校验 | 3–5 天 |

| 5 | 需专用硬件/规范未公开/状态机复杂 | 2–4 月 |

### 5.3 一个重要的比例

从 38 个方案的实际代码量反推：

| 组成 | 占比 |
|---|---|
| 编解码 + 传输 | 45% |
| 会话/重连/批量 | 20% |
| 虚拟设备 + 测试 | 20% |
| 配置/诊断/文档 | 15% |

**多数方案只做了前 45%**，因此「能跑通」与「能上生产」之间差了整整一倍工作量。这就是 G3 缺口的量化表达。

## 6. 三波实现路线

### Wave 1（第一版，12 个协议，约 3 个月）

| 协议 | 角色 | 理由 |
|---|---|---|
| Modbus TCP / RTU / ASCII | 主站 + 从站 | 覆盖 60% 现场；从站用于自测 |
| S7comm | 主站 | 欧系产线标配 |
| OPC UA | 客户端 + 服务端 | 南向接标准设备，北向接 SCADA |
| MQTT | 客户端 | 北向事实标准 |
| REST / SSE | 服务端 | 集成与调试 |
| 虚拟设备（Modbus/S7/OPC UA） | 从站/服务端 | 无真机开发与 CI |

**Wave 1 的验收**：一台 ARM64 盒子，接一台真实 S7-1200 与一台 Modbus 电表，同时向 MQTT 与 OPC UA 输出，断网 24 小时后补发无空洞。

### Wave 2（第一年，11 个协议）

MC 3E、FINS、EtherNet/IP + CIP、BACnet/IP、IEC 104、DL/T 645、CJ/T 188、ADS、OPC DA 桥接、Sparkplug B、SNMP。

> 截至当前实现：MC 3E、FINS、EtherNet/IP + CIP、BACnet/IP、IEC 104、DL/T 645、
> CJ/T 188、SNMP v1/v2c/v3、ADS/AMS 已落地（各含编解码、主站、内置从站/服务端与自检 CLI）；
> Sparkplug B 作为 MQTT 北向的第二种载荷格式落地（编解码 + 生命周期状态机 + 集成测试）；
> OPC DA 桥接归入「不做/独立 Windows 桥接进程」（需要 DCOM/COM，零依赖 Go 不可实现）。
> 645 与 188 都是「表计语义寻址 + 压缩 BCD」，但帧层与字段模型不同：
> 188 只有一个 `0x68`、数据域不加 `0x33`、地址 7 字节且带仪表类型 `T`，一个 DI 是
> 一组字段（901F 在水表与热量表上布局不同）。点表因此从 `WidthProtocol` 进一步引入
> `DIBits`/`DIField`：DI 位数随协议变化，字段偏移只在 188 上允许非 0。
>
> SNMP 补的是「IT/基础设施」这一层：OID 寻址、一条 GET 带多个 varbind、协议自带的
> error-status / 异常标记。v3 的 USM 认证加密（MD5/SHA-1/SHA-2 系列 + DES/AES）已落地，
> 引擎发现、时间同步与密钥本地化全部用标准库实现；固定 engineID 只是省一次发现往返，
> 时间基准仍必须问一次。Trap 不做（轮询主站的采集语义与设备主动推不同）；Walk 只作为
> 自检接口，生产点表必须写明确 OID。一个坏 OID 在 v1 下会毁掉整批返回值，因此驱动对
> `noSuchName` 逐点重发。
>
> ADS 补的是「PLC 工程变量」这一层：地址不是寄存器号而是符号名，一次取值要先按名字
> 取句柄再按句柄读值，句柄随 PLC 重启失效。只做 AMS/TCP 上的符号读写；通知订阅、
> 符号表上传/浏览、跨 AMS 路由发现、多句柄合并读写都不做——它们各自是另一套状态机，
> 半成品比不做更难排查。TCP 48898 与 AMS NetId/端口是两层，配错时症状完全不同，
> 因此 `Open` 立即做 `ReadDeviceInfo` 握手，把错误提前到启动期。
>
> Sparkplug B 补的是「北向语义」而不是又一个南向协议：它把 MQTT 从「一条采样一条
> 消息」升级成带生命周期与序号的节点模型。值映射与 JSON 格式共用同一份 Sample 契约，
> 但 BIRTH/DEATH、序号回绕、bdSeq 与重连重发都要单独处理；因此编解码与状态机拆成
> 两个包，前者可以脱网做金帧测试，后者可以脱 Broker 做序号测试。DataSet、模板、
> 别名、报警出口都不做——它们各自是另一套状态机，半成品比不做更难排查。
>
> **CoAP**（编解码 + 主站 + 内置服务端 + `uic coapread` + `examples/coap.json`）补的是
> 「受限设备 / IoT」这一层：没有寄存器、没有对象索引，数据模型就是 URI 资源；载荷是
> 文本或 JSON，由 `Content-Format` 声明，驱动按声明解码而不是猜。它真正的难点不在发
> 一个 GET，而在三处：**报文标识（MID）与事务标识（Token）要分开**——ACK/RST 看 MID、
> 业务响应看 Token，混用会在分离响应下丢掉真正的响应；**选项 delta 是相对值且扩展字节
> 先 delta 后 length**，写反会让解析器从下一个选项开始读垃圾；**收到空 ACK 后只能等分离
> 响应、不能重发**，否则服务端会把同一动作执行两次。此外首个请求默认不带 Block2 由服务端
> 决定块大小、`4.02` 时退回一次；UDP 重传窗口必须不越过设备级 `timeout`，否则一轮采集会被
> 拖成点位数 × 超时。不做 DTLS、Observe 订阅、Block1 分块发送、CBOR——`Subscribe` 在能力
> 声明里诚实标为 unsupported，一次性 GET 不伪装成推送。

**Wave 2 的验收**：覆盖汽车零部件（CIP）、3C（MC）、水务（104/645）、楼宇（BACnet）四类典型场景。

### Wave 3（第二年，6 个协议）

IEC 61850、SECS/GEM、KNX、Mewtocol、Host Link、MTConnect。

> DNP3、CoAP 与 IEC 101 已在此前落地（见本节末尾的「截至当前实现」），本波补齐其余。

| 协议 | 角色/传输 | 为什么值得做 | 最小可行版本 |
|---|---|---|---|
| **IEC 61850（MMS）** | 客户端 / TCP 102 | 变电站自动化的事实标准；逻辑设备/逻辑节点/数据对象的层次模型是唯一能表达「一台 IED 上有哪几个保护」的寻址方式 | MMS 会话（Initiate/Terminate）+ 读/写已知引用（`LD0LLN0.$MX$...`），不做 SCL 解析、Report、GOOSE、SV |
| **SECS/GEM（HSMS）** | 设备/主机 / TCP 5000 | 半导体设备与工厂的通信主干；PA-31 是 38 份分析里唯一带真实测试的协议 | HSMS 通信层 + SECS-II 数据项编解码 + 少量 SxFy 消息，不做上层设备模型的全部场景 |
| **KNXnet/IP** | 客户端 / UDP 3671 | 楼宇自控第一大总线；组地址模型（GA vs PA）是它的核心 | TUNNELING 请求 + 组地址读写，不做 routing / device management / 安全 |
| **Mewtocol** | 主站 / 串口或 TCP（端口各厂不同，默认 2000） | 松下 PLC 的事实协议；全 ASCII 帧看起来简单，真正的坑是一帧里混着十进制与十六进制 | 主站 + 字区读写 + 接点按字/按点读写 + 定时器值 + 错误码映射，不做 FP2-ET-LAN 封装 |
| **Host Link** | 主站 / 串口（RS-232/422/485）或串口服务器 TCP | 上位链接是欧姆龙小型 PLC 的默认串口协议；它有两种命令集，选错等于重写一遍驱动 | 只做 **FINS 帧（头码 `FA`）**，命令语义与 FINS/TCP 共用；不做 C 模式、跨网长格式、自动重试 |
| **MTConnect** | 客户端 / HTTP | 机床数据采集的事实标准；纯 REST + XML，无二进制编解码 | HTTP GET 取 `probe`/`current`/`sample`，XML 解析，不做资产/事件完整模型 |

> 截至当前实现：MC 3E、FINS、EtherNet/IP + CIP、BACnet/IP、IEC 104、DL/T 645、
> CJ/T 188、M-Bus、DLMS/COSEM、SNMP v1/v2c/v3、ADS/AMS、SECS/GEM、KNXnet/IP、Mewtocol、Host Link、IEC 61850（MMS）、IEC 101、DNP3、CoAP、MTConnect、BACnet MS/TP 已落地（各含编解码、主站、内置从站/服务端/Agent 与自检 CLI）；
>
> **DNP3**（编解码 + 主站 + 内置从站 + `uic dnp3read` + `examples/dnp3.json`）：只做
> TCP 主站、类 0 总召唤、类 1/2/3 事件轮询、CROB 与组 41 直接控制、未请求响应的接收
> 与确认；不做串口、安全认证、文件传输、时间同步写路径、SBO 两段式控制。三层协议最
> 难的不是字段编码，而是**三种确认不能漏**：链路 ACK、传输分片重组、应用层 CON。
> 漏掉应用层确认会让从站事件缓冲区被重发撑爆，现场表现为「跑了几小时后全是旧值」。
> 另外两个线格式陷阱——双点静态量是 2 位/点、静态变体 2 只有「状态+品质」字节而没有
> 独立位图——都已用往返自洽测试钉死。
>
> **CoAP**（编解码 + 主站 + 内置服务端 + `uic coapread` + `examples/coap.json`）：只做
> 明文 UDP 主站、GET/PUT/POST、Block2 分块接收、`/.well-known/core` 资源发现；不做
> DTLS、Observe 订阅、Block1 分块发送、CBOR。它的难点不在「发一个 GET」，而在
> **报文标识与事务标识要分开**（ACK/RST 看 MID、业务响应看 Token）、**选项 delta 是
> 相对值且扩展字节先 delta 后 length**、以及**收到空 ACK 后只能等分离响应、不能重发**。
> Block2 的首请求默认不带选项，由服务端决定块大小；服务端回 `4.02` 时退回一次。
> JSON 写入只发 selector 子树，不做隐藏的读-改-写。
>
> **SECS/GEM**（编解码 + 主站 + 内置设备 + `uic secsread` + `examples/secs.json`）：只做
> HSMS/TCP 主站，消息面覆盖 S1F1/F2、S1F3/F4、S1F11/F12、S1F13/F14、S2F13/F14、
> S2F15/F16、S5F1/F2、S6F11/F12；不做时间（S2F17/S2F31）与报告定义/链接
> （S2F33~S2F45），那些是改设备侧配置的调试动作。点位用**对象地址**承载协议原生编号
> （`svid:1001.value` 只读、`ecid:200.value` 可写），不发明符号映射。四处真正会踩的坑：
> 控制消息的 Stream/Function 线上填 `0xFF`；格式字节低 2 位是**长度字节数**而不是长度
> 值（`00`/`01` 都是 1 字节）；L 项的长度是**子项个数**；整数定宽大端，3 字节的 U4 是
> 畸形而不是「补个 0」。事务配对要同时满足「同 SystemBytes + 同 Stream + Function=
> 请求+1 + W 位清零」，设备异步推的 S6F11 必须丢弃继续读——按 Function 相同去匹配，
> 现象就是「设备明明回了、驱动却总超时」。读按对象类型分组，3 个 svid 点是 1 次事务；
> 写只有 ecid，`ACKC7=0` 才接受，且只认点表里声明过 `writable` 的点（读可按地址临时
> 解析，两者刻意不对称）。
>
> **IEC 60870-5-101**（FT1.2 帧 + 主站 + 内置从站 + `uic iec101read` + `examples/iec101.json`）：
> 只做**非平衡式主站**（串口 / 串口服务器透传），应用层与 104 共用 `codec/iec60870`，本波
> 只新增帧层与轮询语义；不做平衡式、FT1.1、文件传输、时钟同步写路径、带时标命令、选择-
> 执行、分组召唤。它值得单列，是因为**「104 的串口版」这个说法只在应用层成立**：104 双方
> 都能发言、靠 15 位序号与 k/w 流控；101 只有主站能发言，从站被点名才回答，可靠性靠
> 帧计数位 FCB + 链路确认 + 应用层激活确认。这直接决定了驱动的形状——`Read` 必须**真的
> 走总线**（每轮请求第 1 级、按周期站总召唤 + 电能量召唤），而不是像 104 那样只查本地表。
> 四处线格式陷阱：长度字段只计「控制域 + 链路地址 + ASDU」（整帧 = `L+6`）；校验和从控制
> 域累加到 ASDU 末字节；单字节帧没有地址也没有控制域（`E5` 与 `A2` 不能混同）；四类报文
> （总召唤、电能量召唤、时钟同步、初始化结束）**没有信息对象地址**，按通式多写 1..3 个
> 零字节，对端会把整条 ASDU 当未知报文丢弃。另有两处「不是协议但会致命」的工程约定：
> 重传必须复用同一帧字节（重新组帧会把 FCB 翻转成一条新命令，开关被拉合两次）；写入必须
> 等应用层激活确认（链路 `E5` 只说明报文到了）。剖面宽度（ORG/CA/IOA）全部走设备标签，
> 默认值取「一台装置一个公共地址、站内点数不超过 65535」，把某一组当标准写死是接不同
> 厂家装置时最先撞上的墙。

> **Mewtocol**（编解码 + 主站 + 内置从站 + `uic mewtocolread` + `examples/mewtocol.json`）：
> 只做计算机链接的 ASCII 裸帧，串口与串口服务器 TCP 双承载；不做 FP2-ET-LAN 的 16 字节
> 封装、二进制变体、`SC`/`SD` 整块置位、扩展头发送，也不做自动登录。它全 ASCII、抓包可读，
> 看起来比 Modbus RTU 简单，但一帧里混着三种进制：站号两位**十进制**（16 号站写 `16`）、
> 数据区地址五位十进制（DT100 → `00100`）、接点编号是「三位十进制字 + 末位十六进制」
> （X1F → `001F`、X16.3 → `0163`）、定时器接点四位十进制（T10 → `0010`）、数据内容每字节
> 两位十六进制且**字内低字节在前**（H0063 → `6300`）、BCC 两位十六进制且**从帧头 `%` 起算、
> 不含 CR**。任何一处读错都不报格式错，PLC 会回一份**别的地址**的数据——值有、质量好、
> 对应关系全错，是这套协议最典型的假绿。另外四处必须按字节记住：读用「起止地址」而不是
> 「起点 + 个数」；写也带结束地址（冗余，但与数据长度不自洽就回 41H）；应答只回显前两位
> 命令码（`RCC`→`RC`、`WCS`→`WC`）；`RCC`/`WCC` 地址 4 位而 `RD`/`WD` 是 5 位。容量上限
> 也要自己推：读应答 `9+4n`、写请求 `20+4n`，118 字符下取较小者 `MaxWords = 24`；接点按点
> 读写的上限 8 来自「个数」只有一位字符，拆帧绕不开。三条刻意边界：布尔量只走 `WCS` 原子
> 单点写（读-改-写会覆盖同字邻位）；字区上的布尔点位可读不可写（协议没有位写命令）；
> T/C 接点不走 `RCC`（手册会把它们按「每字 16 点」重新编号，与十进制定时器号是两套体系），
> 只走 `RCS`/`RCP`。错误码保留手册四类再映射到 address/permission/protocol，`23/24/26`
> 明确不可重试。

> **Host Link**（编解码 + 主站 + 内置从站 + `uic hostlinkread` + `examples/hostlink.json`）：
> 只做 **FINS 帧**（头码 `FA`），不做 C 模式，不做跨网长格式，也不自动重试。它的价值在于
> 把「FINS 的语义」与「串口信封」分开：内存区、字/位寻址、读写语义、数值字节序与 FINS/TCP
> 逐字节相同，所以命令语义抽进 `driver/finscore` 与 `sim/finsmem` 共用，同一份点表换个
> `protocol`（`fins` ↔ `hostlink`）就能跑；`codec/hostlink` 只负责「FINS 帧 ↔ ASCII 信封」。
> 信封本身有六件必须按字节记的事：等待时间只有**一位**十六进制（0..F，单位 10ms）；应答在
> `FA` 后**多一格结束码、少一格等待时间**（收发是两条独立布局，按请求布局解应答会从第三格
> 起全部错位）；FCS 从 `@` 起异或到正文末、不含 `*` 与 CR（少算 `@` 时本地回环永远通过、
> 真机必挂）；正文是「一字节两字符」的十六进制，整帧纯可打印 ASCII；单元号是两位**十进制**
> （00..31，写成十六进制会让 31 号站变 `1F`）；直连 ICF 是 `0x00`（照抄 FINS/TCP 的 `0x80`
> 会被当跨网帧、找不到路由）。**单次上限读 269 字 / 538 位、写 267 字 / 534 位**，不是
> FINS/TCP 的 999——命令不能在信封上分段，上限由整帧字符预算反推（读看应答能带多少数据、
> 写看命令能塞多少正文，读写差两个字是结构性的），照抄 999 会稳定收到结束码 `0x18`。
> **串口出厂参数是 9600-7-E-2**，与 Mewtocol 的 9600-8-O-1 相反；「FINS 必须 8 位数据位」是
> 错的，套用 8/N/1 的症状是「发得出去、收不到东西」且不报错。错误分两层：信封层结束码
> （`0x13` FCS 错 / `0x14` 格式错 / `0x18` 帧长错，属于配置或组帧问题，修一次永久消失）与
> FINS 层结束码（与 FINS/TCP 同一张表）。两条刻意边界：**不做 C 模式**（`RR`/`RD`/`WD` 是
> 另一套命令集与 BCD 寻址，混进来每个字段都要先判断「现在走哪套」）；**不自动重试**（没有
> 可靠事务号，重发一次写可能把同一个字写两遍，对「加计数」点位是真实数据错误），重连交给
> 调度器。内置从站在单元号不匹配时**完全沉默**（真 PLC 只回应点名到自己的帧），FCS 错回
> `0x13`、格式错回 `0x14`、认不出的头码回 `0x16`。

> **BACnet MS/TP**（编解码 + 主站 + 内置从站 + `uic mstpread` + `examples/bacnet-mstp.json`）：
> 与 BACnet/IP 共用 `codec/bacnet`（`BuildNPDU`/`ParseNPDU` 抽成公共层）与对象属性寻址，
> 只换承载：NPDU 外再套一层 MS/TP 帧，头尾两条 CRC。最值得单独记录的是**双 CRC 的形态**
> ——头 CRC 用标准给出的特殊移位展开（不是常见的 CRC-8/0x8C 反射式），校验有效帧（含 CRC
> 字节）时残差必须是 `0x55`；数据 CRC 是 CRC-16/X-25（反射多项式 0x8408、初值 0xFFFF、
> 结果取反），残差必须是 `0xF0B8`。同一帧里**长度字段大端、数据 CRC 小端**，是标准原文如此，
> 也是二手资料最容易抄错的地方。头 CRC 还有一个只在单字节向量上暴露的陷阱：所有移位项必须
> 由「异或数据后的原始值」一次算出，写成 `c ^= c<<1; c ^= c<<2` 会得到另一条 CRC，但整体
> 残差有时仍碰巧「不对但不报错」——测试因此直接对拍 `crcHeaderByte(0,1)=0xFE`。
>
> **定位是单主站轮询从站**：本机占主站段 0..127（默认 0），被采集设备是 MAC 128..254 的从站
> （`labels.address`，回退 `unitId`）；主站用 DataExpectingReply 点名问、从站回
> DataNotExpectingReply，令牌不发生转移——从站不持有令牌，这正是单主站能成立的原因。驱动
> **刻意不做**多主站令牌环的建立与维护：Tslot 抢占、NextStation 探活、Tno_token/Tusage_timeout
> 这些毫秒级定时器要求常驻状态机，而现场常见的「串口服务器把 RS-485 透传到以太网」会被
> TCP 往返与缓冲抖动破坏时序，一个只在请求时才醒来的节点伪装成令牌环成员只会把别人的环拖垮。
> 同理不做 Who-Is 发现、COBS 扩展帧、波特率自适应、ReplyPostponed 后续上送（直接映射为协议
> 错误，让上层重试），也不轮询主站设备；**空闲时不监听总线**是 sole-master 拓扑的明确前提，
> 不是遗漏。
>
> 在等待从站应答的窗口内会**被动配合**令牌环：收到发给本机的 Token 就记住、事务结束后交还
> （优先 `labels.nextStation`，否则按 PollForMaster 从本机地址之后现场探测下一站），收到
> PollForMaster/TestRequest 立即应答。发送前留 `labels.presilence`（默认 5ms）线路静默，给
> RS-485 收发器方向切换与 `Tturnaround` 留时间；过短会在长线上表现为「随机首字节 0x55 丢失
> → 整帧被当噪声 → 随机超时」。分帧用**滚动缓冲逐字节重扫**：坏头只丢 1 字节而不是丢整段
> 候选头，否则紧跟假 preamble 后的真帧会被一起吞掉，症状是随机丢一帧。半双工纪律里还有一条
> 与其它串口协议相同的硬性顺序：**先 `Drain` 再 `SetDeadline` 再发送**——`link.tcpLink.Drain`
> 会把 deadline 临时压到 `now+1ms` 且不恢复，反序会让每次写都立刻超时。串口按物理路径共享、
> 事务由总线锁串行，`concurrency` 必须为 1。点表层 `PolicyFor("bacnet","bacnet-mstp")` 共用
> `WidthProtocol + AllowObject`，对象地址允许带连字符与纯数字的对象类型。

> **KNXnet/IP**（编解码 + 隧道主站 + 内置网关 + `uic knxread` + `examples/knx.json`）：
> 只做 **TUNNELING（UDP 单播隧道）+ 组地址读写**（`GroupValueRead` /
> `GroupValueResponse` / `GroupValueWrite`）；不做 ROUTING 组播、不做设备管理连接
> （属性/内存下载）、不做 KNX Secure、不做 raw/busmon。它最容易被「聪明地做错」的
> 地方是**类型**：组地址在总线上不携带类型，同一条写报文只说明「把这几个字节写进
> 这个地址」，字节怎么解释完全由工程的组地址表决定。由 `dataType` 反推得不到答案
> ——`float32` 既可能是 9.xxx（2 字节半精度）也可能是 14.xxx（4 字节单精度），编码
> 方式完全不同；而猜错的代价不是报错，是**得到一个合法的错值**（2 字节半精度按
> 4 字节单精度解，21.5 变成 `3.7e-41`，质量还是 good）。因此本仓库把 DPT 前移成
> **地址的一部分**（`1/2/3@9.001`）：`PolicyFor("knx")` 用 `WidthNone + AllowSymbol +
> AllowDPT` 强制要求，缺了在 `uic import` 阶段就拒；`Address.Canonical()` 把
> `@DPT` 拼回去（否则 `1/2/3` 与 `1/2/3@9.001` 会被当成两条地址、重复地址检查
> 漏判，而「改了 DPT」也不会被视为冲突）。DPT 表用**切片而非 map**：`9.001` 与
> `9.1` 是同一类型，字符串键要先补零才能命中，而「补零」要在解析/规范化/错误提示
> 三处各写一遍，迟早漏一处。第二处真正的坑是 **1 位 DPT 的值在 APCI 字节的 bit0、
> 不在数据域**——解析时不把这一位摘掉，一个「开」的 `GroupValueWrite` 会解析成
> `0x0081` 而不是 `0x0080`，调用方按服务码 switch 落空、报文被**静默丢弃**，现场
> 症状是「写返回成功、设备没动、日志里什么都没有」（本仓库实现时真踩到了，已用
> 回归测试钉死）；编码侧的镜像细节是 **TPDU 长度字段不含 TPCI 字节、也不含 APCI
> 高 2 位**，当成「整个 APDU 的字节数」会让网关把最后一个数据字节当成下一条报文
> 的开头。第三处是**隧道生命周期**：序号 8 位、**收到 ACK 之后才加一**，超时重传
> 必须用**同一个序号**（换号会被当新帧、同一次写执行两遍），序号错乱时唯一可靠的
> 复位是**重建隧道**（通道号与序号是一体的，单独「调序号」在真网关上没有对应服务；
> 任何「+1 试试」都在猜，猜错的代价是脏写或漏写）；因此整条会话用一把锁串行化
> ——一条隧道只有一个通道号 + 一个 8 位序号，总线 9600 波特，并发没有收益只有乱序
> 风险。第四处是**写成功的语义**：`L_Data.con` 的 error 位表示**总线级**故障（总线忙、
> 冲突、链路发送失败），**不是**「这个组地址上有没有设备在听」——组地址是广播语义，
> 写一个没人订阅的地址在链路层是**成功**的。把两者混为一谈会让「写了但没生效」与
> 「网络断了」变成同一个错误，而它们的处理动作完全不同；驱动的做法是在 300ms 短
> 窗口内等 con，**收不到按成功**（部分网关不给隧道客户端回 con，硬等会把一半的写判
> 成失败），收到且 error 位置位才判 `protocol`。另外两点工程取舍：`Open` **只 dial
> 不建隧道**（CONNECT 延后到首次 `Probe`/读写，否则「网关隧道槽位满」这个几分钟后
> 会自己恢复的状态会表现成驱动加载失败），`Probe` 定义为「建隧道 + CONNECTIONSTATE
> 往返、**不读任何组地址**」（排障时经常要把「网关连得上吗」与「工程组地址配得对吗」
> 拆开看）。内置网关刻意复现四件事：序号严格校验（宽松一点，驱动里的重传路径永远
> 测不到）、8 位回绕后「新帧 vs 重传」的边界、槽位满回明确状态码而不是静默丢弃、
> **只更新已有的组地址**（给未知地址凭空造对象，会让「点表地址写错」这个最常见的
> 故障从测试里消失），读未知地址时只回 ACK 与 con、不回 `GroupValueResponse`，让
> 客户端正常超时——那个超时正是它该报告给运维的事实。

> **IEC 61850（MMS）**（编解码 + 主站 + 内置 IED + `uic iec61850read` + `examples/iec61850.json`）：
> 只做 **ACSE + MMS 初始化 + 读/写变量 + getNameList 模型浏览**；不做 GOOSE/SV（二层/
> 三层组播，独立生命周期与采样率）、报告控制块（服务端主动推，与调度式采集是两种语义）、
> 文件传输、定值组、数据集读写、TLS。它是全仓库封套最长的一条链路：TPKT → COTP → 会话层
> → 表示层 → ACSE → MMS，五段各有自己的长度与编号。两处必须分开处理，否则**短帧全过、
> 长帧错位**：其一，**会话层 LI 与 BER 长度是两套编码**——`0x00..0xFE` 是单字节长度，
> `0xFF` 后跟**恰好两字节**大端长度，而 BER 长形式「后面跟几个字节」由低 7 位决定；
> 拿通用 BER 解析器读 LI，短帧能过、长帧从错误的偏移继续，症状是「小响应正常、一读大
> 结构就断链」。其二，**封套归属不对称**——COTP 的 CR/CC 自带 TPKT、可以直接发；会话的
> CN/AC/DT/FIN 与所有 MMS 请求必须先套「会话 DT + 表示层」，再由 COTP 补 TPKT 与 COTP
> 头。少套一层对端只会断链，没有任何更具体的提示，所以「谁的帧带谁的壳」必须用单测钉死。
> 地址模型是对象引用 `LD/LN.FC.DO[.DA]`，**FC 是名字的一段而不是元数据**：
> `GGIO1$Ind1$stVal` 与 `GGIO1$ST$Ind1$stVal` 是两个对象，只有一个存在；点表要么写全
> FC，要么由 `labels.defaultFC` 补，**绝不从数据属性名反推**（反推需要完整 SCL 模型，
> 而驱动只有一份点表），FC 白名单严格限定 ST/MX/CO/SP/CF/DC/SG/SE（`MOD` 不是标准 FC）。
> 与 KNX 正好相反，**类型在装置侧**：一个对象是布尔、整型还是浮点由 IED 的 MMS 模型
> 决定，读回来才知道，因此 `PolicyFor("iec61850")` 是 `WidthNone + AllowSymbol`、点表
> 不写 length，`dataType` 只决定平台侧怎么存——把浮点标成 `int32` 不会变成「读四个字节
> 的整数」，只会把浮点按整数入账；`uic iec61850read -raw` 打印的是装置回的类型而不是
> `-type`。第三处坑在报文结构：**读写请求体里 `listOfVariable` 与 `listOfData` 都编码成
> `[0]`（同为 `0xA0`）**，没有任何标签可区分，只能按出现顺序解析（第一个是变量名列表、
> 第二个是数据列表）；把「按标签找」的习惯带进来会静默拿到错位的值。事务层：一条关联上
> 可以有多个在途请求，靠 **invokeID** 分回对应关系，驱动严格配对、迟到响应按 invokeID
> 丢弃——不校验就会在「A 超时、B 复用同一条链路」时把 A 的值写给 B；整条关联仍用一把
> 锁串行化（请求/应答协议，并发只有乱序风险）。错误必须分开：单项数据访问错误不是网络
> 错误，`object-non-existent`/`object-undefined`/`invalid-address`/`type-unsupported` →
> `address`（改点表，不计入熔断）、`access-denied` → `permission`、
> `temporarily-unavailable`/`hardware-fault` → `protocol` 且可重试；混成一类会让运维在
> 「点位配错」与「装置重启」之间两边都查。浏览（`getNameList`）协议支持，但 `Browse`
> 能力位诚实声明为 `unsupported`——整棵模型枚举是一次性运维动作，混进 `Read` 只会让采集
> 多一条难以解释的慢路径；自检命令走包级 `Browse` 按页收齐（continueAfter 用上一页最后
> 一项做游标，256 页上限防「永远说还有、游标却不前进」的畸形对端）。内置 IED 刻意复现
> 四件事：**getNameList 只回项名**（剥掉域前缀——域由 objectScope 单独携带，整键回出去
> 会让客户端拼成 `LD/LD.…`，本仓库实现时真踩到并用 `-browse` 输出钉死）、未知对象回
> `object-non-existent` 而不是默认值、关联可被拒（验证「关联被拒」与「读超时」是两类
> 事故）、读超时注入后连接仍可用。
>
> **MTConnect**（编解码 + 主站 + 内置 Agent + `uic mtconnectread` + `examples/mtconnect.json`）：
> 只做 **HTTP + XML 只读**，三个端点 `/probe`（设备模型与数据项清单）、`/current`（整台设备
> 当前快照）、`/sample`（按序号翻历史窗口）；不做资产/事件完整模型、不校验 MTConnect
> 版本、不做 `/asset`、`/streams`。它的形态与前面所有协议都不同：没有事务、没有请求-应答
> 的配对方程式，一条 GET 就覆盖全设备，所以 `MultiRead` 声明 `supported`、点位数不影响
> 请求数——**「多一个点」与「多一百个点」成本相同**，这在驱动里是独一份。寻址用
> `kind=symbol`，`path` 是 Agent 的 `dataItemId`（如 `Xabs`）；值有多宽由数据项文本与点表
> `dataType` 共同决定，因此点表用 `WidthNone`（与 IEC 61850 同类、`dataItemId` 里的点号是
> Agent 命名习惯而不是下标，selector/index/length 在导入期就拒绝）。四个真正会踩的坑：
> **① 单点问题不升级为链路错误**——`/current` 一条请求覆盖全设备，若把「某个点 `UNAVAILABLE`
> 」「ID 不存在」当 `Read` 错误返回，上层会按错误分类丢掉整条连接，一个本来不可用的点
> 会让整台设备每周期重连；因此 `Read` 只在「文档拿不到 / 解析不了 / 设备选不出来」时返
> 错，`UNAVAILABLE`→`bad`、ID 不存在或类型解析失败→`address_error`，一律只写进该点。
> **② 条件是两层结构**——外层元素是条件类型（`System`），内层 `Normal/Warning/Fault/
> Unavailable` 是级别；同时兼容「元素名即级别、`type` 属性是条件类型」的平铺写法，两种
> 写法归一到同一个级别。条件点的**值就是级别，级别即质量**：`FAULT`→`bad`、
> `WARNING`→`uncertain`、`NORMAL`→`good`，同一 ID 多条条件按 `FAULT > WARNING >
> UNAVAILABLE > NORMAL` 合并（不是「后者覆盖」）。**③ 多设备 Agent 必须显式选设备**——
> `labels.deviceUuid` 优先、其次 `deviceName`；多台且未选就报地址错误并列出可选设备，
> 否则「A 机床的 `Xabs` 覆盖 B 机床的 `Xabs`」不会报错，只会让两台坐标互相串。**④ 地址
> 规范化与探测顺序**——接受 `host:port`/`http://`/`https://`、省略端口一律补 5000、支持
> 反向代理基址子路径、拒绝 URL 内凭据/query/fragment；`Probe` 先 GET `/probe`、遇 404/405
> 退回 `/current`（裁剪版 Agent 可能只实现后者）；`net/http` 自动解 gzip 且按魔数兜底；
> XML 按**本地名**匹配（带 `mt:` 前缀照样解析）、兼容 ISO-8859-1/latin-1/windows-1252 与
> UTF-8 BOM；文档上限 32 MiB，`/sample` 的 `count` 上限 10000。只读是协议边界不是取舍：
> `Write` 声明 `unsupported` 且逐项返回 `ErrUnsupported`（标准没有写数据项的服务），
> `Subscribe`/`Browse`/`Discovery` 都标 `unsupported`——能解析 `/sample` 不等于能订阅，
> `/probe` 是一次性诊断而不是调度式浏览。内置 Agent 复现三件事：**`toolOffset` 初始
> UNAVAILABLE**（数据项存在但此刻无值——真机最常见的常态，用来验证显示为坏质量而不是 0）、
> 条件用规范两层写法渲染、`/sample` 按环形缓冲序号窗口返回（旧观测被顶掉）。

> **M-Bus**（EN 13757-2/3；编解码 + 主站 + 内置表计 + `uic mbusread` + `examples/mbus.json`）：
> 只做**主地址寻址**（0..250）的单一主站轮询，读方向走 `SND_NKE` + `REQ_UD2` 拿整表；
> 不做次级地址（需要先 `SND_UD(CI=52h)` 选中、地址域变 8 字节、校验范围随之变化，混合
> 实现比不支持更难排查，因此编解码层**显式拒绝** `FDh`）、不做 `SND_UD` 写入（CI=`51h`
> 发数据 / `5Eh` 改地址 / `50h` 校时，写什么完全由表厂剖面决定，写错会改变计费参数，
> 改地址/速率还会让表从当前站号「消失」）、不做 2 类数据（ACD）与多主站仲裁。它是全仓库
> 唯一**服务端决定数据布局**的协议：报文的记录顺序、宽度、量纲全由表自己决定，没有「第 n
> 个寄存器」——偏移取决于前一条记录的长度，换一块表就会错位。这是点表模型必须长出**符号
> 寻址**的真实原因，而不是设计偏好。
>
> 四处线格式陷阱：**① 校验和是 `C+A+CI+DATA` 的模 256 和、不覆盖 L 与起止符**——按整帧
> 算会在每个长帧上固定差 3，是所有二手资料里最常见的一处；**② 长帧有两个相等的 L**，
> 必须都校验，整帧长恒为 `L+6`，只信第一个会在半双工丢字节时把半帧当整帧；**③ 四种帧
> （`E5` 单字符 / `10 C A CS 16` 短帧 / `68 L L 68 ...` 长帧 / `L=3` 控制帧）共用两个起始
> 符**，`0x68` 既是长帧头也是控制帧头，而 `E5` 只有 1 字节——当转换器把 ACK 与紧随的应答
> 粘在一次 read 里返回时，扫描器必须能先把 `E5` 单独切出来，否则「链路正常」会被判成
> 「帧结构错」；**④ 可变结构的 12 字节固定头**（表号 BCD 4 + 厂商 2 + 版本 + 介质 + 访问号
> + 状态 + 签名 2）之后才是记录流，少读一个字节会让全部 VIF 错位，读出来的值都是合法数字
> 但量纲全错。记录自描述用 DIF(+DIFE 链) 表达长度/功能位（瞬时/最大/最小/故障）/存储号/
> 费率/子单元，用 VIF(+VIFE 链) 表达物理量与 10 的幂；VIF 表按区间 + 幂次生成而不是手抄
> 256 行，这既省代码也避免「抄漏一行」这类无法测出的错。数据域按 DIF 解：整数 1/2/3/4/6/8
> 字节、BCD 2/4/6/8/12 位（最高半字节 `Fh` 是负号）、REAL 4 字节 IEEE754、变长（`DIF=0Dh`）
> 带 LVAR；Type G 日期 2 字节、Type F/I 日期时间 4/6 字节按位域解，**时间无效位置位时报
> 文本 `(时间无效)`**，而不是把 `0xFF` 解成 2159 年。
>
> 两个语义上的核心取舍：**其一，一条 `REQ_UD2` 拿整表**，点位多少都只发一次请求
> （`MultiRead` 声明 `supported`），同一条报文里的点位天然一致（同一次快照）——这是它与
> 「每点一次读」的驱动在语义上的关键差别。**其二，FCB/FCV 是重传语义的核心**：同一轮重试
> **保持 FCB 不变、跨轮才翻转**，从站据此回放上一次应答（访问号不重复累加、存储值不被重读）；
> 写错的表现是「偶尔读到上一次的值」，极难发现，因此测试直接锁住「同 FCB 重放的访问号不变」。
> 读取失败后驱动补发一次 `SND_NKE` 复位从站的 FCB 状态再重试——长期运行的电池表忘记 FCB 是
> 现场最常见的「隔几轮才读通一次」。`Probe` 用 `SND_NKE` 的**单字节应答**，它不依赖任何数据
> 结构，因此能把「完全没字节回来」（物理层/波特率/站号错）与「有字节但解析不了」（参数错）
> 分开。反过来，若驱动发现「收到字节流但一帧都没成」，会报**协议错误**并提示查波特率/校验位
> （标准 2400 8E1）与终端电阻，而不是笼统报超时——`Reader` 因此多了一个 `BadFrames()` 计数，
> 只有「确实像帧但内容不对」才计入，单纯重同步（起始符之前的噪声）不算，否则总线上电瞬态
> 会让驱动误报线路质量差。
>
> 点表 `path` 是归一化物理量名：`q:energy`（第 1 条 energy 记录）、`q:volume@1`（存储号 1
> 的历史值）、`q:power-max`（功能位=1 的最大值，`-min`/`-error` 同理）、`q:energy/1`（同量名
> 第 2 次出现，多费率表常见）、`r:0`（报文第 0 条记录，厂商自定义 VIF 不认识时的逃生口）。
> 单位与倍率由 VIF 表统一换算到工程值（`energy` 恒为 Wh、`volume` 恒为 m³），点表不需要知道
> 这块表用了 0.001 Wh 还是 10000 Wh 的刻度。固定数据结构（CI=`73h`，16 字节两个计数器）能解
> 但不推荐使用，它是老式紧凑表的形态。内置从站复现五件事：**同 FCB 重放不改访问号**（否则
> 上面那条最重要的语义永远测不到）、访问号逐次自增、地址不符**完全沉默**（替别人的地址应答会
> 让主站张冠李戴）、坏校验只改校验和（验证主站真的靠校验和发现问题而不是靠结构）、`DIF=1Fh`
> 后续报文标志（验证驱动的 follow 上限）。

> **DLMS/COSEM**（IEC 62056-46/-53/-62；编解码 + 主站 + 内置电表 + `uic dlmsread` +
> `examples/dlms.json`）：只做 **LN 逻辑名引用 + 无安全（Lowest Level Security）+ HDLC 三层
> 承载**。这是 DLMS 能做到「离线写出点表」的唯一一条路径：LN 的地址是 6 字节 OBIS 码，含义
> 由标准与 companion specification 固定（`1.0.1.8.0.255` 永远是正向有功电能），点表因此可
> 以离线书写、跨表复用。**SN（short name）引用不做**——short name 是厂商在 `object_list`
> 里分配的，同一个 OBIS 在不同表上 short name 不同，要用它必须先读 `object_list` 建立映射，
> 属于另一套「先发现再寻址」的模型，与「点表直接写地址」的采集方式不兼容。**HLS/GMAC 不做**
> ——需要密钥协商、帧计数器、AES-GCM，且密钥分发方式各厂商完全不同，做了也只能覆盖一部分
> 现场，却会把「密码错」与「地址错」混成同一类超时。**TCP/UDP 的 COSEM wrapper 不做**（另一
> 套 version + wrapper 头封装）。**Set/Action/EventNotification 不做**——写方向要处理
> selective access 与分块写，方法调用要处理参数与返回，服务端主动上报是无编号帧，它们不是
> 「GET 换个方向」，半成品比不做更难排查，`Write` 诚实声明 `unsupported`。
>
> 四处 HDLC 线格式陷阱：**① 长度字段是两标志之间的全部字节数**（含 2 字节格式字段与末尾
> FCS，不含标志），整帧 = `len(body)+2`，11 位跨两字节且 bit11 是分段位——少算 2 字节会让
> 接收方永远等不到结束标志，症状是「第一帧之后就超时」；**② HCS 覆盖 `format+dest+src+ctl`**，
> 因此必须**先算长度再算 HCS**，先占位后回填会让头校验与格式字段不一致，接收方判定「头校验
> 失败」并丢弃整帧；**③ 类型 3 帧不做透明转义**，`0x7E` 可以合法出现在 info 与 FCS 里，分帧
> 必须按长度字段定界而不是「扫下一个标志」——按标志扫会在某些应答上把一帧切成两半，而且只有
> 特定数值才触发（本仓库用 `1.0.13.7.0.255` 的 FCS `7E 64` 做回归）；**④ 地址域是 7 位/字节
> + 扩展位**（bit0=1 表示结束），1/2/4 字节，客户端恒 1 字节，4 字节按「高 7 位组 + 低 7 位
> 组」各左移一位。CRC 是 CRC-16/X-25（初值 `0xFFFF`、反射多项式 `0x8408`、结果取反、小端），
> 好帧残余是 `0xF0B8`——这个固定余数性质是分帧的基础，随手改一个比特就必须失效。
>
> 应用层是 A-XDR（IEC 61334-6）编码的 APDU。建链 `SNRM → UA`、`AARQ → AARE`，读
> `Get-Request-Normal → Get-Response-Normal`，断链 `DISC → UA`；`SNRM` 的金帧是
> `7E A0 07 03 21 93 0F 01 7E`。两处容易写反：**U 帧控制域是固定常量、不携带可变的 P/F 位**
> （UA=0x63 的 bit4 为 0），要求往返保持 P/F 会让建链永远等不到应答；**LLC 头 `E6 E6 00`
> （请求）/ `E6 E7 00`（应答）里的 `E7` 是「这一帧是应答」的唯一信号**，缺了它说明收到的是
> 服务端主动上报。三个真实 bug 是在自检/测试里被挖出来的：`ParseRaw` 最初按 `0x7E` 扫帧尾
> （改成按长度字段定界 + 结束标志校验，失步时前移 1 字节）；`date_time` 解码整体错位一位（日
> 当成了月、星期当成了时——布局是 `年(2) 月 日 星期 时 分 秒 百分秒(2) 偏差(2) 状态`，**星期
> 在日月之后、时分之前**，时区偏差是带符号分钟、`0x8000` 表示未指定）；`data-access-result`
> 编成了 `01 01 xx`（标准是 `[1] IMPLICIT ENUMERATED`，定长 8 位无长度前缀，线上只有
> `01 <值>` 两字节——「兼容两种形态」会让结果码为 `hardware-fault(1)` 的应答被读成「数据不
> 完整」，于是所有硬件故障都报成超时）。
>
> **scaler 是 DLMS 最容易写错的一处**：Register 类（3/4/5）的 attribute 2 是原始整数，
> attribute 3 是 `structure {integer scaler, enum unit}`，工程值 = 原始值 × 10^scaler，
> **scaler 为负是除**（写反会差 10000 倍，而读数「看起来是个数」不会报错）。驱动读完
> attribute 2 再读一次 attribute 3 并应用，带进程内缓存——scaler 是对象的静态配置参数，不会
> 随测量值变化，而每轮每点都多读一次会让往返数翻倍。`ApplyScaler` 必须**一次**乘除
> `10^|scaler|`：逐次除 10 会累积舍入误差，`5001 / 10 / 10` 得到 `50.010000000000005`，屏幕上
> 就是一串尾数且会污染聚合值。单位枚举同样只认标准表：**Wh = 29、VAh = 30、varh = 31**——
> 写错不会报错，只会把电量标成「视在电能」，数值一切正常，最难发现。
>
> 点表 `path` 是 `<OBIS>[:<class>[:<attribute>]]`。只写 OBIS 时类号与属性号从内置表推导，
> **查不到就报 `ErrAddress` 而不是猜**——猜错的类号会让表回 `object-class-inconsistent(9)`，
> 而「猜了一个看起来能读的类」会读到另一个对象的合法数字。`SplitRef` 是**唯一**的地址切分点
> （驱动与自检命令都必须走它，否则两边对同一字符串的解析会分叉，而「自检通过、采集失败」正
> 是最难查的一类问题）：标准正文写法 `1-0:1-8-0-255` 自带冒号，靠「前缀必须能解析成 6 段
> OBIS」确定切点。`data-access-result` 全部归 `ErrAddress`（object-undefined 与
> object-class-inconsistent 都指向点表写错，重试无用）。分块读报 `ErrUnsupported` 并提示调大
> `max-pdu`——表在应答超过 max-PDU 时**必然**走数据块，直接报「不支持」只会让现场看到超时，
> 正确做法是解出块号并明确报告。`MultiRead` 声明 `unsupported`：一条 Get 只读一个属性，批量
> 的 `get-request-with-list` 要求服务端声明 `multiple-references`（现场极少支持），把
> 「N 个点 = N 次往返」暴露给配置的人比假装合并更负责任。`Probe` 打印**协商后**的
> conformance 而非本端请求值——标准允许服务端砍掉一半能力，按请求值判断会得出错误结论。
> 物理层固定 **8N1**：配成 8E1 会收到全错位的字节，驱动的 `BadFrames` 计数会把它归成
> `ErrProtocol` 并提示查波特率/校验位与终端电阻，而不是笼统报超时。内置从站复现五件事：
> 三相表 40+ 项带 scaler_unit 的对象表、未建关联就读回 `read-write-denied`（而不是 DM，让自检
> 拿到明确原因）、对象未定义与类号不一致两种结果码、坏校验只改 FCS 前一字节（验证主站真的靠
> 校验序列发现问题而不是靠内容）、地址不符完全沉默（总线串扰时替别人应答会让主站张冠李戴）。

**明确不做**：PROFINET IO、PROFIBUS、CANopen、CC-Link、FOCAS、DALI、LonWorks、DDS、EtherCAT、HART、GB/T 28181、Euromap、Matter、LoRaWAN、OCPP、Redfish。

不做这些的理由不是「难」，而是**它们需要专用硬件、厂商授权或非工业场景**，投入产出比不成立。若客户有需求，通过「进程外驱动 SDK」由合作方实现。

## 7. 协议知识库的最小字段集

从 PA-30（C++ FINS）与 PA-15（Java S7）的经验看，**协议语义知识比代码更值钱**。目标产品应为每个协议维护一份结构化知识条目：

| 字段 | 内容 | 示例 |
|---|---|---|
| `protocolId` | 唯一标识 | `modbus-tcp` |
| `role` | 支持的角色 | `master`, `slave` |
| `transports` | 传输方式 | `tcp` |
| `addressing` | 寻址类型 | `register` |
| `frame` | 帧结构说明（字段/长度/字节序） | MBAP 7 字节 + PDU |
| `commands` | 命令/功能码表 | 0x01/0x02/0x03/0x04/0x05/0x06/0x0F/0x10 |
| `errors` | 异常码与含义 | 01 非法功能、02 非法地址、03 非法数据值、04 从站故障 |
| `limits` | 单次请求上限 | 125 寄存器 / 2000 线圈 / 260 字节 ADU |
| `timing` | 超时与间隔 | 读超时 3s；RTU 帧间 3.5 字符 |
| `deviceVariants` | 型号差异 | S7-1200 需 PUT/GET；S7-1500 优化块 |
| `quirks` | 已知怪癖 | 某些从站不支持 0x17 读写复合 |
| `testVectors` | 金报文 | 请求 hex / 期望响应 hex |
| `references` | 规范来源（不复制正文） | 标准号、章节 |

这份知识库的用途：

1. 生成配置表单（字段 + 校验 + 提示）；
2. 生成文档（错误码表、限制说明）；
3. 生成测试向量；
4. 培训新驱动作者；
5. 出问题时快速定位是「协议理解错」还是「实现错」。

## 8. 规范获取与法律边界

| 类别 | 例子 | 获取方式 | 法律注意 |
|---|---|---|---|
| 公开标准 | Modbus、BACnet、DNP3 | 官方渠道（部分文本需付费获取） | 标准文本有版权，**不可复制到代码注释或文档** |
| 事实标准 | S7comm、MC、FINS、Host Link | 逆向/社区文档/厂商手册 | 无官方公开规范；实现本身通常不侵权，但**不可复制他人代码** |
| 厂商 SDK | FOCAS、部分机器人协议 | 需签 NDA | 分发受限于 SDK 条款 |
| 开放规范 | OPC UA（公开）、MQTT、Sparkplug | 官网 | 注意各规范的专利声明 |
| 国标/行标 | DL/T 645、CJ/T 188、GB/T 28181 | 标准出版社 | 标准文本有版权 |

**三条纪律**：

1. **只实现语义，不复制文本**：帧结构可以用自己的话描述，不抄标准原文；
2. **不复制他人代码**：包括「改写变量名」的伪原创——本卷 38 份文档的写作方式就是这条纪律的实践；
3. **依赖白名单**：只允许 MIT/Apache-2.0/BSD/ISC；GPL/AGPL 一律阻断。

## 9. 结论

1. **45 个协议在传输层只有 5 种、封装层约 15 种、应用层约 30 种。** 复用点在低层，工作量在高层的语义与批量优化。因此「支持 N 个协议」的正确度量不是 N，而是「共享了多少传输与封装代码」。

2. **P0 的六个协议（Modbus TCP/RTU、S7、OPC UA、MQTT、REST）约需 74 人日，其中 26 人日（35%）花在虚拟设备与金报文上。** 这 35% 正是 38 个方案普遍缺失的部分，也是「可测试」支点的成本来源。

3. **协议路线必须与场景绑定，而不是与「协议知名度」绑定。** Wave 2 的 11 个协议对应四类场景（汽车/3C/水务/楼宇），而不是「把常见协议补齐」。同理，明确不做的 14 个协议不是能力不足，而是「需要专用硬件或厂商授权」的理性放弃。
