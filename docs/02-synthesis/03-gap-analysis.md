# 总分析三｜差距分析：38 个方案共同留下的十二个缺口

> **文档性质**：横切分析（缺口与机会视角）
> **输入**：`01-capability-matrix.md`（能力覆盖）、`02-architecture-patterns.md`（架构纪律）
> **输出**：目标产品的差异化支点清单与风险清单
> **脱敏**：仅用 PA 编号与技术画像

---

## 1. 分析方法

缺口不是「某个方案没做的事」，而是**38 个方案作为一个整体、长期都没能解决的事**。判定标准有三条，缺一不可：

| 判据 | 说明 |
|---|---|
| **普遍性** | 至少 30 个方案存在，或至少 3 个「最优秀的方案」都没做到 |
| **后果严重** | 会在真实交付中造成停工、返工、事故或验收失败 |
| **非人力问题** | 不是「多写点代码就行」，而是需要架构层面的预留 |

按这三条筛下来，共 12 个缺口。下面每个缺口给出：现象 → 证据 → 根因 → 后果 → 目标产品的回答 → 验收标准。

## 2. 十二个缺口

### G1 治理型能力：可运维性均值 2.3，是全卷最低维度

**现象**：38 个方案里，能同时提供「结构化日志 + 指标 + 分级健康检查 + 运行态区分」的只有 4 个（PA-06、PA-08、PA-09、PA-34）。其余 34 个的运维手段是「看日志文件 + 重启」。

**证据**：

| 能力 | 覆盖方案数 | 完整实现数 |
|---|---|---|
| 结构化日志 | 33（提及） | 约 8 |
| 指标 | 32（提及） | 约 5 |
| 分级健康检查 | 19（提及） | 约 6 |
| 运行态 ≠ 配置态 | 少数 | 1（PA-06） |
| 慢设备识别 | 少数 | 2（PA-06、PA-34） |
| 链路追踪 | 1 | 1（PA-34） |

**根因**：运维面不产生「功能」，只产生「可诊断性」。在项目制交付里，验收标准是「能读到数」，不是「能定位到为什么读不到」。于是运维面永远是最后一项，也永远是第一个被砍的。

**后果**：现场故障的平均定位时间从分钟级升到天级。一个「某台设备偶尔超时」的问题，在没有指标的情况下只能靠抓包，而抓包需要停机。

**目标产品的回答**：

| 能力 | 设计 |
|---|---|
| 指标 | 每个设备/通道/协议/北向端点都有计数器与直方图，命名 `uic_<subsystem>_<name>`，Prometheus 文本格式暴露 |
| 运行态 | 设备状态机显式区分 `configured / connecting / collecting / degraded / disabled / faulted`，`accepted ≠ 采集中` |
| 慢设备 | 单次采集耗时 P95 超阈值即标记，并在 API 中返回 |
| 健康 | `/healthz`（进程）、`/readyz`（依赖就绪）、`/api/v1/health`（业务聚合，含每设备状态） |
| 诊断 | `/api/v1/diagnostics/bundle` 生成脱敏诊断包（配置 + 日志尾部 + 指标快照 + 版本信息） |

**验收标准**：给定一台「偶发超时」的设备，运维人员能在 5 分钟内通过 API 判断是网络、协议、还是设备侧问题，无需抓包。

### G2 边缘自治三件套：没有任何一个方案三件套齐全

**现象**：Outbox 持久补发、配置版本化回滚、远程运维命令——这三项共同回答「设备在客户现场、人不在」的命题。

**证据**：

| 能力 | 完整实现 | 部分/提及 |
|---|---|---|
| Outbox 持久补发 | **PA-35（唯一）** | PA-06/08/10 提及 |
| 配置版本 + 备份 + 回滚 | PA-06、PA-34、PA-35 | PA-21/31/37 |
| 远程运维命令（白名单） | **PA-35（唯一）** | — |
| 看门狗 | **PA-34（唯一）** | — |

**根因**：这三项都只在「设备已经部署到客户现场、开发人员不在场」之后才体现价值。而绝大多数方案的生命周期终止于「演示通过」，从未经历「部署 200 台、运行 2 年」。

**后果**（真实场景推演）：

1. 客户现场断网 6 小时，恢复后 6 小时数据全丢 → 生产报表出现空洞 → 客户要求赔偿；
2. 远程改了一个点位地址写错了，导致整台设备采不到 → ��能派人到现场 → 差旅成本 > 软件成本；
3. 程序在凌晨 3 点因句柄泄漏假死，直到早班发现 → 8 小时数据缺失。

**目标产品的回答**：

| 组件 | 设计要点 |
|---|---|
| Outbox | SQLite WAL；按目标端点分区；三重上限（条数/字节/TTL）；投递确认后删除；启动重放未确认；恢复时限速 |
| 配置版本 | 内容哈希作为版本号；`desired/current/status/backup/rollbackCount` 状态文件；应用前备份；失败自动回滚；保留 N 份 |
| 远程命令 | 白名单动作（`apply` / `upsert-device` / `replace-points` / `set-log-level` / `restart-driver` / `selftest` / `rollback` …），每个动作有 schema 与权限要求；未知动作拒绝 |
| 看门狗 | 进程内心跳 + 采集循环推进检测 + 资源水位降级；进程外由 systemd/Windows 服务负责重启 |

**验收���准**：拔掉网线 24 小时，恢复后北向数据无空洞（允许降采样）；远程下发一个错误配置，30 秒内自动回滚且设备继续采集。

### G3 测试能力：只有 2 个方案具备「无真机验收驱动」的能力

**现象**：协议驱动的质量验证依赖真实设备。38 个方案中，具备系统化虚拟设备 + 故障注入 + 金报文的只有 PA-09（最全）、PA-06（金报文 + Fake 服务器）；PA-01/02/34 有仿真但非测试用途。

**证据**：

| 能力 | 覆盖方案数 | 代表 |
|---|---|---|
| 虚拟设备/仿真驱动 | 4 | PA-01、PA-02、PA-09、PA-34 |
| 故障注入（丢包/延迟/错帧） | 3（提及） | PA-09（唯一系统化） |
| 金报文测试 | 2 | PA-06、PA-09 |
| 负载/浸泡测试 | 2 | PA-06、PA-34 |
| 基准测试 | 2（提及） | — |

**根因**：写虚拟设备的工作量与写真实驱动相当，但「不产生功能」。同时，虚拟设备需要**协议知识**（正确的帧、正确的错误码、正确的边界行为），而多数团队只有「能连上真机」的知识。

**后果**：

1. 驱动的异常路径（超时、错帧、异常码、部分响应）从未被测试，上线后以「偶发」形式暴露；
2. 无法做 CI——CI 环境没有 PLC；
3. 第三方驱动作者无法自测，生态起不来；
4. 重构协议层时没有回归保险，只能「改完祈祷」。

**目标产品的回答**：

```
drivertest（独立 Go module）
  ├─ 虚拟设备：按协议实现从站，支持内存模型 + 脚本化响应
  ├─ 故障注入：丢包 / 延迟 / 半包 / 错 CRC / 异常码 / 连接重置
  ├─ 金报文：每协议一组「请求字节 ↔ 期望响应字节」的固定用例
  ├─ 一致性套件：所有驱动必须通过的统一测试（连接/超时/重连/并发/取消）
  └─ 基准：每驱动的单次读耗时、批量读吞吐
```

**验收标准**：新增一个驱动，在没有任何真实设备的情况下，能在 30 分钟内跑通一致性套件并得到「可发布」结论。

### G4 统一数据模型：四类寻址从未被同一套模型容纳

**现象**：38 个方案的地址模型分两类——「寄存器型」（绝大多数）与「寄存器 + 符号型」（PA-06、PA-08、PA-15、PA-24）。对象型寻址（BACnet/IEC 61850）只在 PA-06、PA-27 出现，且都是协议私有实现，未上升到平台模型。

**证据**：

| 寻址形态 | 有平台级模型的方案 | 说明 |
|---|---|---|
| 寄存器（区+偏移） | 几乎全部 | — |
| 符号（DB 符号/CIP 标签） | PA-06、PA-08、PA-15、PA-24 | 多为协议私有 |
| 对象（类型+实例+属性） | PA-06、PA-27 | 协议私有，未平台化 |
| 文件/记录 | 未见 | — |

**根因**：产品从 Modbus 起家，地址模型就是 `(area, offset, length, type)`。当需要接 BACnet 时，只能加一个 `bacnetAddress string` 字段，让驱动自己解析——这等于放弃了统一模型。

**后果**：批量读规划、点位校验、北向映射、模板化全部退化为「按协议特判」。PA-06 的 `addressingMode`（NUMERIC / SYMBOLIC / MIXED）是对这个问题的部分回答，但它只解决了「排序与比较」，没有解决「统一表达」。

**目标产品的回答**：

```
Address（接口/联合类型）
  ├─ RegisterAddress { Area, Offset, Length, BitOffset? }
  ├─ SymbolAddress   { Path, Index? }
  ├─ ObjectAddress   { ObjectType, Instance, Property, Index? }
  └─ FileAddress     { FileID, RecordID, Offset, Length }
```

配套要求：

1. 驱动声明自己接受的地址类型（`acceptedAddressKinds`）；
2. 地址的**规范化字符串**（用于唯一性、日志、北向节点名）由平台统一生成，不由驱动各自实现；
3. 批量规划器按地址类型分派：寄存器型合并连续区间，符号型按前缀分组，对象型按实例分组；
4. 模板化时地址可参数化（`40001 + n`、`DB{n}.DBW0`）。

**验收标准**：同一个「设备模板」机制可以同时生成 Modbus 设备、S7 设备与 BACnet 设备，且北向节点命名规则一致。

### G5 配置生命周期：只有 3 个方案能回答「改错了怎么办」

**现象**：配置版本化在 5 个方案中出现，但具备「备份 + 自动回滚 + 差异对比」完整语义的只有 3 个（PA-06、PA-34、PA-35）。

**证据**：

| 能力 | 方案数 | 代表 |
|---|---|---|
| 配置版本 | 5 | PA-06、PA-21、PA-31、PA-35、PA-37 |
| 一键回滚 | 3 | PA-06、PA-34、PA-35 |
| 配置差异对比 | 1 | PA-06 |
| 灰度/分批下发 | 0 | — |
| 配置原子写 | 少数 | PA-06、PA-13、PA-35 |

**根因**：配置在多数方案里被当作「输入参数」，而不是「需要版本管理的制品」。这与软件工程里「代码要进 Git」的共识形成鲜明对比——**工业配置至今没有 Git**。

**后���**：现场改配置靠「先备份一份文件」，改错了靠记忆恢复；多人协作时互相覆盖；无法回答「上周三那台设备为什么采不到」。

**目标产品的回答**：

| 能力 | 设计 |
|---|---|
| 配置即制品 | 配置有版本号（内容哈希）、作者、时间、来源、变更摘要 |
| 差异对比 | 提供结构化 diff（设备级 / 点位级 / 字段级） |
| 回滚 | 一键回滚到任意历史版本；回滚本身也产生新版本（不破坏历史） |
| 原子写 | 临时文件 + fsync + rename；启动校验失败进入安全模式 |
| 远程下发 | 白名单动作 + 版本单调性检查 + 应用前备份 + 失败自动回滚 |
| 灰度（P2） | 按设备分组分批下发，每组观察窗口后可暂停 |

**验收标准**：任意一次配置变更都能在 30 秒内回滚，且回滚过程不影响其他设备的采集。

### G6 默认安全基线：弱口令与明文凭据是普遍现象

**现象**：至少 5 个方案的仓库中直接包含默认弱口令或明文凭据（PA-21、PA-26、PA-31、PA-37、PA-38 有实证），其中 1 个在 README 中明示「请勿用于生产」。

**证据**：

| 问题 | 出现方案 |
|---|---|
| 默认弱口令 / 明文口令入仓 | PA-21、PA-26、PA-31、PA-37、PA-38 |
| HTTP 无鉴权 | PA-10、PA-35、PA-36（部分） |
| 无 TLS | PA-10、PA-35、PA-37 |
| 无 LICENSE / 许可不明 | PA-07、PA-20、PA-21、PA-22、PA-26、PA-27、PA-28、PA-30、PA-31、PA-33 |
| 传染性许可（GPL/AGPL） | PA-11、PA-14、PA-16、PA-25、PA-29 |

**根因**：工业软件长期运行在「物理隔离的内网」假设下。但现实是：OT 网络正在与 IT 网络打通，且等保 2.0 与关基保护条例已把工控系统纳入强制范围。

**后果**：投标时因「无审计、无 RBAC、默认口令」被否决；上线后被安全扫描发现高危项，整改周期以月计。

**目标产品的回答**（全部为不可配置的底线）：

1. 首次启动生成随机管理员口令并打印到日志/控制台，强制首次登录修改；
2. 凭据（MQTT 口令、数据库口令、证书私钥）加密���储，密钥来自环境变量或系统密钥环；
3. 默认启用认证；关闭认证必须显式配置且日志告警；
4. 所有远程接口默认要求 TLS（自签证书自动生成）；
5. 依赖许可清单（SBOM）随发布物提供，CI 中禁止引入 AGPL/GPL 依赖；
6. 审计日志覆盖认证、授权失败、配置变更、写操作。

**验收标准**：安全扫描（含默认口令、明文凭据、未授权接口）零高危。

### G7 扩展契约：语义化版本与能力声明几乎空白

**现象**：插件机制在 20 个方案中出现，但具备「契约版本 + 能力声明 + 隔离 + 签名」完整链条的只有 1 个（PA-34 的插件清单）。

**证据**：

| 能力 | 方案数 |
|---|---|
| 插件/驱动注册表 | 20（提及） |
| 独立加载隔离 | 1（PA-13） |
| 契约版本区间（min/max gateway version） | 1（PA-34） |
| 插件签名/哈希校验 | 1（PA-34） |
| 插件能力声明 | 少数（PA-06 的四态最接近） |

**根因**：插件生态的前提是「有足够多的插件作者」。在只有官方驱动的阶段，契约版本化看起来是纯粹的负担。

**后果**：一旦第三方驱动出现，任何核心接口变更都会造成「插件全挂」；而如果为了兼容而不改接口，核心就无法演进。这是典型的**技术债复利**。

**目标产品的回答**：

1. 驱动契约以独立 Go module 发布（`uic-driver-sdk`），有独立的版本号与兼容性承诺；
2. 驱动声明 `sdkVersion`、`protocolId`、`capabilities`（四态）、`acceptedAddressKinds`、`configSchema`；
3. 核心加载时校验版本区间，不匹配则拒��加载并给出明确原因；
4. 第一版静态注册（编译进主程序），第二版进程外 gRPC（隔离 + 异构）；
5. 提供 `drivertest` 夹具，第三方可在无真机环境下自测。

**验收标准**：核心升级一个小版本后，所有符合契约的驱动无需重新编译即可继续工作（静态注册场景下为「无需修改代码」）。

### G8 跨平台与交付：Windows 绑定仍是主流，单二进制是少数派

**现象**：跨平台能力 1 分的方案有 11 个；能提供单二进制交付的只有 4 个（PA-16/17/20/27，且都是 Go）。

**证据**：

| 交付形态 | 方案数 | 语言分布 |
|---|---|---|
| Windows 桌面/服务绑定 | 约 20 | C# / C++ |
| JVM fat jar | 4 | Java |
| 单二进制 | 4 | Go |
| 容器镜像 | 3 | .NET / Python |

**根因**：工业上位机生态由 Windows 主导（厂商 SDK、OPC DA、ActiveX、串口驱动），且现场工程师习惯桌面程序。

**后果**：

1. 边缘盒子（ARM Linux）无法��署；
2. 无法容器化，云边协同困难；
3. 升级需要人工到现场或远程桌面；
4. 信创/国产化环境无法满足。

**目标产品的回答**：见 `02-architecture-patterns.md` §9 的部署矩阵。核心约束是**运行时零 CGO 依赖**（串口通过纯 Go 实现或独立辅助进程），从而支持 `GOOS/GOARCH` 全矩阵交叉编译。

**验收标准**：`make release` 一条命令产出 linux/amd64、linux/arm64、windows/amd64、darwin/arm64 四个单文件产物，且任一产物在目标平台��动后 10 秒内通过 `/readyz`。

### G9 语义与集成：数据契约没有版本，Topic/Schema 靠约定

**现象**：38 个方案中，北向数据格式（JSON 字段名、Topic 结构、单位）几乎全部是「代码里写死的字符串」。没有一个方案提供数据契约（Schema）的版本化与演进机制。

**证据**：

| 能力 | 方案数 |
|---|---|
| 北向 JSON 上报 | 27（提及） |
| Sparkplug B（自带契约） | 3（提及） |
| 数据契约版本化 | 0 |
| 单位/量程语义 | 少数（PA-06、PA-14） |

**根因**：北向消费者（MES/云平台）通常在项目里一次性对接，之后很少变更。契约演进的需求被「反正就这一家客户」掩盖了。

**后果**：产品化后，第 10 个客户想要不同的字段名/单位/Topic 结构，只能靠「加配置项」逐个打补丁，最终形成一套无法维护的模板引擎。

**目标产品的回答**：

1. 北向数据有明确的 Schema（点位值对象：`id / value / quality / ts / unit / meta`）；
2. Topic/节点名生成规则可配置且**有默认值**（默认规则稳定，不随版本变化）；
3. 提供 `schemaVersion` 字段，新增字段向后兼容，破坏性变更升主版本并提供双发过渡期；
4. 提供「映射配置」把内部点位 ID 映射到客户期望的外部 ID，而不是改��码。

**验收标准**：同一份采集数据可以同时以两种 Topic 结构输出（旧契约 + 新契约），且切换不需要重启采集。

### G10 时钟与时间语义：无人系统化处理

**现象**：38 个方案中，没有任何一个系统化处理「设备时间与网关时间不一致」「时区」「时间跳变」的问题。

**证据**：全卷检索「时钟同步」「时区」「NTP」相关实现——除个别方案在配置里有一个时区选项外，无系统化设计。

**根因**：单机、单站点、单时区的场景下，这个问题不存在。但一旦涉及多站点、跨时区、或设备侧带时标（IEC 104 的 CP56Time2a、DNP3 的时标、DL/T 645 的时标），问题立刻出现。

**后果**：

1. 设备上报的带时标数据与网关时间戳混用，历史曲线出现「时间倒流」；
2. 跨时区站点的数据在中心侧无法对齐；
3. 系统时间被 NTP 校正后，定时器与历史写入出现空洞或重复。

**目标产品的回答**：

1. 点位值区分三个时间：**设备时间**（协议携带，可空）、**采集时间**（��关单调时钟）、**写入时间**（持久化）；
2. 单调时钟用于调度与超时（不受系统时间跳变影响）；
3. 时区在配置中显式声明，历史存储统一 UTC，展示层转换；
4. 检测到系统时间跳变时记录事件并重置调度基准。

**验收标准**：在采集过程中把系统时间向前/向���调整 1 小时，采集不中断、历史无重复无空洞（时间戳按单调时钟推进）。

### G11 大规模交付工程化：模板化与批量实例化是稀缺能力

**现象**：具备「设备模板 + 批量实例化 + 命名规范」完整能力的只有 PA-14（最完整）与 PA-06（部分）。

**证据**：

| 能力 | 方案数 |
|---|---|
| 模板 | 14（提及） |
| 克隆/批量实例化 | 2 |
| 命名规范约束 | 2 |
| 配置导入导出 | 少��� |

**根因**：模板化的价值只在「500 点以上、10 台以上设备」的项目里体现。而多数方案的验证场景是「1 台 PLC、20 个点」。

**后果**：一个 1000 点、50 台设备的项目，配置工作量为 1000 × 5 分钟 = 83 小时，且极易出错。这是**交付成本的主要构成**，也是竞标时最容易被忽视的成本项。

**目标产品的回答**：

1. **设备模板**：参数化（IP、站号、起始地址偏移、实例号），一���定义、多次实例化；
2. **点位模板**：按「点表 CSV/Excel」批量导入，支持地址表达式（`40001 + n*2`）与命名规则（`{device}.{group}.{name}`）；
3. **命名规范**：唯一性校验、非法字符拒绝、保留字保护；
4. **配置生成**：CLI 子命令 `uic config gen --template t.yaml --vars v.csv` 批量产出；
5. **差异预览**：导入前显示��将新增 N 个、修改 M 个、删除 K 个」。

**验收标准**：1000 点 / 50 台设备的工程，从 CSV 点表到可运行配置，人工操作时间 ≤ 30 分钟。

### G12 许可与供应链：直接复用代码的法律风险高于技术风险

**现象**：10 个方案无 LICENSE 文件（默认保留所有权利，不可复用）；5 个方案为 GPL/AGPL（传染性）；1 个方案存在「根许可与内嵌代码许可冲突」（PA-27：根 MIT + 内嵌 GPLv2+）。

**证据**：

| 许可状态 | 方案数 | 风险 |
|---|---|---|
| 无 LICENSE | 10 | 不可直接复用任何代码 |
| GPL / AGPL | 5 | 闭源分发即违约 |
| 许可冲突（内嵌不同许可代码） | 1 | 无法合规锁定 |
| 宽松（MIT/Apache/BSD） | 约 15 | 可用，但需保留声明 |
| 商业授权 | 约 5 | 需付费，且条款限制部署 |

**根因**：工业协议实现大量来自「厂商 SDK 改写」「开源项目二次开发」「同事离职留下的代码」，许可链条天然混乱。

**后果**：产品化时无法提供 SBOM；政企招标要求「无 GPL 依赖」时无法证明；被上游主张权利时无法追溯。

**目标产品的回答**：

1. **只借鉴协议语义知识（帧结构、错误码、地址规则），不复制代码**——本卷 38 份分析文档的存在本身就是这条纪律的产物；
2. 依赖白名单：只允许 MIT / Apache-2.0 / BSD / ISC；CI 中自动扫描并阻断；
3. 生成 SBOM（CycloneDX）随发布物提供；
4. 自有代码使用宽松许可（建议 Apache-2.0，含专利授权条款）。

**验收标准**：`make sbom` 产出完整依赖清单，CI 中存在 GPL/AGPL 依赖时构建失败。

## 3. 缺口优先级矩阵

横轴为「实现成本」，纵轴为「现场影响」。

```
影响高 ┤  G2 边缘三件套        G1 治理能力
       │  G3 测试能力          G4 统一模型
       │  G6 安全基线
       │  G5 配置生命周期
       ├────────────────────────────────────
       │  G11 模板化   G8 跨平台交付
       │  G12 许可     G9 数据契约
影响低 ┤  G10 时钟     G7 扩展契约
       └────────────────────────────────────
         成本低                    成本高
```

| 优先级 | 缺口 | 理由 |
|---|---|---|
| **第一批（P0）** | G1、G2、G3、G4、G6、G5 | 影响高、成本中低；且都是「架构预留」而非「功能堆叠」 |
| **第二��（P1）** | G8、G11、G12、G9 | 影响中高、成本中；交付与合规必需 |
| **第三批（P2）** | G7、G10 | 影响中、成本中；生态化与多站点阶段才需要 |

**关键判断**：P0 的六个缺口有一个共同特征——**它们都是「底座」而不是「功能」**。这意味着它们必须在第一版就做对，否则后续补做需要重构。这正是「慢工出细活」的投入方向。

## 4. 为什么这些缺口长期存在

理解原因，才能判断「我们做这些是否真的能形成壁垒」。

| 结构性原因 | 表现 | 是否可被我们的做法改变 |
|---|---|---|
| **验收标准偏功能** | 甲方验收「能读到数」，不验收「能定位故障」 | 可改变：把可诊断性做成演示环节的亮点 |
| **项目制交付** | 每个项目重做一遍配置，没有产品化沉淀 | 可改变：模板化 + 配置即制品 |
| **人力结构** | 协议开发与运维开发是两拨人，后者缺席 | 可改变：同一套代码里预留运维面 |
| **存量生态锁定** | 现场已有 Windows 上位机，替换成本高 | 部分可改变：提供并存方案（网关旁挂） |
| **语言生态** | C# 生态协议最全，但服务化/跨平台弱；Go 生态跨平台强，但协议少 | 可改变：Go 里自建协议库（本项目的核心投入） |
| **单人项目占比高** | 38 个方案中约 20 个为单人/小团队作品 | 不可改变（这是市场结构） |
| **没有测试设备** | 虚拟设备开发成本高、无直接收益 | 可改变：把它当作 SDK 的一部分交付 |

**结论**：前五条都可以通过「架构与产品选择」改变，第六条是市场结构（意味着竞品也多为小团队），第七条是我们主动投入的差异化。

## 5. 目标产品的差异化定位

### 5.1 一句话定位

> **一个可治理、可测试、可回滚的跨平台工业连接底座：单二进制部署，协议驱动可��拔，从第一天起就带虚拟设备与配置版本。**

### 5.2 五个支点（每个都对应一个缺口）

| 支点 | 对应缺口 | 一句话价值 | 竞品为什么难跟 |
|---|---|---|---|
| **可治理** | G1 | 每台设备、每个通道、每个点位的健康与性能都可查 | 需要从调度器到北向全链路埋点，后期补做要重构 |
| **可测试** | G3 | 没有 PLC 也能开发、验收、回归驱动 | 需要协议知识 + 工作量，且不产生「功能」 |
| **可回滚** | G2、G5 | 远程改配置，改错了 30 秒退回去 | 需要配置即制品的设计，事后加会破坏所有写入路径 |
| **可移植** | G8 | 一个文件跑在 ARM 盒子上，也能跑在容器里 | 需要零 CGO 与无头架构，桌面方案改不动 |
| **可扩展** | G4、G7 | 四类寻址统一，驱动契约版本化 | 需要第一版就把地址模型设计对 |

### 5.3 明确不做的事（避免定位漂移）

| 不做 | 原因 |
|---|---|
| 组态画面 / HMI 绘图 | PA-04/33 证明这是独立产品，且与「无头底座」定位冲突 |
| 自研时序数据库 | 用 SQLite/现成引擎，专注采集与治理 |
| 云端 SaaS 平台 | 前期只做边缘软件 + 可选中心聚合 |
| 全协议一次性覆盖 | 广度靠时间，第一版只做 12 个协议但做到可测试 |
| 闭源许可 | 与「可扩展、可测试」的生态策略冲突 |

## 7. 结论

1. **38 个方案共同留下的最大缺口不是「协议不够多」，而是「不可诊断、不可回滚、不可测试」。** 这三件事在功能清单上都不占位置，却决定了产品能不能从「演示」走到「部署 200 台、运行 2 年」。

2. **十二个缺口里，有六个必须在第一版解决，且都必须在架构层面预留。** 它们是：治理能力（G1）、边缘三件套（G2）、测试能力（G3）、统一数据模型（G4）、配置生命周期（G5）、安全基线（G6）。这六项构成了「慢工出细活」的具体含义——不是把功能做多，而是把底座做对。

3. **差异化不在「做什么」，而在「顺序」。** 所有竞品最终都会做指标、做插件、做 OPC UA；区��在于我们**先做底座再做协议**，因此当协议数量追平时，底座优势会形成复利；而先做协议的方案，追平底座需要重构。
