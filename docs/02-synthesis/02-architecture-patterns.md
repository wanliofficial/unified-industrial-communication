# 总分析二｜架构模式归纳：38 个方案的七种原型与十二条纪律

> **文档性质**：横切分析（架构视角）
> **分析对象**：PA-01 … PA-38
> **方法**：先按「进程形态 + 扩展方式」把方案归为七种原型，再逐个解剖关键抽象、并发模型、故障恢复与配置生命周期
> **用途**：为目标产品的总体架构（`docs/03-product/02-architecture.md`）提供取舍依据
> **脱敏**：仅用 PA 编号与技术画像

---

## 1. 为什么先分类，再比较

38 个方案如果逐对比较，会得出大量互相矛盾的结论：有的说「插件化是唯一出路」，有的说「插件化是过度设计」；有的说「每设备一线程简单可靠」，有的说「必须全异步」。

矛盾来自**把不同原型的方案放在同一把尺子上**。一个 200 行的编解码库和一个 11 万行的网关，本来就不该用同一套架构标准。

因此本文先分原型，再在每个原型内部找「该原型下的最优解」，最后回答一个问题：**目标产品应该选哪个原型，以及在该原型下必须遵守哪些纪律。**

### 1.1 七种原型

| 原型 | 定义 | 代表 | 规模区间 | 生命周期特征 |
|---|---|---|---|---|
| **A 协议内核库** | 无进程形态，只提供协议客户端/服务端 API | PA-01、PA-18、PA-24、PA-32、PA-15、PA-22、PA-27、PA-28 | 1k–63k 行 | 被引用；无配置、无调度 |
| **B 单体桌面运行时** | UI 与采集同进程，配置即工程文件 | PA-10、PA-12、PA-14、PA-33、PA-35、PA-36 | 19k–192k 行 | 开机自启 + 托盘 |
| **C 服务化网关** | 无头服务 + Web 控制台 + 插件 | PA-06、PA-08、PA-13、PA-34、PA-29 | 51k–192k 行 | 常驻服务 + 容器 |
| **D 轻量脚本单体** | 单进程 + 内置 HTTP + 配置库 | PA-07、PA-20、PA-21、PA-37、PA-38 | 1.8k–8.3k 行 | 手工启动 / 进程守护 |
| **E 仿真与测试平台** | 以「扮演设备」为主业 | PA-09、PA-11、PA-26、PA-02 | 1.6k–205k 行 | 按需启动 |
| **F 组态/HMI 框架** | 以画面与变量绑定为核心 | PA-04、PA-33 | 150 类型–192k 行 | 单机交付 |
| **G 生成器** | 用模板产出另一个程序 | PA-19 | 4.7k 行 | 构建期工具 |

**注意**：PA-33 同时属于 B 与 F，PA-02 同时属于 A（配套）与 E。分类的目的是识别**主导约束**，不是贴标签。

### 1.2 原型决定的三件事

| 原型 | 谁负责「重连」 | 谁负责「配置」 | 扩展的物理边界 |
|---|---|---|---|
| A | 调用方 | 调用方 | 编译期（加包/加文件） |
| B | 运行时自己 | 工程文件 | 编译期（枚举 + switch） |
| C | 运行时自己 | 数据库/配置文件 + Web | 插件目录（运行期） |
| D | 运行时自己（常常没做） | 数据库/JSON | 改代码 |
| E | 不需要（它是被动方） | 场景文件 | 编译期 |
| F | 运行时自己 | 画面文件 | 编译期 |
| G | 生成物自己（通常没做） | 生成器 UI | 模板文件 |

**这张表解释了大量「缺失能力」**：A 类不做重连不是疏忽，是定位；D 类不做重连则是能力不足。评价时必须区分。

## 2. 原型 A：协议内核库

### 2.1 共同骨架

所有 A 类方案都收敛到三层，只是命名不同：

```
┌─────────────────────────────────────────────┐
│  L3 语义层：设备/标签/地址解析/批量规划        │  ← 多数方案缺失
├─────────────────────────────────────────────┤
│  L2 协议层：帧编解码 + 事务（事务号/序列）      │  ← 全部具备
├─────────────────────────────────────────────┤
│  L1 传输层：TCP / UDP / 串口 / TLS            │  ← 全部具备
└─────────────────────────────────────────────┘
```

| 方案 | L1 抽象 | L2 组织 | L3 语义 | 关键差异 |
|---|---|---|---|---|
| PA-01 | 自研 Socket/Serial 基类 | 每协议一个大类 | 有设备类与地址模型 | 广度最大，单类最重（千行级） |
| PA-24 | `SocketBase` / `SerialPortBase` | 每协议一文件（777–1777 行） | 有独立地址模型（S7/FINS/MC） | 传输基类最干净 |
| PA-32 | 统一 TCP/UDP/MQTT/串口/USB/BLE | 客户端基类 + 子类 | `ByteData` 字节视图 | **数据视图抽象最好** |
| PA-15 | 自研网络工具 | 每协议一包 | 有类型化地址 | 批量算法最好 |
| PA-22 | 每包自带连接 | 每协议一包 | 无 | 广度换深度 |
| PA-27 | 依赖第三方传输 | 每协议一包 | 无 | BACnet 深度最好 |
| PA-28 | 自研 | 单文件 | 无 | 最小可读实现 |
| PA-18 | 厂商原生库封装 | 每厂商一包 | 有标签模型 | 工程规范最好 |

### 2.2 L1 传输层的五个必备细节

从 PA-24/PA-32/PA-01 的实现中可以提炼出一份「传输层检查单」。任何驱动缺一项，都会在现场以「偶发超时」的形式暴露：

| 细节 | 正确做法 | 反例 |
|---|---|---|
| 读满 N 字节 | `io.ReadFull` 语义；循环读到期望长度或超时 | 单次 `Read` 就当作完整帧（PA-28 的隐患） |
| 超时分层 | 连接超时 / 读超时 / 单事务总超时，三者独立 | 只有一个 `SetDeadline` |
| 半包与粘包 | 按协议长度字段切分，保留残余缓冲 | 假定「一次读=一帧」 |
| 重连时机 | 在「发送前」检测而非「读失败后」 | 先写后死，写操作永久失败 |
| 连接态机 | `Disconnected → Connecting → Connected → Degraded → Closed` | 布尔 `isConnected` |

**PA-24 的 `SocketBase` 只有 195 行，却把前四项做全了**，这是它可以被 6 个协议复用而不出乱子的原因。反过来，PA-28 的 1,374 行里连 TCP ADU 都没有，说明它的抽象起点错了——先写帧、后写连接。

### 2.3 L3 语义层：A 类方案的分水岭

40+ 个协议里，真正需要「语义层」的只有四类寻址：

| 寻址形态 | 协议 | 语义层要做什么 | 只做 L2 的后果 |
|---|---|---|---|
| 寄存器 | Modbus、DL/T 645 | 区/偏移/长度 → 请求；字序/字节序转换 | 每个调用方自己拼 |
| 符号 | S7 DB 符号、CIP 标签 | 符号解析、类型长度、数组下标 | 符号拼错只能等运行时 |
| 对象 | BACnet、IEC 61850 | 对象类型/实例/属性/索引 | 无法表达「读 present-value」 |
| 文件/记录 | IEC 61850、部分表计 | 文件 ID/记录 ID/偏移 | 只能读固定块 |

PA-27 的 BACnet 实现是唯一在 Go 里做到 L3 对象寻址的样本，但它的 L3 只到「发现设备」，没有到「按点位读」。这恰好说明：**L3 是最难的一层，也是最有价值的一层。**

### 2.4 原型 A 的失败模式

| 失败模式 | 表现 | 案例 |
|---|---|---|
| 巨型类 | 一个协议文件 1,500+ 行，改一处要读全篇 | PA-01、PA-24 |
| 复制粘贴 | Modbus 四个变体各自实现一遍 | PA-24（1557 / 1266 / 1080 / 211 行高度重复） |
| 同步阻塞 | 无 `context`/`CancellationToken`，无法取消 | PA-01、PA-10、PA-32 |
| 无并发保护 | 共享连接被多 goroutine/线程同时写 | PA-28 |
| 依赖倒挂 | 核心库引用 UI 类型 | PA-01（WinForms 用于日志窗） |

### 2.5 对目标产品的取舍

**采纳**：三层分离、传输检查单、地址模型独立于协议实现。
**不采纳**：把 L3 塞进协议包（应独立为 `model` + `planner`）。
**关键改进**：L2 的输入输出必须是**纯字节 + 结构化错误**，不允许直接操作设备对象——这样同一份编解码可以在主站、从站、仿真器、测试用例四处复用（PA-24 的「客户端与模拟器同源」正是这个思路）。

## 3. 原型 B：单体桌面运行时

### 3.1 共同骨架

```
┌───────────────────────────────────────────────┐
│ UI（WinForms/WPF/Avalonia）                    │
├───────────────────────────────────────────────┤
│ 应用服务（项目加载/保存/启动/停止/监视）          │
├───────────────────────────────────────────────┤
│ 运行时（调度器 + 通道 + 快照缓存 + 写入）         │
├───────────────────────────────────────────────┤
│ 协议层（枚举 + 工厂 switch + 每协议一实现）       │
└───────────────────────────────────────────────┘
        配置：单个工程文件（XML/JSON/SQLite）
```

六个方案（PA-10/12/14/33/35/36）的骨架几乎一致，差异只在「运行时是否独立于 UI」：

| 方案 | 运行时能否无头运行 | 配置形态 | 调度模型 | 设备数上限（推断） |
|---|---|---|---|---|
| PA-10 | ✗（入口绑 UI） | 项目文件 | 定时器 + 每设备一线程 | 数十 |
| PA-12 | ✗ | SQLite | 定时器 + 线程池 | 数十 |
| PA-14 | ✗ | SQLite | 同上 | 数十 |
| PA-33 | ✗ | SQLite | 窗体事件驱动 | 十级 |
| PA-35 | ◐（API 可独立，但入口在 UI 工程） | XML + 状态文件 | 定时器 + 线程 | 数十 |
| PA-36 | ◐（Runtime 库可复用，入口仍绑 UI） | XML + JSON | 定时器 + 线程 | 数十 |

**没有一个是真正的 headless。** 这是原型 B 的结构性天花板：所有能力都必须「穿过 UI 工程」才能被调用，导致：

1. 无法容器化（没有 X11/桌面会话）；
2. 无法做 CI 集成测试（启动就要窗口）；
3. 无法被第三方系统嵌入（只能通过它自己的 HTTP API）；
4. 无法多实例（单实例锁与托盘图标）。

### 3.2 两个值得抄的机制

**（1）通道信号量 + 串口全局互斥（PA-10）**

```
设备 → 通道信号量（每通道 N 个并发，默认 4）
     → 串口信号量（全局按端口名，跨通道共享）
     → 执行同步 I/O，单次最多 100ms 后让出
```

这个三层闸门解决了三个真实问题：慢设备拖垮通道、多站点抢同一个 COM 口、单次轮询卡死调度。它比「每设备一线程」高明的地方在于**资源边界显式化**。

**（2）代次隔离（PA-10、PA-06、PA-35 都有）**

每次启动/重连递增 `generation`，异步返回的结果若代次不匹配则丢弃。这解决的是工业现场的高频故障：

> 设备断线 → 重连 → 旧连接的迟到响应到达 → 覆盖新连接的快照 → 界面显示「已连接但数据是 30 秒前的」。

没有代次机制，这个 bug 会以「偶发数据不刷新」的形式存在数年。

### 3.3 原型 B 的失败模式

| 失败模式 | 机制 | 案例 |
|---|---|---|
| UI 线程即调度线程 | 界面卡顿导致采集延迟 | PA-10（部分）、PA-33 |
| 配置即状态 | 改配置必须重启全部设备 | PA-12/14（改一处全重启） |
| 枚举即扩展 | 新增协议改 3 处 switch | PA-10、PA-35 |
| 无头不可用 | 一切能力绑在窗体生命周期 | 全部 6 个 |
| 静默吞异常 | `catch {}` 后继续 | PA-35（多处） |

### 3.4 对目标产品的取舍

**采纳**：通道闸门、串口互斥、代次隔离、配置即工程文件（便于备份/迁移）。
**不采纳**：UI 与运行时同进程。
**关键决策**：**运行时是一个库 + 一个无头二进制；UI 是它的一个客户端。** 这一条把原型 B 的上限（数十设备、单机、不可容器化）直接抬到原型 C 的上限（数百设备、可容器化、可集群部署），且不增加多少代码——PA-36 的 `IPC.Runtime` 分层已经证明可行，只是它的入口没改。

## 4. 原型 C：服务化网关

### 4.1 五种服务化路径

| 方案 | 服务宿主 | 扩展方式 | 配置源 | 无头 | 可容器化 |
|---|---|---|---|---|---|
| PA-06 | Spring Boot fat jar | SPI + 描述符 + Maven 模块 | 数据库 + YAML | ✓ | ✓ |
| PA-08 | ASP.NET Core + DI | 接口 + 程序集扫描 + 签名包 | OPC UA 方法 / TD 文件 | ✓ | ✓ |
| PA-13 | WPF/Blazor 双宿主 | 独立 `AssemblyLoadContext` + NuGet 源 | SQLite | ◐ | ◐ |
| PA-34 | ASP.NET Core + 后台服务 | 插件清单 + 哈希 + 签名 | 数据库 + 包 | ✓ | ✓ |
| PA-29 | OWIN 自宿主 | Manager 流水线 + 接口族 | 配置文件 | ✓ | ◐ |

### 4.2 驱动契约的五种表达

这是全卷最有价值的一组对比。**驱动接口怎么定义，决定了这个产品能长多大。**

**（1）能力位（布尔）**

```
interface Driver { bool CanRead; bool CanWrite; bool CanSubscribe; }
```

问题：「运行时相关」的能力无法表达。某些 PLC 只在特定型号支持订阅，布尔值只能二选一地撒谎。

**（2）能力四态（PA-06）**

```
SUPPORTED / UNSUPPORTED / RUNTIME_DEPENDENT / EXPERIMENTAL
```

这是本卷最精细的设计。它承认了工业协议的现实：**能力是设备型号、固件版本、连接方式的函数**，不是驱动的静态属性。前端据此显示「支持（视型号）」「实验性」徽标，而不是给出错误承诺。

**（3）能力组合接口（PA-06 的另一半）**

```
ProtocolCollector（标记）
  ├─ CollectorLifecycle      init/connect/disconnect/destroy + 统计 + 代次
  ├─ ReadableCollector       单点/多点读
  ├─ WritableCollector       单点/多点写
  ├─ SubscribableCollector   subscribe/unsubscribe
  ├─ ReadPlanCapable         rebuildReadPlans（自建批读计划）
  └─ CommandableCollector    executeCommand(name, map)（弱类型逃生舱）
```

优点：能力即接口，`instanceof` 判断即可，不需要能力位。
缺点：Go 没有 `instanceof`，需要类型断言或能力结构体。

**（4）单一宽接口（PA-10）**

```
IPlcClient { Connect, Disconnect, Read, Write, ProtocolId }
```

5 个成员，23 种数据类型由同一个 `Read` 承载。极简，但：
- 无批量接口 → 批量优化只能在上层做；
- 无取消令牌 → 无法中断；
- 无订阅 → 事件型协议无处安放。

**（5）DI 注册 + 元数据（PA-08）**

```
IProtocolDriver { Discover, BuildTags, Connect, RegisterStructureTypes }
```

驱动的职责被切得更「产品化」：发现设备、生成标签、建立连接、注册结构体类型。其中 `RegisterStructureTypes` 有默认空实现，18 个驱动里只有 1 个覆盖——这说明**「可选能力」用默认实现表达是可行的，但需要文档明确告知「不覆盖会失去什么」**。

### 4.3 驱动契约的评分

| 维度 | 能力位 | 四态 | 组合接口 | 宽接口 | DI+元数据 |
|---|---|---|---|---|---|
| 表达「视情况而定」 | ✗ | ✓ | ◐ | ✗ | ◐ |
| 前后端联动（动态表单） | ✗ | ✓ | ✗ | ✗ | ◐ |
| 实现成本 | 低 | 中 | 中 | 低 | 高 |
| 可测试性 | 低 | 中 | 高 | 中 | 高 |
| 可演进（加能力） | 破坏性 | 兼容 | 兼容 | 破坏性 | 兼容 |

**结论**：目标产品应取「组合接口 + 四态能力声明 + 描述符驱动表单」的并集——接口负责运行期分派，描述符负责配置期渲染，四态负责诚实表达。

### 4.4 并发模型的四种范式

| 范式 | 代表 | 机制 | 设备上限 | 公平性 | 写抢占 | 复杂度 |
|---|---|---|---|---|---|---|
| **每设备一线程** | PA-10、PA-12、PA-35 | `LongRunning` 线程 + 设备锁 | 数十 | 靠排序 | 无 | 低 |
| **时间片推进 + 线程池** | PA-06 | 相位轮单线程 tick + 有界队列 | 数百 | 强（相位） | 中 | 高 |
| **Actor 串行队列** | PA-34 | 每设备一个 actor，`AsyncLocal` 内联 | 数百 | 通道加权 | **强（写优先）** | 中 |
| **全异步无栈** | PA-08 | `async/await` + 有界 Channel | 数百 | 依赖实现 | 中 | 中 |

四种范式的能力差异不在「快慢」，而在**故障隔离粒度**：

- 每设备一线程：一个设备卡死 = 一个线程卡死 = 线程池耗尽（如果共享池）；
- 时间片：一个设备卡死 = 该 tick 延迟 = 所有设备延迟（需要单次执行预算来兜底）；
- Actor：一个设备卡死 = 一个 actor 队列堆积（可观测、可丢弃）；
- 全异步：一个设备卡死 = 一个 Task 挂起（需要超时兜底）。

### 4.5 目标产品的并发模型（决策）

采用 **Actor + 通道加权 + 时间片** 的混合体，理由是它同时解决三个问题：

```
时间片轮（50ms tick）
  └─ 取到期设备（按 nextDue 最小堆）
       └─ 投递到该设备的 actor 队列（容量 1，已有则跳过）
            └─ 通道加权信号量（每通道 maxConcurrent，写优先）
                 └─ 驱动读（context 超时）
                      └─ 结果按代次过滤 → 处理链 → 缓存/Outbox
```

| 机制 | 来源 | 解决 |
|---|---|---|
| 时间片相位轮 | PA-06 | 100 台设备同周期时不错峰 |
| 单设备串行（actor） | PA-34 | 协议层竞态 |
| 通道信号量 | PA-10/PA-34 | 慢设备不拖垮通道 |
| 写优先计数 | PA-34 | 读饿死写 |
| 代次过滤 | PA-06/PA-10 | 旧结果污染新窗口 |
| 单次执行预算 | PA-10 | 单设备卡死拖垮 tick |
| 指数退避 + 抖动 | PA-06 | 重连风暴 |
| 熔断 | PA-34 | 坏设备拖垮全网 |

Go 里这套模型不需要每设备一个 goroutine：actor 队列可以用「每设备一个 `chan struct{}` + 全局 worker pool」实现，1000 台设备的常驻 goroutine 数为 O(worker)。

## 5. 故障恢复：从「重连」到「自愈」

### 5.1 五级恢复能力

| 级别 | 能力 | 实现方案 | 覆盖度 |
|---|---|---|---|
| L1 | 检测到断线并重连 | 几乎所有采集类方案 | 普及 |
| L2 | 指数退避 + 抖动，避免重连风暴 | PA-06、PA-34 | 常见 |
| L3 | 熔断：连续失败后暂停，定期探活 | PA-34（3 次/30s） | 稀缺 |
| L4 | 降级：坏设备不阻塞其他设备与北向 | PA-06、PA-34、PA-10 | 少见 |
| L5 | 自愈：看门狗重启进程/重载配置 | PA-34 | 稀缺（1 个） |
| L6 | 现场可诊断：日志 + 指标 + 诊断包 | 部分 | 稀缺 |

**L5 与 L6 是「无人值守」的真正门槛。** 一个网关在客户机房跑了 8 个月，最可能的故障不是协议解析错，而是：
- 内存缓慢增长 → OOM；
- 某个连接进入半开状态 → 线程/协程泄漏；
- 磁盘写满 → 配置保存失败；
- 系统时间跳变 → 定时器错乱。

这些都不是「重连」能解决的。

### 5.2 看门狗的三层设计（源自 PA-34，需扩展）

| 层 | 监视对象 | 动作 | 判据 |
|---|---|---|---|
| 进程内 | 采集循环心跳 | 记录 + 告警 | 超过 N 个 tick 未推进 |
| 进程内 | 单设备 | 熔断 + 退避 | 连续失败 |
| 进程间 | 主进程存活 | 重启 | 心跳文件超时（外部 supervisor 或 systemd） |
| 系统级 | 磁盘/内存/句柄 | 降级（停历史、删旧 Outbox） | 水位 |

关键设计：**降级必须是「有序丢弃」而不是「崩溃」**。PA-35 的 Outbox 三重上限（条数/字节/时长）与「丢旧保新」策略就是这个思路的正确示范。

### 5.3 断网补发的三种实现

| 实现 | 代表 | 优点 | 缺点 |
|---|---|---|---|
| 内存队列 + 重试 | 多数方案 | 简单 | 进程重启即丢 |
| 嵌入式 KV/自研文件 | PA-35（一消息一文件 + 原子改名） | 无依赖、可审计、易清理 | 小文件多时 inode 压力 |
| 嵌入式数据库（SQLite/BoltDB） | 未见完整实现 | 事务、索引、批量删除 | 写放大、需 WAL 调优 |

**目标产品选择**：SQLite（WAL）作为 Outbox，带「按目标端点分区 + 按时间/条数/字节三重上限 + 投递确认后删除 + 启动时重放未确认」。理由：单文件、可备份、支持按时间范围删除，比一消息一文件更适合 10 万级积压。

**必须明确定义的语义**（多数方案含糊）：

| 语义 | 必须回答 |
|---|---|
| 投递保证 | at-least-once（不承诺 exactly-once） |
| 去重键 | `deviceId + pointId + timestamp + seq` |
| 顺序 | 单设备内有序，跨设备不保证 |
| 过期 | 超过 TTL 直接丢弃并计数（`uic_outbox_dropped_total{reason="ttl"}`） |
| 重放速率 | 限速，避免恢复瞬间打爆 broker |
| 背压 | 队列 > 80% 时降采样（只保留变化点） |

## 6. 配置生命周期：从「文件」到「可回滚的变更」

### 6.1 五种配置形态

| 形态 | 代表 | 可 diff | 可回滚 | 可远程 | 适用规模 |
|---|---|---|---|---|---|
| 硬编码 | PA-30 | ✗ | ✗ | ✗ | 演示 |
| JSON/YAML 文件 | PA-07、PA-16 | ✓ | 手工 | ✗ | 小 |
| 数据库 | PA-06、PA-13、PA-38 | ✓（需工具） | 需实现 | ✓ | 中 |
| 工程文件（XML/JSON）+ 状态文件 | PA-35 | ✓ | ✓ | ✓ | 中 |
| 配置包（含清单/哈希/签名） | PA-34 | ✓ | ✓ | ✓ | 大 |

### 6.2 配置版本化的最小语义（PA-35 的实现值得抄）

```
state.json
  currentVersion   : 当前生效版本
  desiredVersion   : 期望版本
  source           : 下发来源（local / remote / import）
  action           : 本次动作类型
  status           : pending / applied / failed / rolled_back
  backupFile       : 应用前备份路径
  rollbackCount    : 回滚次数
```

规则：

1. `desiredVersion <= currentVersion` → 直接跳过（防重复下发、防回退到旧版本）；
2. 应用前必须备份；
3. 应用失败自动恢复备份并 `rollbackCount++`；
4. 备份按保留数量清理（不能无限增长）；
5. 每个远程动作必须在**白名单**内，未知动作直接拒绝。

PA-35 有约 19 个远程动作（`apply` / `replaceProject` / `upsertDevice` / `replaceTags` / `upsertRule` / `updateMqtt` / `applySettings` …），每个动作有明确输入结构。这比「传一个 JSON 随便改」安全一个数量级。

### 6.3 热更新的三个层次

| 层次 | 能力 | 实现难度 | 现场价值 |
|---|---|---|---|
| L1 重启进程 | 改配置 → 重启 | 低 | 低（断采 10–60s） |
| L2 重启设备 | 只重启受影响设备 | 中 | 中（断采该设备） |
| L3 增量生效 | 加点/改点/删点不中断其他点 | 高 | **高** |

PA-06 的 `ConfigRestartCoordinator` 做到 L2.5：1000ms 防抖 + 差异判断 + 只重启「配置真的变了且期望运行」的设备。这是性价比最高的一档。

**目标产品**：第一版做 L2.5（差异 + 防抖 + 按设备重启），第二版做 L3（点位级增量，需要调度器与快照都支持点位粒度）。

### 6.4 配置的原子性

三条必须遵守的规则（从多个方案的故障中反推）：

1. **写临时文件 + `fsync` + 原子改名**，不允许直接覆盖；
2. **启动时校验 schema，失败则进入「安全模式」而非崩溃**（保留只读 API 与日志）；
3. **配置与运行态分离存储**：配置文件是可评审的输入，运行态（统计、连接状态、质量码）不写回配置文件。

## 7. 数据流与背压

### 7.1 标准数据流（服务化网关）

```
驱动读 → 解码 → 质量码判定 → 缩放/死区 → 点位快照（内存）
                                        ├→ 订阅者推送（SSE/WS）
                                        ├→ 历史写队列（有界）→ SQLite
                                        └→ 上报队列（有界）→ Outbox → MQTT/HTTP
```

### 7.2 三条队列的溢出策略必须分开设计

| 队列 | 溢出策略 | 理由 |
|---|---|---|
| 历史写 | DROP_OLDEST + 计数 | 历史可丢，但要可观测 |
| 上报 Outbox | 落盘 + TTL + 丢旧保新 | 断网期间的连续性优先 |
| 实时推送 | DROP_LATEST（每订阅者独立） | 慢客户端不能拖累采集 |

PA-06 的 `MessageBatchDispatcher` 提供 `BLOCK / DROP_LATEST / DROP_OLDEST` 三选一，是正确做法——**策略可选本身就是可运维性**。

### 7.3 一个常被忽略的问题：写路径与读路径的资源竞争

38 个方案中只有 PA-34 明确实现了「写优先」（`WaitingWrites` 计数）。没有它，现场表现是：

> 操作员点击「启动」按钮，命令排在 200 个读请求后面，3 秒后才生效；操作员以为没点上，又点了一次。

工业控制场景里，**写命令的延迟预算是百毫秒级，读是秒级**。两者必须在调度器里分级，不能共用一个 FIFO。

## 8. 扩展机制：五种物理边界

| 机制 | 代表 | 隔离性 | 热加载 | 依赖冲突 | 适用 |
|---|---|---|---|---|---|
| 编译期 switch | PA-10、PA-35 | 无 | ✗ | 无 | 内置协议 |
| 注册表（进程内） | PA-06、PA-24 | 无 | ✗ | 无 | 官方协议 |
| DI 扫描 + 接口 | PA-08、PA-13 | 无 | ✗ | 有 | 官方 + 半开放 |
| 独立加载上下文 | PA-13（`AssemblyLoadContext`） | 强 | ✓ | 解决 | 第三方插件 |
| 进程外（gRPC/HTTP） | 未见 | 最强 | ✓ | 彻底解决 | 异构/不可信插件 |

### 8.1 插件平台的真实门槛

PA-29 是最惨痛的样本：51k 行、50 个接口、8 个 Manager、651 个测试、双 CI——**零协议驱动**。它把「平台抽象」做到了极致，却在「第一个能用的驱动」之前停下了。

由此得出四条门槛（按重要性排序）：

1. **先有杀手级驱动，再有插件体系。** 没有驱动，插件接口设计得再好也没人实现。
2. **契约必须语义化版本 + 能力声明。** PA-34 的清单字段（`DriverId` / `Version` / `MinGatewayVersion` / `MaxGatewayVersion` / `AssemblySha256` / `Signature`）是可用的最小集。
3. **隔离不是可选项。** 第三方插件带自己的依赖版本，进程内注册表迟早冲突（PA-13 用独立 ALC 解决）。
4. **必须有「插件测试夹具」。** 插件作者需要能在没有真机的情况下验证——这又回到虚拟设备。

### 8.2 目标产品的双模插件

```
进程内：Go 接口（plugin 包或静态注册）
        → 官方驱动、性能敏感、可信代码

进程外：gRPC over UDS/TCP
        → 第三方、异构语言、不可信、需隔离
```

Go 的 `plugin` 包限制多（Linux/macOS、版本必须完全一致），因此**第一版只做静态注册**（编译进主二进制），第二版做进程外 gRPC。这个顺序不能反——静态注册先证明架构，再谈生态。

| # | 纪律 | 违反后果 | 反例 |
|---|---|---|---|

| 2 | 每设备串行，跨设备并行 | 协议竞态、帧错位 | PA-28 |

| 6 | 配置变更必须可回滚 | 远程改错=现场停工 | 除 PA-06/34/35 外 |

| 8 | 质量码必须贯穿全链路 | 坏值进入报表与联锁 | 多数方案 |
| 9 | 驱动接口必须表达「视情况而定」 | 前端承诺了做不到的能力 | 多数方案 |

| 12 | 凭据必须加密且无默认口令 | 合规红线、被扫描即失分 | PA-21/26/31/37/38 |

## 11. 目标产品的架构决策摘要

| 决策 | 选择 | 主要依据 | 备选与否决理由 |
|---|---|---|---|
| 进程形态 | 单二进制无头服务 + Web 控制台 | PA-34/06 的可运维性来自服务化 | 桌面壳（PA-10/35）无法容器化 |
| 并发模型 | 时间片 + 设备 actor + 通道信号量 | 三者分别解决错峰/竞态/隔离 | 每设备一线程在数百设备时崩 |
| 驱动契约 | 组合接口 + 四态能力 + 描述符 | PA-06 的诚实能力模型 | 布尔能力位会撒谎 |
| 数据模型 | 四类寻址统一（寄存器/符号/对象/文件） | PA-27/08 证明单一寻址不够 | 只做寄存器会推倒重来 |
| 队列 | 三条独立有界队列 + 各自溢出策略 | PA-06 的三策略 | 单队列会让慢客户端拖累采集 |
| 持久化 | SQLite（WAL）：配置 / 历史 / Outbox 三库分离 | 单文件、可备份、可删除区间 | 一消息一文件在 10 万级积压时 inode 压力大 |
| 配置 | 文件 + 版本 + 备份 + 回滚 + 白名单动作 | PA-35 的完整语义 | 数据库配置对小现场过重 |
| 扩展 | 第一版静态注册，第二版进程外 gRPC | PA-29 的教训：先有驱动再谈生态 | Go `plugin` 包限制多 |
| 北向 | REST + SSE/WS + MQTT + OPC UA 四通道 | PA-37（易集成）与 PA-08（标准面）互补 | 只做 OPC UA 会挡住 80% 集成方 |
| 测试 | 虚拟设备 + 故障注入 + 金报文三件套 | PA-09 是唯一系统化样本 | 只做单测无法覆盖协议异常路径 |

## 12. 结论

1. **原型选择比框架选择重要。** 原型 B（桌面单体）无论用 WinForms 还是 Avalonia，都长不出健康检查与远程升级；原型 C 无论用 Spring 还是 .NET，都能自然长出这些能力。目标产品必须从原型 C 起步，把 UI 降级为客户端。

2. **并发模型的评价标准不是吞吐，是故障隔离粒度。** 「每设备一线程」在 30 台设备时表现优秀，在 300 台时一个卡死设备就能拖垮全局。时间片 + actor + 通道闸门的组合，本质上是把「一个设备的故障」限制在一个队列里。

3. **架构纪律的 12 条里，有 7 条与「可回滚、可观测、可测试」有关，只有 1 条与性能有关。** 这印证了本卷的总判断：工业连接软件的难点不在「快」，在「出了事能不能查、改错了能不能退、没设备能不能测」。
