# ADR-0002｜历史存储：自建有界采样日志，不引入 SQLite

- **状态**：已决定（Accepted）
- **决策日期**：历史功能落地时
- **决策者**：架构组
- **影响范围**：`internal/history`、`storage.history` 配置、`GET /api/v1/history`、诊断包
- **相关文档**：`docs/03-product/03-domain-model.md` §11、`docs/03-product/05-northbound-api-spec.md` §4.8、`docs/03-product/07-roadmap.md` §4.2

---

## 1. 决策摘要

**历史数据用「按时间切段的 NDJSON 追加日志 + 整段淘汰 + 扫描聚合」实现，不引入 SQLite、不引入任何时序数据库。**

一句话理由：

> 历史的访问模式只有一种——「按 `device + point` 查一段时间」；而本项目的三条硬约束（零第三方依赖、零 CGO、单二进制交叉编译）恰好会被任何嵌入式数据库打破。为一种访问模式引入一个通用查询引擎，是用交付形态换便利。

同时明确：**这不是「永远不用 SQLite」**。当需求越过本文 §6 的边界（多点多列聚合、跨设备 join、压缩率、数十 GB 级数据）时，应当替换实现而不是继续加功能；替换点已经收敛到 5 个方法（§7）。

> **与路线图的偏差**：`07-roadmap.md` 的 Wave 2 最初写的是「SQLite 历史库」。本 ADR 是对那一处表述的正式修订，理由见 §3。

---

## 2. 背景：需求给出的硬约束

| # | 约束 | 来源 | 对存储的含义 |
|---|---|---|---|
| H1 | 零第三方依赖 | ADR-0001、README | 不能引入 ORM/驱动；依赖树必须保持为空 |
| H2 | 零 CGO | ADR-0001（`CGO_ENABLED=0`） | 排除 `mattn/go-sqlite3` |
| H3 | 单二进制 + 交叉编译 | 一个二进制拷到 ARM 盒子 | 不能依赖外部数据库进程 |
| H4 | 内存有界（1000 点/50 设备 ≤ 150MB） | NFR | 查询不能把整段时间的数据读进内存 |
| H5 | 7×24 常驻、SD 卡/闪存 | 现场部署 | 不能每条 fsync，不能无限增长 |
| H6 | 写入绝不反压采集 | 架构原则 | 历史写失败只能计数 |

### 2.1 访问模式（这是决策的关键）

把「历史」拆成真实查询后，只有四类：

1. 某点位最近 N 分钟/小时的原始点（画曲线）；
2. 某点位一段时间的定步长聚合（1m/1h 桶的 avg/min/max）；
3. 某点位某个时刻附近的值（排障时「三点半到底是多少」）；
4. 导出/备份（直接拷文件）。

**没有**：多点多列 join、任意维度 group by、全文检索、跨设备相关性分析、窗口函数、事务。

### 2.2 容量估算（诚实的数字）

单条记录约 **100 字节**（短键 JSON：`t/d/p/ty/v/q`）。容量完全由「点位 × 变化率」决定：

| 场景 | 记录速率 | 每天 | 256MB 能存 |
|---|---|---|---|
| 1000 点，值稳定，5 分钟心跳 | 3.3 条/秒 | ~28 MB | ~9 天（受 `maxAge=7d` 约束） |
| 1000 点，平均 5 秒变一次 | 200 条/秒 | ~1.7 GB | ~3.6 小时 |
| 100 点，1 Hz 变化 | 100 条/秒 | ~860 MB | ~7 小时 |

结论写在文档里而不是藏起来：**默认的 256MB / 7 天是为「点位多、变化慢」的产线场景调的**。高频点位必须靠 `deadband` 与 `minInterval` 压下来——这不是存储的缺陷，而是「历史是有界缓存」这个定位的直接后果。

## 3. 候选方案

| 方案 | 交付形态 | 依赖 | 结论 |
|---|---|---|---|
| A. SQLite（CGO，`mattn/go-sqlite3`） | 破坏 `CGO_ENABLED=0`，交叉编译需要每目标平台的 C 工具链 | 1 个 C 库 | **排除**（违反 H2/H3） |
| B. 纯 Go SQLite（转译版） | 可交叉编译，但引入数万行生成代码 | 1 个大依赖 | **排除**（违反 H1；且体积/审计成本高） |
| C. 外部 TSDB（InfluxDB/TDengine 等） | 需要独立进程/服务 | 外部系统 | **排除**（违反 H3；边缘盒子跑不动） |
| D. 嵌入式 KV（bbolt 等） | 可交叉编译 | 1 个依赖 | 排除（违反 H1，且仍需自己实现时间索引与降采样） |
| E. 自建 NDJSON 分段日志 | 标准库即可 | 0 | **采用** |

### 3.1 为什么 E 不是「重新发明数据库」

因为需求里没有「数据库」：

- **写入**是严格追加，不需要 B 树、不需要页管理、不需要 WAL 恢复协议（掉电丢最后一个缓冲周期是可接受的，历史不是账本）；
- **索引**只需要「段的首末时间」——两个时间戳，重启时读每个文件的首行与末行即可，不需要持久化索引；
- **查询**是单点位的顺序扫描，聚合在扫描时算，不需要物化视图；
- **保留**是整段删除，一次 `os.Remove`，不需要逐行墓碑与压缩。

把这几件事写出来大约 700 行，而引入一个数据库要付出的是**交付形态**（H1–H3），那是本产品最核心的差异化。

## 4. 设计要点

| 主题 | 决策 | 理由 |
|---|---|---|
| 记录格式 | 短键 JSON（`t/d/p/ty/v/q`），约 100B/条 | 比 `json.Marshal(Sample)` 小 2–3 倍；`ty` 必存，否则 `0` 与「没有值」不可区分；`bytes` 用 base64（JSON 字符串不能承载非法 UTF-8） |
| 分段 | `seg-<UnixNano>.ndjson`，默认 16MB | 查询打开的文件数可控；淘汰粒度不会一次扔掉一周数据 |
| 跨段 | 一条记录绝不跨段 | 被切开的半行会让整段尾部不可读 |
| 索引 | 只记每段首条/末条记录时间 | 重启耗时与数据量无关；不用 mtime 作上界（掉电重启后 mtime 会偏新） |
| 淘汰 | 整段淘汰，`maxBytes` 与 `maxAge` 取先到者，**永远保留至少一段** | 「没有数据」与「数据被淘汰」必须能区分 |
| 掉电 | 末尾半行 → 另起新段 | 接着半行写会把下一条正常记录拼进坏行，表现为「重启后第一条数据消失」 |
| 落盘 | 用户态缓冲 + 200ms 定期 flush，不逐条 fsync | SD 卡寿命与写入延迟；崩溃最多丢 200ms |
| 采样 | 事件驱动 + 心跳；死区、最小间隔、pending 补写 | 见领域模型 §11.1 |
| 查询 | 快照段索引（短锁）→ 锁外顺序扫描 | 一次大范围查询不能阻塞采集写入 |
| 损坏 | 跳过坏行并计数（`skipped`） | 丢一条记录远好过让整段查询失败 |
| 聚合 | 扫描时累加，桶对齐 `from + k*step` | 不物化；桶边界不随查询时刻漂移 |

## 5. 后果

### 5.1 正面

- 依赖树保持为空；`CGO_ENABLED=0` 交叉编译不受影响，产物仍是单文件。
- 历史是一个普通目录，运维可以直接 `cp`、`tar`、`rsync`，不需要导出工具。
- 崩溃恢复逻辑只有一条（半行处理），比数据库的恢复协议更容易验证。
- 查询路径完全在进程内，没有 IPC/网络/序列化开销。

### 5.2 负面与缓解

| 负面 | 缓解 |
|---|---|
| 不支持 SQL / join / 多点多列 | 北向 API 只承诺单点位；需要多点的消费方自己拉多条（文档明确写清） |
| 大跨度查询要全段扫描 | 桶数上限 5000 + `step` 强制；跨度越大越应该用聚合 |
| 无压缩，磁盘占用偏高 | 短键编码 + 死区/心跳/最小间隔；`maxBytes` 默认 256MB 是硬上限 |
| 段淘汰粒度粗（最坏丢 16MB 的数据） | `segmentBytes` 可调；这是「简单」换来的代价，明确写进文档 |
| 手写存储的边界条件（并发删除、半行、时钟回拨） | 对应测试覆盖：并发 Write+Query、坏行、重开追加、乱序时间戳、淘汰保底 |

## 6. 什么时候应当推翻本决策

出现以下任一情况，说明访问模式已经越过「单点位时间范围查询」：

1. 需要**多点多列**对齐（同一张图上 N 个点位共享时间轴，且要求严格插值对齐）；
2. 需要**跨设备 join / 相关性分析**；
3. 需要**样本级删除/更正**（GDPR 式的按记录删除）；
4. 单站点历史数据稳定超过 **数十 GB**，或需要压缩率 < 10%；
5. 需要把历史直接暴露成 SQL/Arrow 接口给 BI 工具。

此时的正确动作是**替换 `internal/history` 的实现**，而不是在 NDJSON 上继续加索引、加缓存、加查询语言——那会得到一个自制的、更难维护的数据库。

---

## 7. 替换边界（接口契约）

上层（`runtime` / `httpapi`）只依赖这 5 个方法，替换实现不需要改北向契约：

```go
func Open(o Options) (*Store, error)
func (s *Store) Write(r Record) error
func (s *Store) Query(q Query) (Result, error)
func (s *Store) Stats() Stats
func (s *Store) Flush() error
func (s *Store) Close() error
```

其中对外的语义承诺写在 `docs/03-product/05-northbound-api-spec.md` §4.8.5（采样、保留、落盘、重启、时区），这些承诺与「用不用 SQLite」无关，是产品契约。换成 SQLite 时：

- `Options` 里的 `MaxBytes`/`MaxAge`/`SegmentBytes` 映射为 `PRAGMA page_count` + `DELETE` + `VACUUM`（或分区表删除）；
- `Query` 映射为一条 `SELECT ... ORDER BY ts` 与 `GROUP BY ts/step`；
- `Stats` 映射为 `page_count * page_size`；
- 北向 JSON 结构、错误码、时间语义**不变**。

---

## 8. 三条关键结论

1. **历史是「有界缓存」，不是「账本」。** 这个定位决定了它可以丢最后一个 flush 周期、可以整段淘汰、可以没有事务——而正是这些「可以」让它能用 700 行标准库代码替代一个数据库。

2. **交付形态是硬约束，不是偏好。** 零依赖、零 CGO、单二进制交叉编译这三条一旦让步，产品的差异化就不存在了；为历史这一点便利让步不划算。

3. **替换点必须提前画好。** 本 ADR 的价值不只在「选了 E」，更在 §6/§7：明确写出「什么时候该换」与「换的时候改哪里」，避免三后再在 NDJSON 上长出一个自制数据库。
