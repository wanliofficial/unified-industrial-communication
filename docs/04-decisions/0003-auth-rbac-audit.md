# ADR-0003｜认证、授权与审计：静态 Token + 三角色 + 哈希链日志

- **状态**：已决定（Accepted）
- **决策日期**：RBAC / 审计功能落地时
- **决策者**：架构组
- **影响范围**：`internal/auth`、`internal/rbac`、`internal/audit`、`internal/northbound/httpapi`、`server.users` / `storage.audit` 配置、`GET /api/v1/audit*`、`uic token`
- **相关文档**：`docs/03-product/05-northbound-api-spec.md` §2.2 / §4.9 / §4.10、`docs/03-product/02-architecture.md` §10、`docs/03-product/06-nfr.md` §4

---

## 1. 决策摘要

三句话：

1. **认证用配置里的静态 Bearer Token，一个 Token 一个具名用户；不做登录会话与口令。**
2. **授权按「动作」划分九项权限，收敛成 `viewer` / `operator` / `admin` 三个角色，且 `viewer ⊆ operator ⊆ admin`。**
3. **审计是 NDJSON 分段文件 + SHA-256 哈希链，默认开启；写失败只计数，绝不阻断业务。**

理由可以压成一句：

> 这一版的产品形态是「边缘网关 + 少量运维客户端」，不是面向终端用户的门户。任何需要口令存储、重置流程、会话清理的东西，都会增加一个必须 7×24 正确运行的持久化子系统，却不会让只有三类角色的系统更安全。

---

## 2. 背景：被拒绝的三个替代方案

### 2.1 方案 A：账号 + 口令 + 会话 Token（PRD 初稿）

| 维度 | 评价 |
|---|---|
| 安全收益 | 低。仍然要在网关上存口令哈希；首次改密、找回、锁定都要做 |
| 运维成本 | 高。现场经常没有可用的邮件/短信通道，忘记口令只能上机改配置 |
| 交付成本 | 高。会话存储、过期清理、并发登录策略、CSRF |
| 与本项目约束 | 冲突。ADR-0001 要求零第三方依赖、单二进制；会话持久化会把「拷一个二进制就能跑」变成「还要一个会过期的状态目录」 |

**结论**：不做。保留在 Wave 2 的产品化路线里（Web 控制台需要它时再做），但 Wave 1 不引入。

### 2.2 方案 B：只保留一个全局 `server.token`

这是项目已有的实现。问题是它无法回答审计里最重要的问题：**是谁做的**。

所有写入都会记成同一个 `api` 用户；一旦出现「谁把设定值改成 90」，日志只能证明「有人用了那个 Token」。多人共用一个 Token 时，这个字段没有信息量。

**结论**：保留字段做兼容（映射为名为 `api` 的 admin），但新部署必须用 `server.users`。

### 2.3 方案 C：JWT / OAuth2 / 外部 IdP

| 维度 | 评价 |
|---|---|
| 安全收益 | 中。能做短期 Token 与集中吊销 |
| 交付成本 | 高。需要密钥轮换、时钟同步、JWKS 拉取，或一个必须常驻的 IdP |
| 现场现实 | 产线网络经常与办公网隔离；引入外部 IdP 等于引入一个「网断了就登录不了」的单点 |

**结论**：不做。用静态 Token + 配置热更新，等价于「吊销 = 改配置，下一条请求生效」，在单站点规模下已经够用。

## 3. 关键设计点

### 3.1 Token 先哈希再定长比较

直接比较明文字符串会让「长度不同」比「长度相同但内容不同」快一点。长期观测能还原出 Token 长度——这不是理论问题，是计时侧信道的基本形态。

实现：服务端对请求 Token 做 SHA-256，与存储的哈希用 `crypto/subtle.ConstantTimeCompare` 比较，且**不提前 break**。配置可以只存 `tokenSha256`，明文不落盘。

### 3.2 无凭据 = open 模式，不生成默认口令

如果没配任何凭据就自动生成一个「默认口令」，它永远不会被改——这是 38 个参考方案里反复出现的失败模式（NFR §226 已把它列为红线）。

实现：`auth.Store.Open()` 为真时，请求被当作 `anonymous/admin`；启动横幅与 `auth_open_mode` WARN 明确说出「任何能连上端口的人都是 admin」。比偷偷生成口令诚实，也比直接拒绝启动更适合「先跑起来看看」的场景。

### 3.3 凭据表可整体替换（`auth.Reloadable`）

配置热更新要求「删掉的用户立刻失效」。如果 HTTP 层在启动时捕获了 `*auth.Store`，热更新只能换掉 runtime 手里的指针，HTTP 层仍对着旧表认证——配置说删了，进程还能用。

实现：`Reloadable` 内部是 `atomic.Pointer[Store]`；HTTP 层持有的是接口与 `Reloadable`，`buildAuth` 只调用 `Set`。已在进行中的请求用旧表完成，新请求立刻用新表。

**这是本 ADR 里唯一一个「不做就会静默出错」的点**：没有报错、没有日志，只有一个本该失效的 Token 继续工作。

### 3.4 权限按动作，而不是按资源路径

按路径授权会产生「同一个动作在两个端点上有两种权限名」的问题（`POST /points/{d}/{p}/write` 与 `POST /points/{d}/write`）。按动作授权把权限表收敛到九个词，路由只引用它们。

高危动作的判定放在 `rbac.CommandPermission`，与命令白名单在同一个仓库里评审：

| 命令 | 权限 |
|---|---|
| `outbox.drop` / `config.rollback` / `log.level` | `command.danger`（仅 admin） |
| 其余白名单命令 | `command`（operator 起） |

路由级只校验 `command`，handler 解析出 `action` 后再判一次。这样新增一个高危命令时，漏改路由不会把危险动作漏给 operator。

### 3.5 审计用哈希链，而不是「只写文件」

只追加的日志能证明「发生过什么」，但不能证明「没有被改过」。审计的全部价值在于事后可信，因此每条记录带 `seq`、`prev`、`hash`：

```
hash = SHA-256("时间长度:时间" + "用户长度:用户" + … + "prev长度:prev")
```

字段边界用「长度:内容」编码：直接拼接会让 `user="ab", action="c"` 与 `user="a", action="bc"` 得到同一个哈希——这不是理论漏洞，是任何手写链式哈希的第一批 bug。

### 3.6 审计失败不阻断业务

| 选择 | 后果 |
|---|---|
| 审计写失败 → 拒绝写点位 | 磁盘满导致产线停摆 |
| 审计写失败 → 计数 + ERROR | 丢一段追溯依据，但产线继续 |

选择后者，理由是可追溯性可以让位于可用性，但必须可见：`uic_audit_write_errors_total` 与 `audit_write_failed` ERROR 日志就是让人发现的入口。

## 4. 与参考方案的差异

| 常见做法 | 本项目 | 原因 |
|---|---|---|
| 默认 admin/admin | 无凭据即 open，且大声告警 | 默认口令永远不会被改 |
| 明文 Token 存配置 | 可只存 SHA-256 | 配置会被备份、贴工单、进 git |
| 登录会话 + 过期 | 静态 Token + 配置热更新 | 少一个必须常驻的持久化子系统 |
| 权限绑在页面上 | 权限绑在动作上 | 同一动作不能有两个权限名 |
| 审计是普通文本日志 | NDJSON + 哈希链 | 事后可信比「有日志」重要 |
| 审计写失败让请求失败 | 计数 + 告警 | 可用性优先，但必须可见 |

## 5. 后果

### 5.1 正面

- 凭据轮换 = 改配置 + apply，**下一条请求生效**；可双写过渡。
- 审计能回答「谁、何时、对哪个点、旧值/新值、结果、从哪来」，且可验证未被篡改。
- 零第三方依赖（`crypto/sha256`、`crypto/subtle`、`crypto/rand` 都是标准库）。

### 5.2 负面

- Token 不会过期，也不会自助轮换；轮换是运维动作。
- 没有账户锁定与失败次数限制；配置 Hot reload 之后仍然只能靠网络层限流。
- 审计不是加密的：能读文件的人能看到操作内容（但不含凭据）。
- 哈希链只保证「段内自洽 + 跨段连续」；整段删除会被 `seq gap` 发现，但如果从第一段开始整体重写，链无法自证（需要外部锚点，Wave 2 可做）。

### 5.3 退出条件

出现以下任一情况时，应替换本决策而不是继续加补丁：

1. 需要 Web 控制台的多用户自助登录（→ 会话 + 口令哈希 + 改密流程）；
2. 需要与企业 IdP / LDAP 集成（→ OIDC/SAML，放弃静态 Token）；
3. 审计需要防「整体重写」（→ 定期把 `lastSeq + lastHash` 锚定到外部系统）；
4. 单站点用户数超过约 50（→ 需要分组、批量管理与更细的权限模型）。

替换边界已经收敛：`auth.Store`（凭据判定）、`rbac.Can`（授权）、`audit.Store`（存储与校验）三个包的导出方法，HTTP 层与 runtime 只依赖这些方法。
