# ADR-0001｜实现语言选型：Go 为主，C# 为辅

- **状态**：已决定（Accepted）
- **决策日期**：项目启动阶段
- **决策者**：架构组
- **影响范围**：全部运行时、驱动 SDK、部署形态、招聘画像
- **相关文档**：`docs/02-synthesis/02-architecture-patterns.md`、`docs/03-product/02-architecture.md`

---

## 1. 决策摘要

**主运行时使用 Go（1.22+）；允许在 Windows 专用能力上使用 C# 编写独立辅助进程，通过本地 IPC 接入。**

一句话理由：

> 目标产品的差异化是「单二进制、可交叉编译、可无头运行、可被容器编排」，这四项在 Go 上是默认属性，在 C#/Java 上是需要持续对抗的工程约束；而 Go 的主要短板（工业协议库少）恰好是**我们无论如何都要自研**的部分（许可原因）。

同时明确：**如果评估权重偏向「协议生态现成度」而非「交付形态」，C# 会胜出**（见 §7 敏感性分析）。本决策不是「Go 全面优于 C#」，而是在本产品的约束下，Go 的综合得分更高。

## 2. 背景：需求对语言提出的硬约束

语言选型不能脱离产品形态。以下 10 条来自 `docs/02-synthesis/03-gap-analysis.md` 的 P0 缺口，是**硬约束**而非偏好：

| # | 约束 | 来源 | 量化指标 |
|---|---|---|---|
| C1 | 单文件交付，无运行时依赖 | G8 | 一个二进制 ≤ 40 MB，拷贝即运行 |
| C2 | 交叉编译到 linux/amd64、linux/arm64、windows/amd64 | G8 | 一条命令产出全部产物 |
| C3 | 无头运行 + 容器化 | G1、G8 | 镜像 ≤ 60 MB（distroless） |
| C4 | 常驻 7×24，内存有界 | G2 | 1000 点 / 50 设备常驻 ≤ 150 MB |
| C5 | 数百设备并发，单设备串行 | 架构决策 | 1000 设备时 goroutine/线程数 O(worker) |
| C6 | 位级编解码（位偏移、字节序、BCD、无符号） | 协议目录 | 无「无符号类型缺失」类障碍 |
| C7 | 串口 + TCP/UDP + TLS，且不引入 CGO | G8 | `CGO_ENABLED=0` 可构建 |
| C8 | 可测试：虚拟设备可在 CI 中跑 | G3 | `go test ./...` 无需外部依赖 |
| C9 | 插件扩展（第一版静态，第二版进程外） | G7 | 契约可版本化、可隔离 |
| C10 | 小团队（3–5 人）可持续维护 3 年 | 全局 | 单人可读懂核心链路 |

### 2.1 被排除的「伪约束」

以下需求常被拿来当语言选型理由，但在本产品中不成立：

| 伪约束 | 为什么不是硬约束 |
|---|---|
| 硬实时（μs 级） | 网关的闭环周期是 100ms–1s 级；μs 级实时属于 PLC/运动控制，不在本产品范围 |
| 极致吞吐（10 万点/秒） | 现场典型规模是 1 万点 / 秒级；瓶颈在协议往返而非语言 |
| GPU / AI 推理 | 边缘推理是 P2，且可通过 sidecar 调用 |
| 富客户端 GUI | 已决定 headless 优先，UI 是浏览器 |
| 与厂商 SDK 二进制兼容 | 通过辅助进程桥接（§8），不在主进程内 |

## 4. Go 的优势：逐条对应硬约束

### 4.1 C1/C2/C3 交付形态：默认属性，不需要工程对抗

```bash
CGO_ENABLED=0 GOOS=linux   GOARCH=arm64 go build -trimpath -ldflags="-s -w" -o uic-arm64
CGO_ENABLED=0 GOOS=linux   GOARCH=amd64 go build ...
CGO_ENABLED=0 GOOS=windows GOARCH=amd64 go build ...
```

三个产物、一条命令、零外部依赖。这不是「配置得好」，而是**语言运行时模型决定的**：Go 程序链接成静态可执行文件，不依赖 libc（`CGO_ENABLED=0` 时）、不依赖 JVM/CLR、不需要 `jlink`/`PublishSingleFile` 之类的打包技巧。

对比：

| 语言 | 单文件方案 | 实际体积（含运行时，量级） | 交叉编译 |
|---|---|---|---|
| Go | 原生 | 15–40 MB | 原生支持，改环境变量即可 |
| C# | `PublishSingleFile` + `SelfContained` | 60–120 MB | 需目标平台 SDK 或容器；AOT 有限制 |
| Java | `jlink` + `jpackage` | 80–200 MB | 需目标平台 JDK；jpackage 不能跨平台打包 |
| Rust | 原生 | 5–30 MB | 需交叉工具链（musl/链接器） |
| Node | `pkg`/SEA | 40–80 MB | 需目标平台二进制 |
| Python | PyInstaller | 30–80 MB | **不能跨平台打包**（PA-19 的实证） |

PA-19 的教训值得单独记一笔：该方案用 PyInstaller 打包，结果生成物只能在打包时的平台上运行，且需要 `_MEIPASS` 补丁处理资源路径——**「生成器」这个产品形态被打包工具的能力边界直接限制死了**。

### 4.2 C4/C5 并发与资源：goroutine 的「便宜」是真实的

| 指标 | Go（goroutine） | Java（平台线程） | C#（Task） |
|---|---|---|---|
| 单实例栈初始 | 2 KB（可增长） | 512 KB–1 MB | ~1 MB（线程） |
| 10,000 并发阻塞 I/O | 可行（~20 MB 栈） | 需虚拟线程（Java 21+）或 NIO | 需 async/await 全链路 |
| 调度 | 运行时 M:N 调度 | 内核调度（或 Loom） | 线程池 + 内核 |

1000 台设备、每台一个「逻辑串行队列」：

- Go：1 个设备 = 1 个 channel + 状态结构体，worker pool 复用 goroutine；常驻 goroutine 数 = O(worker)，内存增量 < 5 MB。
- Java（17）：要么 1000 个平台线程（~1 GB 栈），要么 NIO + 状态机（开发成本高）。
- C#：`Task` + `async` 可以做到，但**协议层若有一个同步阻塞调用，整个链路退化**——需要全链路 async 纪律，而工业协议库大量是同步 API（PA-10 的 `IPlcClient` 就是同步接口）。

**这不是「Go 更快」，而是「Go 的正确写法更便宜」。**

### 4.3 C6 协议编解码：无符号与位操作

Go 有完整的无符号类型（`uint8/16/32/64`）、`encoding/binary`（大小端）、`math/bits`（位操作）。工业协议需要的：

| 需求 | Go 写法 | 备注 |
|---|---|---|
| 大端读 u32 | `binary.BigEndian.Uint32(b)` | 标准库 |
| 字序交换（CDAB） | `bits.RotateLeft32` 或手写 | 一行 |
| 位提取 | `(v >> n) & mask` | 原生 |
| BCD 解码 | 手写 8 行 | — |
| 结构体映射 | `unsafe` 或手写（推荐手写） | 显式胜过隐式 |
| 无符号溢出检查 | 原生类型 | — |

对比 Java 的痛点（PA-25 作者在停更说明中明确提到）：**Java 没有无符号整数类型**，处理 `0xFFFF` 作为寄存器值时，必须提升到 `int` 并做掩码，任何一处遗漏就是符号扩展 bug。这不是不可克服，而是**每天都要多写一层防御**。

C# 在这一点上与 Go 相当（有 `byte/ushort/uint/ulong`，且 `BinaryPrimitives` 很好用），这是 C# 得分 5 的原因。

### 4.4 C8 可测试性

```bash
go test ./...            # 单元 + 集成，无需外部依赖
go test -race ./...      # 数据竞争检测（内置）
go test -bench . -cpuprofile cpu.out
go vet ./...
```

内置的 race detector 是工业协议实现的**关键工具**：多设备共享连接、串口互斥、缓存读写，这些正是数据竞争的高发区。C#/Java 需要额外工具（ThreadSanitizer 不支持托管代码；Java 需 jcstress）。

### 4.5 许可

Go 标准库 BSD-3-Clause；工具链 BSD；生态库以 MIT/Apache-2.0 为主。**没有运行时授权问题**。

C# 运行时为 MIT，但其工业生态的关键组件（OPC UA 栈的部分扩展、商业 PLC 库、控件库）多为商业授权或 Windows 绑定（PA-01、PA-04、PA-37 均有实证）。这不是语言问题，但会影响「零成本交付」的可行性。

## 5. Go 的短板：诚实清单

### 5.1 协议库少，且质量参差

| 协议 | Go 生态现状（本卷可核实） | 结论 |
|---|---|---|
| Modbus | 有成熟库（goburrow/modbus 等） | 可用，但需自建批量规划与串口治理 |
| S7 | 有若干实现，深度不一 | 建议自研（PA-15/24 的语义可参考） |
| OPC UA | 有 gopcua 等，服务端能力弱于官方栈 | **自研封装 + 关键路径自测** |
| BACnet | PA-27 内嵌一份完整 SDK | 深度最好，但许可需核实（该方案存在许可冲突） |
| MC / FINS / CIP | 零散、多为报文构造 | 自研 |
| IEC 104 / 61850 | 稀少 | 自研 |

**量化影响**：P0 六个协议中，Modbus/MQTT/REST 有成熟库，S7/OPC UA 需自研或深度封装。按 `04-protocol-catalog.md` §5.1 的估算，P0 总计约 74 人日——**这个工作量与语言选择无关**，因为许可原因我们不能直接复用 C# 商业库，而开源实现的深度普遍不足。

### 5.2 插件机制弱

`plugin` 包要求宿主与插件用**完全相同的 Go 版本与依赖**编译，且仅支持 Linux/macOS。这意味着：

- 第一版必须**静态注册**（驱动编译进主二进制）；
- 第二版必须走**进程外 gRPC**，而不是 `plugin`。

这已在架构决策中接受（`02-architecture-patterns.md` §8.2）。代价是「第三方驱动不能直接链接进主程序」，但收益是隔离与异构语言支持——对工业场景反而是优点。

### 5.3 错误处理冗长

`if err != nil` 的重复是真实成本。缓解手段：

- 在协议编解码层用 panic + recover 收敛（仅在纯函数内，边界处转 error）；
- 用 `errors.Join` / 自定义错误类型携带上下文；
- 关键路径用表驱动测试覆盖错误分支。

**评估**：这部分成本约占总开发量的 8–12%（推断），低于跨平台打包与运行时依赖带来的成本。

### 5.4 GUI 生态弱

不构成问题：已决定 headless 优先，UI 用 Web。若未来需要桌面壳，可用 Wails/webview 或直接打包浏览器。

### 5.5 泛型较新、生态惯用法仍在演化

Go 1.18 引入泛型，当前生态已基本适配。对本项目的影响主要在「通用解码器」与「集合工具」，可控。

## 6. 为什么不是 C#（最强竞争者）

必须承认：**如果只看「写出工业协议驱动的速度」，C# 是明显更优的选择。**

### 6.1 C# 的真实优势

| 优势 | 证据 |
|---|---|
| 协议生态最全 | PA-01 有 50 个协议家族、120+ 端点；PA-02 有 218 个协议调试页 |
| OPC UA 官方栈 | 官方 .NET Standard 栈成熟，服务端/客户端/信息模型齐全（PA-08 用到极致） |
| 语言表达力 | `async/await`、LINQ、`Span<byte>`、`BinaryPrimitives`、模式匹配 |
| 工具链 | Visual Studio / Rider 的调试与重构体验领先 |
| 插件隔离 | `AssemblyLoadContext` 是托管运行时里最好的插件隔离方案（PA-13 实证） |
| 串口/网络 | `System.IO.Ports` + `Socket` 开箱可用 |

### 6.2 但它在四个硬约束上持续失分

| 约束 | C# 的实际状况 | 代价 |
|---|---|---|
| C1 单文件 | `PublishSingleFile` + `SelfContained` 产物体积 60–120 MB；`PublishTrimmed` 对反射/序列化不友好 | 边缘盒子磁盘与升级带宽 |
| C2 交叉编译 | 需目标平台 SDK 或容器；`PublishAot` 跨平台交叉编译受限 | CI 复杂度上升 |
| C3 容器 | `dotnet/runtime-deps` 基础镜像 + 自包含产物，镜像通常 80–150 MB | 比 distroless Go 镜像大 2–3 倍 |
| C4 内存 | 空载 CLR 进程约 30–60 MB，加载 ASP.NET Core 后 80–150 MB；GC 堆随负载增长 | 512 MB 边缘盒子上余量紧张 |

再加上两个「非语言」问题：

- **OPC DA / COM / 厂商 SDK 只能在 Windows 上跑**——这会把「跨平台」变成「跨平台 + 一个 Windows 辅助机」，部署拓扑复杂化（PA-34/35 都是这个形态）。
- **生态中的关键组件许可复杂**：商业 PLC 库、控件库、OPC 栈扩展常常需要授权（PA-01/04/37 的商业模式即建立在此之上）。

### 6.3 结论

C# 适合「Windows 为主、协议为王的桌面/服务混合产品」。本产品的定位是「跨平台、边缘优先、可容器化的底座」，两者取向不同。

**如果未来产品转向「Windows 上位机 + 全协议调试台」，应重新评估并可能切换到 C#。** 这是明确的退出条件（§9）。

## 7. 敏感性分析：什么情况下结论会翻转

把权重做三组替换，重新计算：

| 场景 | 权重调整 | Go | C# | 结果 |
|---|---|---|---|---|
| **基准** | 见 §3.2 | **87.0** | 78.0 | Go 胜 |
| **生态优先** | 生态 30、交付 10 | 86.0 | **87.0** | **C# 胜** |
| **交付优先** | 交付 30、生态 10 | **88.0** | 72.0 | Go 大胜 |
| **团队熟悉 C#** | 开发效率 20、可维护 5 | 84.0 | **82.0** | Go 仍胜但差距缩小 |
| **只做 Windows** | 交付 10、生态 25、跨平台不计 | 80.0 | **85.0** | C# 胜 |

**读法**：

1. 只要「跨平台单二进制」是硬约束，Go 就领先；
2. 一旦放弃跨平台（只做 Windows），C# 反超；
3. 「团队是否熟悉」会把差距从 9 分压到 2 分——**这意味着如果团队是资深 C# 团队，选 C# 也是理性的**。

**本项目的判断**：跨平台单二进制不是「nice to have」，而是差异化支点（`03-gap-analysis.md` G8）。因此维持 Go。

## 8. 混合架构：Go 主进程 + 辅助进程

语言选型不是「全有或全无」。以下能力通过**独立辅助进程**实现，主进程通过本地 IPC 调用：

| 能力 | 辅助进程语言 | 原因 | 接口 |
|---|---|---|---|
| OPC DA 客户端 | C#（.NET Framework） | COM/DCOM 只能 Windows | 本地 gRPC / 命名管道 |
| 厂商闭源 SDK（FOCAS、部分机器人） | C++/C# | 仅提供 Windows DLL | 同上 |
| Windows 性能计数器 | C# | WMI/PDH | 同上 |
| 高性能 PCAP 抓包 | C/Go（`AF_PACKET`） | 需原始套接字 | 进程内 |
| AI 推理（可选） | Python | 生态 | HTTP sidecar |

**约束**：

1. 辅助进程**不得成为关键路径**——主进程必须在辅助进程不可用时降级（该协议标记为 `unavailable`，其余协议正常）；
2. 辅助进程有独立版本与独立升级；
3. 通信协议版本化，主进程兼容 N-1 版本。

这套设计让「Go 的协议短板」变成「可插拔的外部能力」，而不是产品缺陷。

## 9. 后果与退出策略

### 9.1 正面后果

| 后果 | 说明 |
|---|---|
| 交付极简 | 单二进制 + 配置文件 + 数据目录，三个东西构成一个安装 |
| CI 简单 | `go build` + `go test` + `goreleaser`，无需目标平台 SDK |
| 部署面广 | x86/ARM、Linux/Windows、容器/裸机，同一份代码 |
| 资源占用低 | 1000 点场景常驻内存目标 ≤ 150 MB |
| 招聘可替代 | Go 开发者供给充足，且语法简单，C#/Java 工程师 2 周可上手 |

### 9.2 负面后果与缓解

| 后果 | 缓解 |
|---|---|
| 协议库需自研 | 第一版只做 12 个；编解码/传输分层复用；金报文驱动开发 |
| 插件只能静态注册 | 第二版进程外 gRPC；第一版通过「编译期注册表」保证可扩展性 |
| 错误处理冗长 | 约定：纯函数层 panic + 边界 recover；业务层显式 error |
| 缺少成熟 GUI | Web 控制台；必要时 Wails |
| OPC UA 服务端能力弱 | 自研封装 + 一致性测试；北向同时提供 REST/MQTT，降低对 UA 的依赖 |

### 9.3 退出条件（何时应推翻本决策）

出现以下任一情况，应启动语言重评估：

1. **P0 协议的自研成本超过估算 2 倍**（> 150 人日）且无可行替代库；
2. **目标客户 90% 以上为 Windows 且明确拒绝 Web 控制台**；
3. **需要与既有 C# 产品线深度集成**（同进程加载、共享类型）；
4. **Go 生态出现无法绕过的许可/安全问题**（例如核心依赖变更为 AGPL）。

**迁移成本估算**：核心运行时（调度/模型/北向）约 2.5 万行，迁移到 C# 约 4–6 人月；协议驱动可保留「帧级测试向量」，重写编解码约 2–3 人月。**总计约 7–9 人月**——可承受，但不是免费的。这就是为什么要在第一版把「协议知识库 + 金报文」做成语言无关的资产。

## 10. 决策记录

| 项 | 内容 |
|---|---|
| 决策 | 主运行时 Go；Windows 专用能力用 C# 辅助进程 |
| 版本基线 | Go 1.22+（使用 `slog`、`net/http` 增强路由、泛型） |
| 禁止事项 | 主进程引入 CGO；主进程依赖 JVM/CLR；使用 GPL/AGPL 依赖 |
| 强制事项 | `CGO_ENABLED=0` 构建；`go vet` + `-race` 进 CI；每驱动必须有金报文与虚拟设备 |
| 复审时点 | Wave 2 结束时（约 12 个月）复审一次 |
| 复审依据 | §9.3 的四条退出条件 + 实际人日偏差 |

## 11. 三条关键结论

1. **本决策的本质不是「Go 比 C# 好」，而是「产品形态优先于语言偏好」。** 当「单二进制 + ARM + 无头 + 容器」是硬约束时，Go 的默认属性直接消除了四类工程对抗；当这些约束被放弃（只做 Windows 桌面），C# 会反超 9 分（§7）。因此决策必须与产品定位绑定，不能抽离语境讨论。

2. **Go 的最大短板（协议库少）与我们的最大约束（许可不能复用商业库）恰好重合。** 既然 P0 的六个协议无论如何都要自研 74 人日，那么「生态里没有现成库」的边际成本远低于表面看起来的程度；真正的成本在虚拟设备与金报文（占 35%），而这部分与语言无关。

3. **混合架构让选型从「二选一」变成「分层」：** 主进程用 Go 保证交付形态，Windows 专用能力用 C# 辅助进程保证兼容性。这条设计同时保留了退出路径——若未来必须迁移，协议知识库与测试向量是可带走的资产，代码不是。
